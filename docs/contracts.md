# Kestrel contracts

Every component builds against these. Change them only together with all callers.

| Boundary | Definition |
|---|---|
| Telemetry, alerts, policy, actions, wire payloads | `crates/kestrel-common` (Rust, serde JSON) |
| Agent ↔ server transport | `proto/kestrel.proto` (gRPC, mTLS) carrying `kestrel_common::wire` JSON |
| Detection engine API | `crates/kestrel-detect/src/lib.rs`, `paths.rs`, `table.rs` (public items) |
| Tray ↔ agent | `kestrel_common::tray` over `\\.\pipe\kestrel-tray`, JSON lines |
| Console ↔ server | REST API below |

Product name: **Kestrel EDR**. Rule ids: `ST-01`…`ST-16` (stealer), `TP-01`…`TP-06` (tamper; `TP-06` is raised by the agent itself for the local turn-off switch), custom Sigma rules `SIG-<uuid8>`.

---

## REST API (console ↔ server)

Base path `/api`. JSON in/out, `snake_case` keys, timestamps are **ms since epoch** (integers), ids are UUID strings unless noted.

**Auth.** Session cookie `kestrel_session` (HttpOnly, Secure, SameSite=Strict) set by login. Mutating requests must send header `X-CSRF-Token` equal to the `csrf_token` returned by `/api/auth/login` and `/api/me`. API tokens (`Authorization: Bearer kst_…`) are accepted for SIEM/automation and skip CSRF.

**Errors.** Non-2xx responses have body `{"error": {"code": "not_found", "message": "…"}}`. Codes: `bad_request` 400, `unauthorized` 401, `forbidden` 403, `not_found` 404, `conflict` 409, `rate_limited` 429, `internal` 500.

**Lists.** Paginated lists accept `?limit=50&cursor=<opaque>` and return `{"items": [...], "next_cursor": "…"|null, "total": 123}`.

### Devices

`Device = {id, hostname, os_name, os_build, arch, domain, agent_version, status: "online"|"offline"|"degraded"|"isolated"|"paused", last_seen: ms, first_seen: ms, ip_addresses: [string], logged_on_user, group_id, group_name, policy_id, policy_name, policy_version_applied, tags: [string], health: AgentHealth (see kestrel-common wire.rs), open_incidents: int, cert_expires_at: ms|null, possible_duplicates: [device id], uninstall_token_set: bool, uninstall_token_pending: bool, pause: PauseState|null, capabilities: [string], removal: DeviceRemoval|null}`

`capabilities`: `Hello.capabilities` of the device's last connect (kept while it is offline), e.g. `live.files`, `live.desktop`, `agent.uninstall`. `removal`: see [Remove device](#remove-device-remote-uninstall).

`pause` (also `health.pause`): protection turned off locally with the tray switch, `PauseState = {mode: "detection_only"|"full", since_ms, until_ms: ms|null (null = until turned back on), by_user}` (`kestrel_common::pause`; `by_user` pseudonymised like `logged_on_user`). See [Local turn-off](#local-turn-off-tray-switch).

`logged_on_user` (and `health.logged_on_user`) is a pseudonym (`u_` + 16 hex) when the device's policy has `privacy.hash_usernames`. `possible_duplicates` lists devices that enrolled with the same hardware UUID; enrollment never re-binds an existing device id.

Status rule (SQL `device_status`, migration 0008): `isolated` if health.isolated; else `offline` if last_seen older than 3 min; else `paused` if `health.pause` is set (the agent clears it when protection comes back on; a pause still reported 10 min after its `until_ms` raises `TP-SRV-PAUSE-OVERDUE`); else `degraded` if !health.etw_ok or etw_events_lost increased in last hour; else `online`. `paused` ranks above `degraded` because a full turn-off stops the sensors on purpose.

Event-loss split (additive, 2026-10-22): `health.etw_events_lost` stays the total; agents from 2026-10-22 also report `health.etw_kernel_events_lost` (lost inside ETW: kernel session buffers full, the consumer could not keep up) and `health.sensor_internal_dropped` (dropped by the agent's own sensor queues and caps: raw queue / agent channel full, file-activity aggregator caps, persistence enrichment queue). Both are `u64|null`; `null`/absent = older agent (only the total is known). Since 1.1.6 the console device page's Sensor health "Events lost" row shows *"N lost by Windows, M dropped by Kestrel"* when the agent reports the split (the total otherwise), and the server's `TP-SRV-EVENTS-LOST` summary names both deltas and the dominant side when this and the previous heartbeat both carry the split (unchanged wording otherwise).

### Incidents & alerts

Alerts are grouped into incidents server-side: same device + same root process tree (topmost non-system ancestor GUID) within 30 min → same incident; an open incident whose root is one of the alert's ancestors (e.g. ClickFix: `explorer.exe` RunMRU alert → `powershell.exe` → payload, all rooted at system-path binaries) also absorbs it (exact root match preferred); otherwise new incident.

`AlertRow = {id, incident_id, device_id, hostname, ts, rule_id, rule_name, rule_author, severity, attack: [string], mode, summary, process_guid, image, data_at_risk: [DataCategory], actions: [ActionOutcome], status: "new"|"acknowledged"|"closed", protection_off: "detection_only"|"full"|null}`

`protection_off` (from `Alert::protection_off`, additive) is set when protection was turned off on the device when the alert fired: the alert was forced to Audit and no automatic action ran.

`Incident = {id, title, severity, priority: 0-100, status: "open"|"in_progress"|"resolved"|"dismissed", classification: null|"true_positive"|"false_positive"|"benign", assignee: User|null, device_id, hostname, user, created_at, updated_at, alert_count, rule_ids: [string], attack: [string], data_at_risk: [DataCategory], contained: bool}`

Priority = max alert severity base score + 10 if any `data_at_risk` + 10 if an **impact-stage** rule fired + 5 if not contained, capped at 100. Impact stage (v1.1) = an exfiltration-stage stealer rule (ST-04/ST-14) **or any ransomware `RW-xx` or credential-dumping `CD-xx` rule** — encryption and a finished OS-credential dump are where the damage is done, like stolen data leaving the device. Persistence (`PS-xx`) alone does not add it. SigmaHQ pack hits (`SIG-*`) never add it; the builtin they corroborate does.

Title auto-generated, first match wins: all alerts `TP-*` → `"Agent tampering on {host}"`; any `RW-*` → `"Ransomware activity by {image} on {host}"`; any `data_at_risk` → `"Credential theft by {image} on {host}"`; any `CD-*` → `"Credential dumping by {image} on {host}"`; exfil-stage → `"Possible data exfiltration by …"`; any `PS-*` → `"Persistence planted by {image} on {host}"`; else `"{top rule name}: {image} on {host}"`. `{image}` is the first non-system process of the tree (the payload, not explorer/services).

### Local turn-off (tray switch)

Owner decision 2026-10-21 (`docs/DECISIONS.md`). Types: `kestrel_common::pause`.

* **Policy** `Policy.local_pause: LocalPause = {enabled: bool (default true), allow_full: bool (default false), max_minutes: u32 (default 480), allow_until_resumed: bool (default false)}`, `#[serde(default)]` (older policies get the defaults). `PUT /policies/:id` refuses `max_minutes` outside 1..=10080 (400). Offered durations: 15, 60, 240, 480 minutes capped by `max_minutes` (plus `max_minutes` itself when it is below 480 and not a step), and "until turned back on" only with `allow_until_resumed`. A `max_minutes` above 480 only raises the cap the agent accepts; the tray never offers more than 8 hours.
* **Tray side:** before sending `PauseProtection` (the only request carrying a secret) the tray checks that the pipe server process is `kestrel-agent.exe` in its own install folder (`GetNamedPipeServerProcessId` + `QueryFullProcessImageNameW`), on top of the session-0 check every connection gets; a service account in session 0 adding a pipe instance cannot collect the token.
* **Tray protocol** (additive): `TrayRequest::PauseProtection {token: string, mode: "detection_only"|"full" (default detection_only), minutes: u32|null (null = until turned back on)}` and `TrayRequest::ResumeProtection` (never a token). Both are answered with `TrayResponse::PauseResult(PauseResult {ok, error: null|"wrong_token"|"locked_out"|"not_allowed"|"already_off"|"not_off"|"unidentified"|"internal", message, attempts_left, locked_until_ms, denied: null|"disabled"|"mode_not_allowed"|"duration_not_allowed", state: PauseState|null})`; an older agent answers `Error`. `TrayStatus` gains `pause: PauseState|null` and `local_pause: PauseOffer|null` (`{enabled, allow_full, minutes: [u32], allow_until_resumed, locked_until_ms}`; `null` from older agents = hide the switch). `TrayStatus.state` keeps its usual value; the tray derives "Protection is off" from `pause`. Turn-off and turn-on also push a public `Notification`.
* **Agent enforcement** (`crates/kestrel-agent/src/pause.rs`): order of checks = caller identity (pipe client token user; unidentified = `unidentified`), already off, lockout, policy (`LocalPause::check`, never counted as a wrong token), token (Argon2id `verify_uninstall_token` on a blocking thread; never logged, stored, uploaded; `TokenInput`'s `Debug` is redacted). Wrong tokens: 5 per round, then a lockout of 1 min doubling per round up to 1 h; per device (not per pipe client), persisted in the agent store (`pause_lockout`) so restarts do not reset it; a correct token or 24 h without a wrong one resets the escalation. Every wrong token is reported (`AgentPayload::Pause{event: denied}` + `TP-06` alert) at most once a minute, plus always when a lockout starts.
* **Effect.** `detection_only`: sensors, detection, alerts and telemetry continue; `Engine::set_paused` forces every alert to Audit with `Alert::protection_off` set and lets no `Output::Action` out except `ResumeProcess` (open suspend windows are resumed at once, held autorun removals and ClickFix kills dropped); the agent additionally refuses every `ActionOrigin::Engine` action except `ResumeProcess`; automatic hardening (policy change, start, 15-min re-check) is neither re-applied nor reverted; analyst commands (`ActionOrigin::ServerCommand`) still run. `full`: the same, and the sensors are stopped and not restarted by housekeeping or policy changes; heartbeat, health, transport and tray continue.
* **State**: `PauseState` persisted in the agent store (`pause_state`, `%ProgramData%\Kestrel`), so it survives restarts and reboots; the agent turns protection back on at `until_ms` (checked every 5 s) and at start when `until_ms` passed while it was down. Turning back on restarts the sensors (full) and re-applies hardening. A new policy that disables the switch or `full` ends the pause (`reason: policy`); a lower `max_minutes` or a lost `allow_until_resumed` clamps `until_ms` to `now + max_minutes` (`event: clamped`).
* **Wire** (additive): `Hello.pause`, `AgentHealth.pause` (`PauseState|null`), `AgentPayload::Pause(PauseReport {event: "off"|"on"|"clamped"|"denied", ts, state, reason: null|"manual"|"expired"|"console"|"policy", by_user, failures, locked_until_ms})` (outbox priority High; older servers drop it). `ResponseAction::ResumeProtection` (`{"type":"resume_protection"}`, privilege `response.collect`, issued with `POST /devices/:id/actions`): the agent ends the pause (`reason: console`) or answers ok "nothing to do"; the engine can never issue it.
* **Server**: `pause_report` writes the audit entry (`device.protection_off`, `device.protection_on`, `device.protection_off_clamped`, `device.protection_off_denied`; actor system; target device id; details `{hostname, ts, mode, since_ms, until_ms, by_user, reason, failures, locked_until_ms}`) and updates `health.pause` at once; `Hello` sets `health.pause` too. While the current heartbeat reports a `full` pause, `TP-SRV-ETW` is not raised (a paused previous heartbeat counts as healthy, so sensors that fail to come back still raise it); `TP-SRV-EVENTS-LOST` is not raised across a full pause. `TP-SRV-PAUSE-OVERDUE` (medium): a heartbeat still carries a pause 10 min after its `until_ms` (agent clock set back, or the automatic turn-on failed). On start with protection still off the agent raises `TP-06` again ("started with protection still turned off").
* **TP-06** "Protection turned off on the device" (tamper, Audit, never acts, cannot be excluded): medium for detection only, high for completely off; info when protection comes back on or a pause is shortened; medium for a wrong token, high when a lockout starts. Built by `kestrel_detect::catalog::protection_alert`; the subject is the agent process with the tray user as `user`.

### Remove device (remote uninstall)

Owner request 2026-10-22. Uninstalls Kestrel from the PC and then removes the device from the device list (history kept).

**Who.** Privilege `devices.remove`, held only by the built-in `admin` role (through `*`), and only from an **interactive console session**: API tokens get 403 even with `*`; analyst / readonly 403.

**`POST /devices/:id/remove {purge_data, confirm_hostname, comment?}`.** Checks, in this order (error `reason` inside the `error` object): 403 privilege / API token → 404 device not found (also for decommissioned or removed devices) → 400 `confirm_mismatch` (`confirm_hostname`, trimmed, case-insensitive, must equal the hostname) → 403 `reauth_required` when the admin has MFA enabled and no `POST /me/reauth` in the last 10 minutes → 409 `agent_too_old` (the device's last `Hello.capabilities` lacks `agent.uninstall`) → 409 `no_uninstall_token` (the server holds neither a current nor a pending uninstall token) → 409 `removal_pending` (a removal is queued or running) → 429 `rate_limited` (at most 20 removal requests per admin per rolling hour, counted from `response_actions`; cancelled requests count). Success queues `ResponseAction::UninstallAgent{purge_data}` (`{"type":"uninstall_agent","purge_data":bool}`) with a **90-day** lifetime (other commands: 7 days), points `devices.removal_action_id` at it and delivers it now if the agent is connected. `comment` is cut to 500 characters.

**`DELETE /devices/:id/remove`.** Allowed only while the command never left the server (`pending`, never sent; one atomic `UPDATE … WHERE status = 'pending' AND sent_at IS NULL`, so a concurrent delivery wins or loses cleanly) → action status `cancelled` (`result_detail` "cancelled by <email>"), `removal` → `null`. 409 `already_started` once it was sent (also on a stream that dropped before the ack) or is `running`; 404 `no_pending_removal` when there is nothing to cancel.

**Token handling.** The uninstall token is **never** part of the action (actions table, `/actions`, audit, SSE, `pending_messages`). The server attaches it only when it sends the command on the agent's mTLS stream: `ServerPayload::Command{command_id, action, secret: {uninstall_tokens: [current, pending?]}}`, opened from the sealed columns (master key) at that moment. Both the current and a pending (rotated, not yet confirmed) token are sent, so a rotation in flight does not break the removal; the agent uses whichever matches its Argon2id hash. `CommandSecret`'s `Debug` prints only the number of tokens.

**Older agents.** Agents announce support with `agent.uninstall` in `Hello.capabilities` (stored as `Device.capabilities`); the console disables the button without it. A queued removal is never sent to an agent whose current `Hello` lacks the capability (downgrade, or not yet reported): the command is failed instead with `result_detail` "unsupported: the agent on this PC (version …) does not support remote removal; …". Older agents could not parse the action and would drop the whole message unacked.

**Lifecycle.** `DeviceRemoval = {state: "pending"|"removing"|"failed"|"expired"|"removed", action_id, requested_at, requested_by: string|null (name or email; for removed devices: who removed it), purge_data, started_at: ms|null, removed_at: ms|null, error: string|null}`, derived from the command's status:
- `pending`: action `pending` / `sent` (offline PCs get it when they next connect).
- `removing`: the agent answered `ActionOutcome{ok: true, artifact: "uninstall_started"}` → action status `running` (not completed).
- `failed`: the agent answered `ok: false` (`artifact: "uninstall_failed"`; e.g. token mismatch, helper missing, the server did not confirm the start in time, Windows Installer error code and log path), or the server failed it (agent too old, no readable token). Final; the device stays listed; the admin can request again. When the agent reports a failure the token had reached the PC, so the server rotates the uninstall token automatically (pending token, `SetUninstallToken`; audit `device.uninstall_token_rotated` with `reason`).
- `expired`: not delivered within 90 days.
- `removed`: the device stayed disconnected for **10 minutes** after the removal started (`running` only; the agent starts the uninstall only after the server acked its `uninstall_started` outcome). The server then, in one transaction: marks the action `succeeded`, sets `decommissioned_at` = `removed_at` and `removed_by` (= requester), expires its other pending commands and drops its pending messages. Its certificates are revoked **7 days** later (`REVOKE_AFTER_REMOVED_MS`). Until then a removed PC that connects again (the uninstall did not complete: shut down mid-way, installer rollback) is let in and the removal is undone: device back in the list, `decommissioned_at` / `removed_at` cleared, action `failed` ("the PC connected again after the removal: Kestrel is still installed there"), audit `device.remove.failed`, token rotated. A plain decommission never gets that grace. `GET /devices/:id` keeps working for removed devices; every other device endpoint answers 404.

Removal does not erase server-side history (alerts, incidents, actions, audit). The sealed uninstall token stays stored (not revealable for decommissioned devices).

**Audit** (target = device id): `device.remove.requested` {hostname, action_id, purge_data, comment, ip, online}, `device.remove.cancelled` {hostname, action_id}, `device.remove.started` {hostname, action_id, detail}, `device.remove.failed` {hostname, action_id, detail or error}, `device.remove.completed` {hostname, action_id, requested_by}, `device.remove.expired` {action_id}. Never the token.

**Agent side.** `UninstallAgent` runs only from a server `Command` with its `secret` (`Core::run_command_with`); `execute_action_as` refuses it for every origin (engine, local / tray, and a command without the secret). The agent verifies a delivered token against its Argon2id hash (mismatch → `ok: false`, nothing else happens), records the `uninstall_started` outcome in its command ledger (a redelivered command never starts a second removal), stores a marker, shows the tray notification "IT is removing Kestrel from this PC", queues the outcome and waits up to 5 minutes for the server's ack (no ack → the uninstall is not started and a failure outcome is queued), then starts the helper: a copy of `kestrel-uninstall.exe` in a new folder `%SystemRoot%\SystemTemp\kestrel-remote-uninstall-<uuid>` (or `Temp`) created with a protected SYSTEM / Administrators-only DACL, run as SYSTEM with `--quiet --token-stdin [--purge]` and `DETACHED_PROCESS | CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP | CREATE_BREAKAWAY_FROM_JOB` (retried without breakaway when the job does not allow it), the token written to its stdin only. The helper removes the product with `MsiConfigureProductExW(INSTALLSTATE_ABSENT, "UNINSTALL_TOKEN=… REBOOT=ReallySuppress")` (the package's custom action verifies the token again, V-M2), purges `%ProgramData%\Kestrel` link-safely when asked and the removal succeeded, schedules its own copy and folder for deletion at the next restart, and on failure writes `%ProgramData%\Kestrel\remote-uninstall-result.json` = `{exit_code, outcome, msi_code, message, log}` (never the token). Helper exit codes: 0 removed, 1 wrong token, 2 anything else. A still-running agent watches the helper and reports a non-zero exit with that file as `ok: false`; after an installer rollback the restarted agent reports it from the marker (or, after 10 minutes without a result file, that the removal did not finish).

### Remote access: remote desktop and file manager (admin only)

Owner request 2026-10-21 (see `docs/DECISIONS.md`). Wire types: `kestrel_common::remote`.

**Who.** Privileges `remote.desktop` and `remote.files`, held only by the built-in `admin` role (through `*`). Both also require an **interactive console session** (cookie + CSRF); API tokens get 403 even when they carry `*`. Analyst / readonly → 403.

**Remote-access profiles, install-time ceiling, effective profile.** `RemoteAccessProfile = {desktop: "off"|"view_only"|"control", files: "off"|"read_only"|"full", guardrails: RemoteGuardrails}`; `RemoteGuardrails = {require_consent, consent_timeout_secs (0 = 60), require_reason, require_mfa_reauth, allow_upload, allow_delete (also gates rename/move), max_session_minutes (0 = no limit), idle_timeout_minutes (0 = no limit), allowed_hours: null|{days: [0=Mon…6=Sun], start_minute, end_minute} (device local time, no wrap past midnight), blocked_paths: [path prefix]}` (`kestrel_common::remote`). Missing guardrail fields deserialize to the **guarded** defaults. Presets: `none()` (Off/Off), `unrestricted()` (Control/Full, every guardrail off, no limits), `guarded_default()` (Control/Full; consent, reason and MFA re-auth required; upload yes, delete no; 60 min max; 15 min idle; `C:\Windows\System32\config` blocked). The on-screen banner and the tray notification are mandatory in every profile.
* **Security boundary (read this before choosing a profile).** A file manager in `full` mode with uploads allowed is equivalent to running arbitrary code as SYSTEM on the device (for example by writing a DLL or a service binary into a system folder). Against a malicious or compromised admin account, the other guardrails (allowed hours, blocked paths, delete off, consent for later operations) are therefore **not a hard boundary**; they are accident and policy controls. The only hard boundaries are the install-time ceiling (`none()` devices cannot be opened by any server message) and `files: read_only` / `off`.
* **Ceiling:** the profile bound to the enrollment token (`remote_profile`, default `none()`) is returned in `EnrollResponse.remote_profile` and pinned by the agent in its protected config. No later server message changes it; only a new enrollment (reinstall with the uninstall token) does. Agents enrolled before profiles: ceiling `none()`. The server stores the token's profile as the device's `remote_ceiling` at enrollment; the agent reports its pinned ceiling in `Hello.remote_ceiling` and `AgentHealth.remote_ceiling`.
* **Policy:** `Policy.remote_access: RemoteAccessProfile` (default `none()`, also for policies saved before the field existed).
* **Effective** = `ceiling.intersect(policy)` (commutative, stricter wins: lower mode; a guardrail requirement if either requires it; `allow_*` only if both allow; smaller non-zero limits and consent timeout; allowed-hours intersection; blocked-path union). The agent enforces it and reports it in `AgentHealth.remote_effective`. The server computes the same from its stored ceiling ∩ the agent-reported ceiling ∩ the device's policy for its checks and the UI; the agent is the authority.
* **Consent** (`require_consent`): before a desktop session, and before the first non-read file operation (upload, mkdir, rename, delete) of a file-manager session (`fm_session`), the agent asks the employee through the tray (Allow / Deny, `consent_timeout_secs`); no answer, no signed-in console user or no consent-capable tray = deny. The agent sends `LiveAgentMsg::ConsentPending{request_id, timeout_secs}` meanwhile; the server extends its wait by that timeout (+ 15 s) and tells the console. Read-only operations never need consent.
* **Reason** (`require_reason`): the desktop `reason` query parameter / the file `reason` query parameter must be non-empty (400 `error.reason = "reason_required"`); it appears in the banner, the consent prompt, the tray notice and the audit log.
* **MFA re-auth** (`require_mfa_reauth`): the admin must have confirmed a TOTP code with `POST /me/reauth` in the last 10 minutes (403 `error.reason = "reauth_required"`; an admin without MFA gets 403 `error.reason = "mfa_not_enabled"`). Checked when a desktop session starts and on every file request (a file-manager session is a batch: one re-auth covers 10 minutes).
* **Hours / limits / blocked paths** are enforced by the agent (`outside_allowed_hours`, `blocked_path`) and, for desktop session length and idle time, also by the server's timers (effective values; 0 = no limit).

Error details such as `reason` and `remote_code` are fields of the `error` object itself (`{"error": {"code", "message", "reason", "remote_code"}}`).

**Preconditions (checked in this order, after RBAC).** Device exists (404) → device not decommissioned (409) → the effective profile allows the feature / operation (403 with `error.reason` = `"not_permitted"` when the device's install ceiling forbids it, `"disabled_by_policy"` when the policy does; `remote_code` likewise) → reason / MFA re-auth guardrails (above) → the agent is connected (409 `conflict`, message "device is offline") → the agent's `Hello.capabilities` contains `live.desktop` / `live.files` (409, message "the agent on this device is too old for remote access; update it"). The agent re-checks everything against its own effective profile.

**Paths.** Absolute Windows path `X:\…` or a drive root `X:\` (`/` accepted, normalised to `\`), ≤ 32,000 chars, no NUL / control characters, no `.` / `..` components, no `:` after the drive (alternate data streams), no `*?"<>|`, no component ending in `.` or space, no UNC / device paths (`\\server\…`, `\\?\…`, `\\.\…`): 400 `bad_request`. Validation is `kestrel_common::remote::validate_remote_path`, shared by server and agent. The agent additionally refuses (403, `remote_code: "protected_path"`) anything inside the Kestrel install folder or `%ProgramData%\Kestrel` (after resolving 8.3 names, junctions and symlinks), and renaming / deleting / overwriting any ancestor of them; network drives are refused too.

**Agent errors** map to HTTP as: `not_found` 404; `protected_path`, `blocked_path`, `access_denied`, `disabled_by_policy`, `not_permitted`, `consent_denied`, `outside_allowed_hours` 403; `reason_required` 400; `consent_timeout` 408 (`consent_timeout`); `already_exists`, `busy`, `integrity_error` 409; `invalid_operation`, `invalid_path` 400; `too_large` 413 (`payload_too_large`); `timeout` / no answer within 30 s 504 (`gateway_timeout`); `unavailable` 503 (`unavailable`); others 500. The error body carries `remote_code` (the `RemoteErrorCode`) next to `code` and `message`. Server-side failures: the agent stream ends during a request → 409 `conflict` ("device disconnected"); the agent's outbound queue is full → 503 `unavailable` (`remote_code: "unavailable"`); an unexpected reply → 500; a size / offset / SHA-256 mismatch the server detects in a transfer → 409 (`remote_code: "integrity_error"`).

**Audit** (hash-chained log, target = device id; details always include `hostname`, `ok` and, on failure, `error`): `remote.files.list` {path}, `remote.files.download` {path, bytes, sha256}, `remote.files.upload` {path, bytes, sha256}, `remote.files.rename` {from, to, overwrite}, `remote.files.delete` {path, recursive, removed}, `remote.files.mkdir` {path}, `remote.files.end` {fm_session, delivered}, `remote.desktop.start` {session_id, view_only, reason, effective profile summary}, `remote.consent` {kind, fm_session or session_id, result: "allowed"|"denied"|"timeout"}, `auth.reauth` {ok}, `remote.desktop.mode` {session_id, view_only}, `remote.desktop.stop` {session_id, duration_ms, ended_by: "admin"|"idle"|"max_duration"|"agent"|"disconnect"|"server", reason}. Frames and file contents are never logged, stored or sent to telemetry. As built: `remote.desktop.start` carries the effective profile summary as `profile`; file rows also carry `fm_session` (and `reason` when given) and every row the client `ip`. Precondition refusals (ceiling, policy, reason, MFA re-auth, offline, agent too old, desktop busy) are audited with `ok: false`; RBAC 403s and 400s for malformed input are not. `GET /files/stat` is audited as `remote.files.stat` {path}. Every operation runs (agent exchange + audit row) in a server task of its own, so a client that aborts the HTTP request — or disconnects in the middle of a download or upload — cannot skip the audit row (an interrupted transfer is recorded with `ok: false` and the bytes moved so far). `remote.consent` is written from the agent's `ConsentResult` (and inferred from the outcome for agents that do not send it). A desktop session that never started (agent error, consent denied / timeout, start timeout) is recorded as `remote.desktop.start` with `ok: false` and no `remote.desktop.stop`.

`RemoteAvailability = {available: bool, reason: null|"not_permitted"|"disabled_by_policy"|"offline"|"agent_too_old"|"decommissioned"}`. `GET /devices/:id` adds `remote_access: {desktop: RemoteAvailability, files: RemoteAvailability, ceiling: RemoteAccessProfile, ceiling_summary: string, policy: RemoteAccessProfile, effective: RemoteAccessProfile, effective_summary: string, agent_reported_ceiling: RemoteAccessProfile|null}` (present for everyone; only admins can use it). `ceiling` is the server's record from the enrollment token intersected with what the agent reports.

**Remote-desktop WebSocket.** Same-origin only: the `Origin` header must be present, `https`, and its host and port must equal the request `Host` (HTTP/2: `:authority`) exactly — port 443 may be omitted on either side — or its host must be one of `KESTREL_PUBLIC_HOSTNAME` **and** its port the server's HTTPS port; else 403. `csrf` (query) must equal the session's CSRF token (browsers cannot set headers on a WebSocket). All preconditions above are checked before the upgrade (HTTP error, no upgrade). One session per device: a second one → 409 naming the admin who holds it. Query: `view_only` (`1`/`true`), `quality` 30–90 (default 60), `scale` 25–100 % (default 100), `fps` 1–15 (default 8), `reason` (≤ 200 chars, shown to the employee). The busy check (409) also answers a plain `GET` without an upgrade, which otherwise gets 400 after every other check. With an effective `view_only` desktop mode, a `settings` message asking for control is answered with `{"type":"error"}` and the session stays view-only. The start deadline is 30 s, or the consent timeout + 30 s after `consent_pending`. The re-check fails closed: two consecutive failed checks (database errors) end the session (`ended_by: server`). The agent may always drop the session back to view-only (`DesktopInfo.view_only: true`), never raise it to control on its own. Mode changes are audited when they take effect.

* Server → browser **text** (JSON, `DesktopServerMsg`): `{"type":"starting","session_id","view_only"}`, `{"type":"consent_pending","timeout_secs"}`, `{"type":"consent_result","allowed","code"}` (both also mid-session), `{"type":"started", …DesktopInfo}`, `{"type":"info", …DesktopInfo}`, `{"type":"ended","reason","code"}` (then the server closes), `{"type":"error","message"}`, `{"type":"pong"}`.
* Server → browser **binary**: one frame per message: 16-byte header (big-endian `u32 seq`, `u16 width`, `u16 height`, `u64 agent ts ms`) + JPEG bytes. The server acks each frame to the agent once written to the socket (the agent keeps ≤ 3 in flight).
* Browser → server **text** (`DesktopClientMsg`): `{"type":"input","event": InputEvent}`, `{"type":"settings","quality","scale_pct","max_fps","view_only"?}`, `{"type":"activity"}` (admin present, resets the idle timer), `{"type":"ping"}` (answered with `pong`, does not reset idle), `{"type":"stop"}`. Max 64 KiB per message; input on a view-only session is dropped. `InputEvent` (`kind`): `mouse_move {x,y}`, `mouse_button {x,y,button: left|right|middle|x1|x2, down}`, `mouse_wheel {x,y,delta_y,delta_x}` (notches), `key {code, down}` (browser `KeyboardEvent.code`), `text {text}` (≤ 4096 chars), `ctrl_alt_del`, `release_all`; `x`, `y` normalised 0..1 over the captured virtual screen.
* `view_only` is forced on when the effective desktop mode is `view_only` (switching to control is refused). The session ends on: browser close / `stop` (`ended_by: admin`), the effective `idle_timeout_minutes` without input or `activity` (`idle`; 0 = never), the effective `max_session_minutes` (`max_duration`; 0 = no limit), agent end (`agent`), agent stream loss (`disconnect`), session revalidation failure every 60 s (`server`). The agent also ends a session after 90 s without any server message (the server pings every 20 s) and when its stream drops.
* The employee always sees a banner at the top of the screen ("IT (<admin name>) is viewing / controlling this PC" + reason) for the whole session and a Windows notification at start and end, in every profile; there is no hidden mode. With `require_consent` the session only starts after the employee clicks Allow.

**File-manager banner (mandatory, fail closed).** A file-manager session (`fm_session` + admin) gets the same on-screen banner, drawn by the same helper as remote desktop (independent of the tray window): "IT (<admin name>) is accessing files on this PC since HH:MM" (device local time) + " — Reason: …" when every active session gives the same reason; several admins are listed together. The agent shows it **before** the first operation of the session runs (also a plain listing) and re-checks it before every operation; a helper that died is restarted. If it cannot be shown (no console session, helper or banner window fails, the platform has no banner) the operation is refused with `remote_code: "unavailable"` (or `"timeout"`) → 503 / 504 and a message starting "the on-screen notice for the user at this PC could not be shown (…); remote file access is refused"; a new session does not start (no tray notice) and running file sessions end (transfers aborted, consents dropped). This mirrors the desktop rule (the desktop session also fails with `unavailable` when its helper / banner cannot start). While a desktop session runs, its banner carries the file notice as an extra part ("IT (Jane) is viewing this PC  |  IT (Bob) is accessing files on this PC since 14:02") and the stand-alone file banner is closed, so there is one banner on screen; when the desktop session ends with file sessions still active, the file banner is shown before the desktop banner is removed (if that fails, the file sessions end). The banner ends with the last file-manager session: `FileSessionEnd`, `FILE_SESSION_IDLE_MS` without operations, stream loss, files switched off by policy, agent shutdown. Notify-only profiles (no `require_consent`) still never ask; the banner and the tray notification are not consent.

**Agent side (`ServerPayload::Live` / `AgentPayload::Live`).** One `session_id` per desktop session, per download, per upload and per single file operation. File ops are `LiveServerMsg::FileRequest{request_id, op}` → exactly one `LiveAgentMsg::FileReply{request_id, reply}`. Reads within a download session must be sequential from 0 and the agent keeps the file open; the `eof` reply carries the SHA-256 of all bytes read. Uploads: `write_begin{path,size}` → `write_chunk{offset,data_b64}`… → `write_end{sha256}` (temp file `.<name>.kestrel-upload-<random>.tmp` in the target folder, created exclusively, renamed over the target after verification; `write_abort`, a mismatch, 120 s without a chunk, or stream loss deletes it). `FileRequest.context = {fm_session, admin_name, reason}` (absent from older servers: treated as its own session with no reason). `LiveServerMsg::FileSessionEnd{fm_session, admin_name}` (no reply; ignored as `unknown` by older agents) ends that admin's file-manager session on the agent. Platform hooks (`kestrel_platform::remote`): `RemoteDesktop::show_banner(text) -> SessionBanner` (returns only once the banner is on screen; Windows: the desktop helper in banner-only mode, `HelperSettings{banner_only: true, files_notice}`, which reports `BannerShown` on the pipe and starts no capture or input thread) and `DesktopSession::set_files_notice(text)`. Live messages are never queued in the agent outbox; the agent sends them with envelope seq 0 and does not ack server `Live` messages. Server limits: a decoded `live` payload larger than `LIVE_MAX_MESSAGE` + 64 KiB is dropped before parsing (rate-limited warning); per live session at most `DESKTOP_MAX_INFLIGHT` frames and 8 MiB (approximate payload bytes, including replies that arrived ahead of their request) may be queued — more closes the session ("the agent exceeded the live-session limits"). Downloads and uploads re-check the console session, `remote.files` and the effective profile every 16 chunks and at least every 60 s (failing closed); a failed check aborts the transfer (upload: `write_abort`) and is audited. `Hello.capabilities` lists `live.files` / `live.desktop` when the platform supports them.

### Evidence capture for suspected data theft

Owner decision 2026-10-25 (`docs/DECISIONS.md`). Types: `kestrel_common::evidence` (policy, manifest, report, limits, `KEB1` container), `kestrel_common::seal` (`KSE1` at-rest encryption), console `EvidenceBundle` / `EvidenceDownloadTicket` (`console/src/api/types.ts`).

**Trigger.** An ST-02 or ST-04 alert in any mode (Audit included, and while protection is turned off in detection-only mode) starts a capture for the alerting process tree (the process, its descendants, its ancestors up to the first one in Windows / Program Files; ≤ 64 processes). A second trigger for the same tree within 10 min joins it (`alert_ids`).

**Parts** (`Policy.evidence: EvidencePolicy = {staged_files: true, secrets_list: true, secrets_copy: true, pcap: true, local_retention_days: 14}`, `#[serde(default)]`; all on by default; `PUT /policies/:id` refuses `local_retention_days` outside 1-365; all four off = no capture; `secrets_copy` needs `secrets_list`):

| Part | What | Limits |
|---|---|---|
| Staged files | Files the tree newly created (Kernel-File CreateNewFile only: a failed open never counts; in-place overwrites and appends are not seen) under user-writable locations (profile, AppData, Temp, Downloads, ProgramData, `\Windows\Temp`) from 120 s before the alert until 60 s after it; copied at the end of that window | 50 MB per file, 200 MB and 500 files per bundle |
| Secrets read (list) | Every credential-store file the tree opened (store, what it holds, path, size, first / last read, open count), from the engine's store classification | 200 stores |
| Secrets read (copies) | Those store files as they are on disk at capture time; a file another program holds without read sharing is `locked` ("locked, not copied") | 50 MB per file, 100 MB per bundle |
| Connection capture | pcapng of traffic matching the tree's remote IP / port / protocol tuples for 60 s after the alert (`PktMon.exe`, Windows 10 2004+) | 50 MB (circular: the oldest packets are overwritten), 16 filters |

Collection scope (review of the 1.1.7 integration, M1 / M2 / L2): every decision is made on the path the file system resolves (8.3 short names expanded, `EvidenceHost::resolve_path`) and checked again on the opened handle's final path before a byte is read. Copies come from the tree user's own profile: the exact folder of the account's SID (`ProfileList\<SID>\ProfileImagePath`, `EvidenceHost::profile_dir`) when it resolves, else exactly `X:\Users\<name>\` (never `<name>.<suffix>`); other users' profiles never; nothing under `\Users\` when the user is unknown. Outside the own profile (`\Users\Public`, `ProgramData`, `\Windows\Temp`, other folders) only staged files whose creation by the tree the sensor confirmed (`StagedCandidate.confirmed`: Kernel-File CreateNewFile hints; `FileAccess` creates / writes are open attempts) are copied, and credential stores are listed but never copied (the sensor does not see whether an open succeeded and Kestrel copies as SYSTEM). Machine-secret locations are never copied: `ProgramData\Microsoft\{Crypto, Vault, Wlansvc, Windows\WER, Group Policy}`, `ProgramData\ssh`, `System32\config`, `System32\Microsoft\Protect`, `SysWOW64\config`, `Windows\{NTDS, repair, ServiceProfiles, Panther, Security, CCM, Minidump, LiveKernelReports}`, `System32\Sysprep`, `Windows\MEMORY.DMP`, `System Volume Information`, `pagefile.sys`, `hiberfil.sys`, `swapfile.sys`. Refused files are listed with status `error` and a reason. Ancestors join the tree only when they sit in a user-writable folder without a valid signature. Copies are read-only, sharing read / write / delete, opened with `FILE_COMPLETE_IF_OPLOCKED` (an oplock never makes Kestrel wait; a break in progress = `locked`), cloud placeholders are refused (never hydrated as SYSTEM), reads time out after 30 s and a build after 10 min; junctions, symbolic links, mount points, hard-linked files, alternate data streams and Kestrel's own folders are never followed or collected (`CopyStatus`: `copied`, `truncated`, `too_large`, `bundle_full`, `link`, `locked`, `missing`, `kestrel`, `not_a_file`, `error`, `disabled`). Filter limitation (recorded in `PcapInfo.filters`): other programs' traffic to the same IP:port is included; TLS / VPN traffic stays encrypted; loopback is not captured; a pktmon session someone else started is never taken over (`busy`).

**Bundle on the PC.** `%ProgramData%\Kestrel\evidence\bundles\<bundle_id>.kev` (SYSTEM / Administrators only): a `KEB1` container (entries `staged/NNNN-<name>`, `secrets/NNNN-<name>`, `capture.pcapng`, then `manifest.json` last; names `[A-Za-z0-9._-]`, no traversal) sealed with `KSE1` (AES-256-GCM, 1 MiB chunks, nonce = random 8-byte prefix ‖ chunk index, AAD = magic ‖ index ‖ last-flag ‖ bundle id) under a per-PC key stored DPAPI-protected (machine scope). Deleted after `local_retention_days` when nobody collects it, and after the server stored it. At most 2 uncollected bundles per program (image SHA-256), 32 and 2 GB in total, and never when less than 2 GB would stay free. Pcap filters never use ports 53, 88, 135, 139, 389, 445, 464, 636, 3268, 3269 (domain / file-server traffic of every program). With `privacy.hash_usernames` the profile folder name in uploaded manifest paths is pseudonymised.

**Wire** (additive):
* `AgentPayload::Evidence(EvidenceReport {bundle_id, alert_id, alert_ids, rule_id, state: "capturing"|"ready"|"failed"|"deleted"|"expired", ts, manifest: EvidenceManifest|null (with "ready", filtered by the device's privacy policy), bundle_size, bundle_sha256, local_expires_at, detail})`, outbox priority High. Metadata only. Server checks (review of the 1.1.7 integration, M4): `alert_id` must be an alert of this device with a trigger rule (ST-02 / ST-04), except that `capturing` / `failed` / `deleted` / `expired` may arrive before the alert (the agent queues them first); `ready` (the only state that stores a manifest) needs the alert. New rows are ignored when the device already holds 32 bundles that are open (`capturing`, `ready_on_device`, `collecting`) or name an alert the server does not have for it, or when the alert already has 4 bundles. The stored manifest is at most 1 MiB (lists halved, with a note; the bundle keeps the full one). SSE `evidence` events only on a real change.
* `ResponseAction::CollectEvidence {bundle_id}` / `DeleteEvidence {bundle_id}` (`{"type":"collect_evidence","bundle_id":"…"}`), privilege `evidence.download`, queued only by the `/evidence` endpoints (the generic `POST /devices/:id/actions` and checklist approvals answer 400). The agent refuses both from the engine and the tray. `CollectEvidence`: the bundle must be ready; the agent tells the employee in the tray ("IT collected evidence from this PC for a security investigation") and answers ok with `artifact` = bundle id. `DeleteEvidence`: ok also when already gone.
* `LiveServerMsg::EvidenceRead {request_id, bundle_id, offset, len ≤ 512 KiB}` → `LiveAgentMsg::EvidenceData {request_id, reply: FileReply::Data{offset, data_b64, size, eof, sha256 (on eof)} | FileReply::Error}`: sequential reads from 0 of the container plaintext, only for a bundle prepared by `CollectEvidence`; not subject to the remote-access profile. `Hello.capabilities` contains `evidence.v1` (`evidence::CAP_EVIDENCE`) on agents that support all of this.

**Server.** Table `evidence_bundles` (migration 0010). Statuses: `capturing`, `ready_on_device`, `collecting`, `stored`, `failed`, `expired`, `deleted`. After an admin collects, the server pulls the bundle (`EvidenceRead`), verifies size and SHA-256 against the report and the container format, stores it in `KESTREL_EVIDENCE_DIR` sealed with `KSE1` under a random per-bundle key (context = bundle id) kept wrapped with `KESTREL_MASTER_KEY` in `evidence_bundles.data_key_enc` and erased on delete / expiry (crypto-shredding). One pull per device, 60 s per chunk, overall deadline 5 min + 1 s per 64 KiB, and queues `DeleteEvidence` to the PC. Storage cap `KESTREL_EVIDENCE_MAX_GB` (default 20). Never written to the telemetry store, ClickHouse or hunt.

`EvidenceBundle = {id, device_id, hostname, incident_id, alert_id, alert_ids, rule_id, status, created_at, captured_at, manifest, bundle_size, bundle_sha256, local_expires_at, collect_requested_at, collect_requested_by, collected_at, expires_at, deleted_at, deleted_by, last_error, downloads, last_downloaded_at, device_online, agent_supports_evidence}` (user references are display names).

### Agent transport rules (server side)

- Enrollment always creates a new device id; a matching `os.hw_uuid` only flags `possible_duplicates`. `EnrollResponse.uninstall_token` is issued per device (`kun_…`).
- `AgentPayload::RenewCertificate{csr_pem}` on the stream → `ServerPayload::Certificate{cert_pem, ca_pem}` (CN = stream device id). The server sends `ServerPayload::RenewCertificate` after Hello when the presented certificate expires within 30 days. Older certificates of the device are revoked when it first connects with a newer one. At most 3 stream renewals per device per 10 minutes.
- `Hello.outbox_epoch` (random UUID created with the agent's outbox database, constant across restarts) change → the per-device seq high-water mark resets to 0 (`TP-SRV-OUTBOX-RESET`). Agents that send no epoch keep the old behaviour.
- Heartbeats: duplicates are detected by `seq`; `ts` is clamped to server time.
- `Hello.policy_version` / `rules_version` above the server's → server tamper alert **`TP-SRV-VERSION`** (Medium, at most once per device per hour; expected once after a database restore). The server then catches its counters up (bounded jump of 1,000,000) at most **once per device per 10 minutes**.
- A message the database rejects for its content is acked (it would block the outbox forever) **only** for SQLSTATE `22P05`, `22021`, `22P02`, `22003`, `22007`, `22008`; any other error closes the stream so the agent re-sends. The rejected message is recorded in `ingest_dead_letters` as metadata only (device, seq, payload type, database error with quoted input values redacted, payload byte length, payload SHA-256, received_at — never the unscrubbed content; newest 1000 rows per device, 30-day retention) and raises **`TP-SRV-INGEST`** (Medium, at most once per device per hour). An alert is stored in one transaction (alert, incident, actions, checklist, activity) before its evidence is copied to the telemetry store; an action result's status update and its side effects also commit together.
- Server-side scrub (defence in depth over the agent privacy filter): secrets are always redacted from command lines, script blocks, registry data, task actions, service image paths, WMI filter / consumer text and alert summaries. Per the device's policy, user names are pseudonymised (process users, task principals, service accounts, logged-on user), `capture_cmdline: false` truncates command lines, task actions and service image paths to the image and first flag, and `redact_path_prefixes` replaces matching paths (images, file paths, target images, file-activity samples, and paths inside task actions, service image paths, WMI text, registry data and summaries) with `[REDACTED]`.
- `ServerPayload::Command{command_id, action, secret?}`: `secret` (`CommandSecret{uninstall_tokens}`, additive, omitted when absent) is attached at send time only, today only for `uninstall_agent` (see "Remove device"). The in-memory map that tracks acks holds it; it is never persisted.
- `ServerPayload::SetUninstallToken{token}` carries a rotated uninstall token. The server tracks its seq like `Command` / `Policy` / `Rules` and promotes the pending token when the agent acks that seq and the token is still the pending one. It is re-sent after `Hello` while a rotation is pending and is never queued in `pending_messages` (no plaintext token at rest outside the sealed column).
- `ServerPayload::Update(UpdateManifest)`: `signature` is base64 Ed25519 over the UTF-8 bytes of `kestrel-update-v1\n{version}\n{url}\n{sha256}` (fields trimmed, sha256 lower-case hex; version and url must not contain line breaks), verified against the key embedded at build time (`KESTREL_UPDATE_PUBKEY`). The server sends it only for releases an administrator registered and promoted to the device's ring (see "Agent updates"): after `Hello` and when a ring is promoted (connected agents), never to decommissioned or `pinned` devices, and only when the newest non-halted release enabled for the ring is newer than `Hello.agent_version` (`kestrel_common::update::is_newer`). It is not acked or queued; it is re-offered on every `Hello` until the device reports the version.
- `AgentPayload::UpdateResult{version, ok, error}` (new, additive): the agent reports a failed update (no embedded key, bad signature, download error, hash mismatch, installer did not start) once per version + error. The server marks that device's delivery `failed`. Success is inferred from a later `Hello` with `agent_version >= version`. Older servers drop the message as malformed and ack it.

- Endpoint footprint (additive, 2026-10-25, agents 1.1.7+): `AgentPayload::Events{events, repeats?}`. `repeats: [EventRepeat{index, count, first_ts}]` (omitted when empty) marks `events[index]` as a summary that stands for `count` identical events (same process instance, kind and target; `count` includes the row itself) seen from `first_ts` to the row's `ts`, after a first copy that was uploaded as its own row. The server stores `repeat_count` and `repeat_first_ts` in that row's raw JSON (returned on device / hunt event rows, console type `DeviceEvent`); out-of-range indexes and `count: 0` are ignored. Older servers ignore the field.
- gRPC transport compression (2026-10-25): the server compresses responses with zstd only when the agent sends `grpc-accept-encoding: zstd` (agents 1.1.7+; older agents get plain frames). Compressed *requests* are refused with `Unimplemented`: tonic 0.12 inflates them without a size bound before any handler (an unauthenticated memory bomb via `Enroll`). Agents send plain frames; every outbox payload is zstd-compressed inside the envelope (`compressed`, inflation bounded by `MAX_PAYLOAD`).
- Heartbeat health (additive, 2026-10-25): `health.sensor_high_value_dropped` (part of `sensor_internal_dropped` that may blind a detection: high-value records lost to a full queue, persistence records, processes the file-activity aggregator could not track) and `health.sensor_events_total` (events the sensors delivered since the agent started); both cumulative, omitted by older agents. Device status `degraded` from event loss now needs, between two heartbeats, any increase of `etw_kernel_events_lost` or `sensor_high_value_dropped`, or a loss above 1 % of the interval's events (`ingest::significant_loss`); for agents without the fields any increase still counts (unchanged). `repeats` with duplicate indexes or beyond the number of events are ignored.

### Agent transport rules (agent side)

- Every server message with `seq > 0` is acked (`AgentPayload::Ack{seq}`, envelope seq 0) after it was handled. Exception: a `SetUninstallToken` whose new hash could not be stored (or an empty / oversized token) is not acked, so the server keeps it pending and re-sends it on the next connect.
- `SetUninstallToken`: the agent replaces `uninstall_token_hash` in `agent.toml` (Argon2id PHC; the token itself is never stored or logged) by writing a temp file, flushing it and renaming it over `agent.toml`, then acks. `kestrel-agent uninstall` / `release-isolation` verify against the new hash from then on.
- Certificate renewal: with < 30 days left (checked after `Welcome` and daily) or on `ServerPayload::RenewCertificate`, the agent creates a new key + CSR and sends `AgentPayload::RenewCertificate` (seq 0). On `Certificate` it swaps key and certificate (keeping the previous pair), reconnects, and deletes the previous pair after the next `Welcome`; after 3 failed connects with the new identity it restores the previous one. An interrupted swap is repaired at start.

## Agent CLI and tray (endpoint)

- `kestrel-agent uninstall --token <t>` and `kestrel-agent release-isolation --token <t>` (also `KESTREL_UNINSTALL_TOKEN`) need the device's uninstall token and administrator rights. `release-isolation` is the local break-glass for an isolated host that cannot reach the server: it removes Kestrel's isolation filters and the running service does not re-apply them.
- The MSI no longer takes an uninstall token at install; the server issues it at enrollment. If the server issues none (old server), `install` writes a random one to `C:\ProgramData\Kestrel\uninstall-token.txt` (administrators only), replaced at the next enrollment. MSI uninstall still needs `UNINSTALL_TOKEN=`.
- Tray pipe (`kestrel_common::tray`): every request is attributed to the pipe client's identity (its process token). `Activity` returns the caller's own items plus machine-wide ones; notifications go only to their owner's tray; `RequestReview` only for alerts the caller can see, once per alert until IT decides, at most 5 per user per hour; `QuickCheck` at most once per 5 minutes (a recent result is returned otherwise); `PauseProtection` needs the uninstall token and an identified caller and is rate-limited per device, `ResumeProtection` needs nothing (see [Local turn-off](#local-turn-off-tray-switch)).

## Event provenance fields (v1.1, additive)

- `registry_set`, `task_registered`, `service_installed`, `wmi_subscription` carry `attribution: "exact" | "heuristic" | "none"` (default `exact` for older agents). Only `exact` actors may be killed or rolled back; the console shows *writer inferred* / *writer unknown* badges in the device timeline, incident evidence and hunt results, and storylines append *(writer inferred)* / *(writer unknown)*.
- `registry_set.target` (additive, optional, 2026-10-21): `{path, signed, signer, sha256}` on-disk facts of the file the value starts, verified by the Windows sensor. Only filled for HKLM `RunOnce` values whose target is directly in `<system drive>:\ProgramData\Package Cache\<folder>\*.exe` (WiX Burn reboot continuation, PS-01); absent otherwise and from older agents.
- `process_start.agent_spawned: bool` — a direct child the agent itself started; the console labels it *started by Kestrel*.
- `file_activity.remote_writer: bool` (writes came via the System process from another machine over SMB; no local process is blamed) and `canary_in_place: bool` (decoy write found by content polling; the actor is inferred). Shown as *remote client over SMB* / *decoy write found by polling*.
- 1.1.6 file-activity semantics (additive): `file_activity.self_created: u32` (`#[serde(default)]`, 0 from older agents) = distinct touched files the process created itself (its first operation on the file was a create), including creates older than the 10 s window that the sensor still remembers (bounded at 2,048 self-created and 4,096 pre-existing files per process; only a CreateNewFile proves a create, a Create with FILE_CREATE may be a failed open); a renamed file keeps the mark. `new_files` now counts a file only when its first operation in the window is a create of a file the process did not know before (delete-then-recreate is a rewrite and counts in `overwrites`), and directories are never files, new files or note candidates. Pre-existing files touched = `files_touched - max(new_files, self_created)` (RW-06 counts only those). The console and the server storyline add *"(N created by the process itself, M existing files)"* when `self_created > 0`.

## Built-in rule semantics changed by the security fixes

- **ST-16 (canary tripwire).** Ignored readers: the agent itself, PID 0/4, and validly signed security, search-indexer, backup and management tools on the allow-list (Unknown signatures never count). In Protect mode a hit kills the reader's process tree, blocks the image's network (`BlockImageNetwork`, 24 h TTL) and quarantines the image; `IsolateHost` (server IPs permitted) is added **only** when the reader is unsigned / invalid / unknown **and** runs from a user-writable path. A hit by the store's own application (e.g. Chrome reading the decoy profile) is a High alert without actions.
- **Protected processes** (kill / suspend refused): one shared list for engine and agent, matched by name **and** exact path on the system volume **and** a valid Microsoft signature (Defender only in its real install directories).
- **Signatures:** `Unknown` is never trusted (owners, benign readers, allow IOCs, signer exclusions, protected processes). Late hash / signature facts re-run hash and cert IOCs, ST-12 and ST-08(b). Revoked certificates count as `Invalid`.
- **Exclusions:** path values keep the drive, `*` matches within one path segment and `**` across segments; exclusions never apply to `TP-*` rules.
- **ST-11** kills only the `nslookup` child, not its parent shell.
