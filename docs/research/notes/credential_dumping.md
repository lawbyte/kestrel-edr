# OS credential dumping (LSASS, hives, NTDS, DPAPI): techniques and user-mode telemetry

Research notes for the planned `CD-xx` rule family. Date: 2026-10-21.
Scope: what a user-mode Kestrel agent (SYSTEM service, real-time ETW, no kernel driver) can see and stop.
Items marked **[UNVERIFIED]** need a lab check in the disposable VM before a rule depends on them.

Licensing note: SigmaHQ rules are DRL 1.1, so a rule that ports their logic must show author attribution. Fibratus rules are Apache-2.0 (licence **[UNVERIFIED]**, check the repo `LICENSE` before porting text). Elastic rules are ELv2: we cite them only for context and copy no logic text.

## 1. Threat landscape 2025–2026 (short)

* LSASS dumping still separates EDRs. AV-Comparatives' **LSASS Credential Dumping Certification Test 2026** (8 May 2026) used standard/custom tools, LOLBins, Win32 vs direct/indirect syscalls, PPID spoofing, snapshot-based and staged dumps. Only 2 enterprise products were certified (≥2/3 of scenarios prevented or detected). https://av-comparatives.org/lsass-credential-dumping-certification-test-2026/
* A community "chokepoint" catalogue (updated 2026-03-30) tracks 24 variants. They fall into three stages that every variant must pass: handle acquisition → memory read → extraction/artefact. https://iimp0ster.github.io/detection-chokepoints/chokepoints/lsass-credential-dumping/
* New in 2025–2026:
  * **WerFaultSecure.exe abuse (Sep 2025).** An old Windows 8.1 build of the Microsoft-signed WerFaultSecure.exe, run as PPL via a CreateProcessAsPPL helper, writes an *unencrypted* LSASS dump. The dump is disguised as a PNG, so the header must be patched back to `MDMP`. The same primitive freezes EDR processes ("EDR-Freeze"). https://borncity.com/win/2025/09/28/windows-11-24h2-hackers-can-use-werfaultsecure-exe-to-steal-lsass-passwords-and-disable-security-software/
  * **KslDump (reported to MSRC Mar 2026, public Jul 2026).** It abuses Defender's Microsoft-signed `KslD.sys` by pointing `HKLM\SYSTEM\CurrentControlSet\Services\KslD\ImagePath` at an old vulnerable copy (plus an `AllowedProcessName` value) and reads LSASS memory without opening an LSASS handle. MSRC: not a vulnerability because admin is needed. Source is a secondary write-up, **[UNVERIFIED]** against MSRC. https://www.besthub.dev/articles/how-ksldump-uses-a-microsoft-driver-to-bypass-ppl-and-dump-lsass-credentials-via-registry-edit-3c40a1c05f4a
  * **PPLFault** (Elastic, 2022) was fixed in Insider Canary build 25941 (Sep 2023). The fix enforces page hashes for images on remote devices. It stays relevant on unpatched or older builds. https://www.elastic.co/security-labs/threat-command/inside-microsofts-plan-to-kill-pplfault
* Red Canary: Task Manager and rundll32 (comsvcs) are the built-in tools abused most often for LSASS dumps. https://redcanary.com/threat-detection-report/techniques/lsass-memory/

### 2.1 Why DCSync is out of scope
DCSync emulates DC replication: an account with "Replicating Directory Changes (All)" calls DRSUAPI `IDL_DRSGetNCChanges` against a DC over RPC. Nothing runs on the attacker host that looks like credential access. No LSASS handle, no hive file, and the process is often just a C2 implant or a remote impacket box that has no agent at all. MITRE's only analytic for it is unauthorised DRS replication calls from non-DC endpoints, which you see on the DC or the network. https://attack.mitre.org/techniques/T1003/006/
Kestrel v1 has no DC-side Security-log (4662) ingestion and no RPC/DCE parsing in its network telemetry (net_connect only gives the 5-tuple). The best Kestrel could do is a weak heuristic: "non-DC endpoint opens TCP 135 + high RPC port to a DC from an unsigned process". That is too noisy to ship. Record it as a server-side future item (`TP-SRV`-style correlation if DC logs are ever ingested).

### 2.2 Effect of LSA protection (RunAsPPL) and Credential Guard
* **RunAsPPL**: `HKLM\SYSTEM\CurrentControlSet\Control\Lsa\RunAsPPL` = `1` (with UEFI variable, sticky) or `2` (no UEFI lock, Win11 22H2+ only). Needs a reboot. Verify with System log **Wininit event 12** "LSASS.exe was started as a protected process with level: 4". On by default on *new* Win11 22H2+ installs that are enterprise-joined (AD/Entra/hybrid) and HVCI-capable, not on upgrades. Audit mode via IFEO `LSASS.exe\AuditLevel=8`; CodeIntegrity Operational events 3065/3066 (audit) and 3033/3063 (enforced). Audit is on by default on 22H2+, but no audit events are generated when Smart App Control is on. Plug-ins (smart-card, password filters) must be Microsoft-signed. https://learn.microsoft.com/en-us/windows-server/security/credentials-protection-and-management/configuring-additional-lsa-protection
* With PPL, a non-protected process cannot get `PROCESS_VM_READ`, `PROCESS_VM_WRITE`, `PROCESS_VM_OPERATION`, `PROCESS_DUP_HANDLE`, `PROCESS_CREATE_PROCESS`, `PROCESS_CREATE_THREAD`, `PROCESS_QUERY_INFORMATION`, `PROCESS_ALL_ACCESS`, etc. on lsass. Only `PROCESS_QUERY_LIMITED_INFORMATION` and similar remain. https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights. **Detection consequence:** on a PPL host, a PsOpenProcess on lsass asking for VM_READ shows up with a non-zero `ReturnCode` (STATUS_ACCESS_DENIED 0xC0000022 expected, **[UNVERIFIED]** exact code). A failed attempt is still a high-signal alert, because benign software that really needs memory access is either itself protected (MsMpEng) or asks only for query rights.
* **Credential Guard**: NTLM hashes, Kerberos TGTs and domain credentials stored by apps are moved into LSAIso (VBS). It does **not** protect local accounts, Microsoft accounts, NTLMv1/MS-CHAPv2/Digest/CredSSP, the NTDS database, keyloggers, or the use of already-available privileges. On by default on Win11 22H2+/Server 2025 devices that meet requirements (no UEFI lock). https://learn.microsoft.com/en-us/windows/security/identity-protection/credential-guard/how-it-works , https://learn.microsoft.com/en-nz/windows/security/identity-protection/credential-guard
  → SAM-hive dumping and LSASS dumping for local-account hashes stay valuable to attackers even with CG. Keep the rules on.
* **WDigest**: since Windows 8.1/2012 R2, `UseLogonCredential` is absent and treated as 0 (no cleartext). KB2871997 added the switch to older OSs. Setting it to 1 re-enables cleartext caching. https://adsecurity.org/?p=559 , https://www.cisa.gov/eviction-strategies-tool/info-countermeasures/CM0087

## 3. Microsoft-Windows-Kernel-Audit-API-Calls: exact schema

Provider GUID **`{e02a841c-75a3-4fa7-afc8-ae09cf9b7f23}`**, message file `Microsoft-Windows-System-Events.dll`. https://winevt-kb.readthedocs.io/en/latest/_sources/sources/eventlog-providers/Provider-Microsoft-Windows-Kernel-Audit-API-Calls.md.txt
The manifest has no keywords and no opcodes (task_0 only), and all events are version 0. Manifest (Win10 17134): https://github.com/repnz/etw-providers-docs/blob/master/Manifests-Win10-17134/Microsoft-Windows-Kernel-Audit-API-Calls.xml. Kernel function mapping: Elastic Security Labs "Kernel ETW is the best ETW", https://www.elastic.co/security-labs/kernel-etw-best-etw

| Id | Symbol | Kernel function | Payload fields (inType) |
|---|---|---|---|
| 1 | KERNEL_AUDIT_API_PSSETLOADIMAGENOTIFYROUTINE | PsSetLoadImageNotifyRoutineEx | NotifyRoutineAddress (Pointer), ReturnCode (UInt32) |
| 2 | KERNEL_AUDIT_API_TERMINATEPROCESS | NtTerminateProcess | TargetProcessId (UInt32), ReturnCode (UInt32) |
| 3 | KERNEL_AUDIT_API_CREATESYMBOLICLINKOBJECT | ObCreateSymbolicLink | LinkSourceName, LinkTargetName (UnicodeString), DesiredAccess, ReturnCode (UInt32) |
| 4 | KERNEL_AUDIT_API_SETCONTEXTTHREAD | NtSetContextThread | ReturnCode (UInt32) |
| **5** | **KERNEL_AUDIT_API_OPENPROCESS** | **PsOpenProcess** | **TargetProcessId (UInt32), DesiredAccess (UInt32), ReturnCode (UInt32)** |
| **6** | **KERNEL_AUDIT_API_OPENTHREAD** | **PsOpenThread** | TargetProcessId (UInt32), **TargetThreatId** (sic, UInt32), DesiredAccess (UInt32), ReturnCode (UInt32) |
| 7 | KERNEL_AUDIT_API_IOREGISTERLASTCHANCESHUTDOWNNOTIFICATION | IoRegisterLastChanceShutdownNotification | DriverName, ReturnCode |
| 8 | KERNEL_AUDIT_API_IOREGISTERSHUTDOWNNOTIFICATION | IoRegisterShutdownNotification | DriverName, ReturnCode |

Practical notes:
* **Source PID/TID = the event header** (the event is written in the caller's context). `TargetProcessId` is in the payload. There is **no GrantedAccess**: `DesiredAccess` is what was asked for. Seen on Win11 26200: `MAXIMUM_ALLOWED` shows as `DesiredAccess=0x02000000` while the real handle got 0x1FFFFF. Failed opens on an invalid target return `ReturnCode=0xC000000B` (STATUS_INVALID_CID) with `TargetProcessId=0xFFFFFFFF`, a sentinel that must never be resolved to a process. A plain elevated, non-PPL session receives the events. https://github.com/Karib0u/rustinel/issues/302
  → Kestrel must: treat `DesiredAccess & 0x02000000` (MAXIMUM_ALLOWED) as "could be everything"; keep `ReturnCode != 0` events as *attempts*; drop or flag sentinel targets; never rename DesiredAccess to GrantedAccess in the common types (Sigma rules that use `GrantedAccess` against our events are only approximate).
* Event 6 (thread open on an lsass thread) is the precursor for some dumpers and Fibratus uses it (`open_thread`). Lower priority.
* **WOW64 caveat**: a Microsoft Q&A (Sep 2024, unanswered) reports that event 4 (SetContextThread) is missing for 32-bit processes on 64-bit Windows 10/11. Whether event 5 also misses WOW64 callers is **[UNVERIFIED]**. Test with a 32-bit `OpenProcess` harness in the VM. https://learn.microsoft.com/en-us/answers/questions/2076764/microsoft-windows-kernel-audit-api-calls-etw-event
* **Blind spots of event 5** (inference from the function name; **[UNVERIFIED]**): only `PsOpenProcess` (NtOpenProcess path) is audited. Handles that come from `NtDuplicateObject` (technique 6), from `NtGetNextProcess` enumeration, or that the creator inherits from `NtCreateProcess*` probably do not raise event 5. Lab test: `NtGetNextProcess` loop to lsass, and DuplicateHandle from a process holding an lsass handle.
* **Volume**: event 5 fires for every OpenProcess on the box, so it is very noisy. Filter in the consumer callback *before* allocation: keep only `TargetProcessId ∈ {lsass pid}` (tracked from process_start of `\Windows\System32\lsass.exe` whose parent is `wininit.exe`) plus Kestrel's own pid (tamper rule) and the protected list. Everything else is dropped unless a broader rule needs it.
* **Optional call stacks**: `ENABLE_TRACE_PARAMETERS.EnableProperty |= EVENT_ENABLE_PROPERTY_STACK_TRACE` on `EnableTraceEx2` attaches `EVENT_EXTENDED_ITEM_STACK_TRACE64` (MatchId + return addresses, ≤192 frames, event dropped if >64 KB) to each event. https://learn.microsoft.com/en-us/windows/desktop/ETW/enable-trace-parameters , https://learn.microsoft.com/en-us/windows/desktop/api/Evntcons/ns-evntcons-event_extended_item_stack_trace64 . Fibratus-style module attribution (dbgcore/dbghelp/comsvcs/seclogon/"unbacked" frames) would be possible by resolving the addresses against Kestrel's image_load map for the source pid. Whether the stack property works for this kernel-emitted provider and includes user frames is **[UNVERIFIED]**. It costs CPU, so enable it only on event 5/6 for the lsass-filtered subset (the filter is applied after the stack is captured, so measure the overhead).

### 3.1 Access masks that matter for lsass
Rights from https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights :
TERMINATE 0x1, CREATE_THREAD 0x2, VM_OPERATION 0x8, **VM_READ 0x10**, VM_WRITE 0x20, **DUP_HANDLE 0x40**, **CREATE_PROCESS 0x80**, SET_QUOTA 0x100, SET_INFORMATION 0x200, QUERY_INFORMATION 0x400, SUSPEND_RESUME 0x800, QUERY_LIMITED_INFORMATION 0x1000, SYNCHRONIZE 0x100000, **ALL_ACCESS 0x1FFFFF**, MAXIMUM_ALLOWED 0x02000000 (generic).

| Mask | Meaning | Typical source |
|---|---|---|
| 0x1010 | QUERY_LIMITED + VM_READ | mimikatz sekurlsa classic |
| 0x1410 | + QUERY_INFORMATION | mimikatz, many dumpers, also some legit tools |
| 0x1038 / 0x1438 / 0x143a | + VM_OPERATION/VM_WRITE (read+write) | dumpers / injectors (Sigma memdump rule) |
| 0x1FFFFF | ALL_ACCESS | Task Manager dump, procdump, comsvcs MiniDump (MiniDumpWriteDump callers often request all) |
| 0x0810 | SUSPEND_RESUME + VM_READ | nanodump read mode (per chokepoint page) |
| 0x40 | DUP_HANDLE | handle-dup tricks; Process Explorer / Handle / THOR also ask for it (Sigma filters these) |
| 0x80 / 0x1080 etc. | CREATE_PROCESS | clone/snapshot/fork dumping, seclogon leak |
| 0x02000000 | MAXIMUM_ALLOWED | generic, resolves to full on non-PPL lsass for SYSTEM/admin+debug |
| 0x1000, 0x1400, 0x400, 0x100000 | query/sync only | benign enumerators (Task Manager list, monitoring), not alertable |

Masks from https://iimp0ster.github.io/detection-chokepoints/chokepoints/lsass-credential-dumping/ and the Sigma rules below. **Decision rule for Kestrel**: alert if `DesiredAccess & (VM_READ|VM_WRITE|VM_OPERATION|DUP_HANDLE|CREATE_PROCESS|CREATE_THREAD) != 0` or `DesiredAccess & MAXIMUM_ALLOWED`. That is the "dangerous bit set" approach (as in Fibratus), not an exact-value list, because tools trivially vary the extra query bits.

### 3.2 Known benign openers of lsass (seed allow-list; must be path + signer + mask scoped)
* `C:\Windows\System32\csrss.exe`, `wininit.exe`, `services.exe`, `lsm.exe`, `svchost.exe` (several services), `wmiprvse.exe`, `taskhostw.exe`, `msiexec.exe`, `MRT.exe`: Fibratus exclusions. https://raw.githubusercontent.com/rabbitstack/fibratus/master/rules/credential_access_suspicious_lsass_process_access.yml , https://raw.githubusercontent.com/rabbitstack/fibratus/master/rules/credential_access_potential_lsass_memory_dump.yml
* Defender: `C:\ProgramData\Microsoft\Windows Defender\Platform\*\MsMpEng.exe` (and mpengine.dll call traces with 0x1418), `MpClient.dll`/`mprtp.dll` call stacks; Sysmon `Sysmon64.exe`; `explorer.exe` with 0x401; Process Explorer / handle.exe / THOR / Aurora / MBAM with 0x40; VMware `vmtoolsd.exe`; VS Code; WebEx 0x401: SigmaHQ filters. https://detection.fyi/sigmahq/sigma/windows/process_access/proc_access_win_lsass_susp_access_flag
* Google Chrome updater makes needless calls to lsass (Microsoft ASR doc). Other EDR/AV agents, backup agents, password-sync tools (Quest Dirsync uses VirtualAllocEx in lsass), and smart-card/SSO middleware are similar. https://learn.microsoft.com/en-us/defender-endpoint/attack-surface-reduction-rules-reference
* `taskmgr.exe` asks for query rights to list lsass (benign). It asks for **0x1FFFFF** only for "Create dump file" (malicious context, alert).
* Exclusions must check **signer + exact path + mask** (Sigma notes that its generic "Program Files / System32" filter is a placeholder and should be replaced by specific AV paths). Attackers drop tools into Program Files or rename them, so plain path allow-listing is weak.

## 4. Other user-mode signals

* **Dump artefacts**: SigmaHQ "LSASS Process Memory Dump Files" (a5a2d357…, mod 2024-10-08) matches names such as `lsass.dmp`, `lsass*.dmp`, `\lsassdump`, `\nanodump*.dmp`, `PPLBlade.dmp`, `Coredump.dmp`, `SQLDmpr*.mdmp`. https://detection.fyi/sigmahq/sigma/windows/file/file_event/file_event_win_lsass_default_dump_file_names . Names are attacker-chosen, so add a **content check**: when a process that opened lsass with read rights in the last 2 min closes a file larger than 20 MB, read the first 4 bytes. `MDMP` (0x504D444D) means a minidump. Note that the WerFaultSecure variant patches the header to PNG, so also check the size of "images" written by that process. Fibratus correlates the lsass open with a `.dmp/.mdmp/.dump` create within 2 min, grouped by process. https://raw.githubusercontent.com/rabbitstack/fibratus/master/rules/credential_access_potential_lsass_memory_dump.yml
* **dbghelp.dll / dbgcore.dll image loads** by processes in user-writable paths (Temp, Downloads, Public, AppData\Roaming, Desktop) followed by an lsass open. SigmaHQ 9f5c1d59… (2025-11-27, experimental) does this with CallTrace. Kestrel can approximate it as IL(dbghelp|dbgcore) + PA(lsass, read bits) from the same pid. https://sigma.controlassurance.com/rules/proc_access_win_susp_dbgcore_dbghelp_load/ . FP: debuggers, crash reporters (Chrome/Electron crashpad, game anti-cheat, IDEs) load dbghelp all the time, so the image load alone is never an alert.
* **comsvcs**: rundll32 cmdline with `comsvcs` + `full` + (`MiniDump`|`#24`|`#+`/`#-`|`#65560`). SigmaHQ 646ea171… (mod 2025-02-23, level high, FP "Unlikely"). https://detection.fyi/sigmahq/sigma/windows/process_creation/proc_creation_win_rundll32_process_dump_via_comsvcs . Behavioural backup: rundll32 opening lsass with read bits at all (Sigma proc_access_win_lsass_dump_comsvcs_dll). https://detection.fyi/sigmahq/sigma/windows/process_access/proc_access_win_lsass_dump_comsvcs_dll
* **Generic SigmaHQ process_access rules**: "Potentially Suspicious GrantedAccess Flags On LSASS" (a18dd26b…, mod 2026-06-29) uses suffix/prefix mask matching with a large filter set. "Potential Credential Dumping Activity Via LSASS" (5ef9853e…, mod 2026-06-29) requires 0x1038/0x1438/0x143a/0x1fffff plus a dbgcore/dbghelp/kernel32/kernelbase/ntdll call trace, excludes SYSTEM (`AUTHORI`) source users, and has 0x1010/0x1410/0x40 **commented out as too noisy**. https://detection.fyi/sigmahq/sigma/windows/process_access/proc_access_win_lsass_memdump . These Sigma rules expect `GrantedAccess`/`CallTrace` (Sysmon EID 10). Through `rsigma` they only run against Sysmon EID 10 input, or via a field-mapping shim (DesiredAccess→GrantedAccess) that is **approximate**, so mark it as such in rule metadata.
* **SilentProcessExit**: SigmaHQ 55e29995… (critical, FP "Unlikely") matches any registry change under `…\SilentProcessExit\lsass.exe`. Fibratus matches `SilentProcessExit\lsass*`. Also watch `Image File Execution Options\lsass.exe\GlobalFlag`. https://detection.fyi/sigmahq/sigma/windows/registry/registry_event/registry_event_silentprocessexit_lsass/ , https://raw.githubusercontent.com/rabbitstack/fibratus/master/rules/credential_access_lsass_memory_dump_preparation_via_silent_process_exit.yml , background https://www.deepinstinct.com/blog/lsass-memory-dumps-are-stealthier-than-ever-before-part-2
* **WER**: Fibratus: WerFault.exe/WerFaultSecure.exe spawn, then a file with `lsass` in its path within 2 min. https://raw.githubusercontent.com/rabbitstack/fibratus/master/rules/credential_access_lsass_memory_dump_via_wer.yml . SigmaHQ "LSASS Process Dump Artefact In CrashDumps Folder" and the Application-log WER lsass-crash rule. https://detection.fyi/sigmahq/sigma/windows/file/file_event/file_event_win_lsass_shtinkering/ , https://detection.fyi/sigmahq/sigma/windows/builtin/application/application_error/win_werfault_susp_lsass_credential_dump
* **Clone/reflection**: Fibratus flags a new process created via `RtlCloneUserProcess`/`RtlCreateProcessReflection` (needs call stacks). https://raw.githubusercontent.com/rabbitstack/fibratus/master/rules/credential_access_lsass_process_clone_creation_via_reflection.yml . ## 5. False positives: how SigmaHQ and Fibratus handle them
* SigmaHQ keeps the lsass process_access rules at **medium** and disables the noisiest masks (0x1010, 0x1410, 0x40, 0x1000, 0x1400) in its generic rules. It splits FP handling into `filter_main_*` (always) and `filter_optional_*` (environment-specific tools) and combines path *and* mask (e.g. procexp only with 0x40, explorer only with 0x401). High-confidence rules key on a second signal (comsvcs/dbghelp in CallTrace, user-writable source path).
* Fibratus uses (a) the dangerous-bit set instead of exact masks, (b) process path exclusions for core Windows services, (c) a **call-stack signature check**: skip if all frames are Microsoft-signed *unless* dbgcore/comsvcs appear, and (d) **sequence correlation** (open → dump file within 2 min). It ships `kill` as the action only on the highest-confidence rule (MiniDumpWriteDump stack → `kill`, also on reflection clone).
* Microsoft ASR treats most lsass access events in Audit as noise and recommends deciding by outcome (Block), not by alerting on each access.
* Lesson for Kestrel: lsass-access alerts need ≥2 independent facts (dangerous bits **and** [unsigned/user-writable/LOLBin source **or** dump-file follow-up **or** dbghelp load **or** failed attempt against PPL]). Single-fact access alerts stay Audit and low severity.

## 6. Proposed rules CD-01 … CD-14

Common definitions:
* `LSASS` = process whose image is `%SystemRoot%\System32\lsass.exe` and whose parent is `wininit.exe` (track the pid; re-resolve on boot).
* `DANGEROUS(m)` = `m & 0x00FA != 0` (VM_OPERATION 0x8, VM_READ 0x10, VM_WRITE 0x20, DUP_HANDLE 0x40, CREATE_PROCESS 0x80, plus CREATE_THREAD 0x2) **or** `m & 0x02000000` (MAXIMUM_ALLOWED) **or** `m == 0x1FFFFF`.
* `BENIGN_OPENER` = exact-path + Microsoft/known-vendor signer list (§3.2), shared in `kestrel_detect::protect`-style data so admins can extend it via policy exclusions.
* Response safety: never act on protected/critical processes; re-check start time before kill/suspend. lsass itself is never the target of a response.

## 8. Exact sensor changes needed

1. **Kernel-Audit-API-Calls consumer (`kestrel-win` ETW)**
   * Ensure events **5 and 6** are enabled (no keywords exist, so enable with level ≥ 4 and `MatchAnyKeyword = 0`). Parse `TargetProcessId`, `DesiredAccess`, `ReturnCode` (and `TargetThreatId` for 6). Source pid/tid come from `EVENT_HEADER`.
   * Add `return_code: u32` and `target_tid: Option<u32>` to the process_access event in `kestrel-common` (`#[serde(default)]`). Keep the field named `desired_access`, and add a doc note that it is *not* granted access. Add `success: bool` (ReturnCode == 0).
   * Drop `TargetProcessId == 0xFFFFFFFF` sentinel events early (or mark `target_unresolved`).
   * In-callback filter: keep only targets in {LSASS pid, Kestrel pids, protected-process pids}, plus any target when the source is on a watch list. Count dropped events for health metrics.
   * Lab-verify: WOW64 callers, `NtGetNextProcess`, DuplicateHandle, MAXIMUM_ALLOWED, PPL denial ReturnCode value.
2. **LSASS identity + protection state**: on startup and on process_start, resolve the LSASS pid (image path + parent wininit). Query the protection level (`ProcessProtectionInformation`) and RunAsPPL/Credential Guard state, and expose it to the engine (`HostPosture { lsass_ppl: bool, cred_guard: bool }`) for CD-06/CD-13 and for UI.
3. **Dynamic file watch for dump follow-up (CD-04)**: when a non-benign pid gets a DANGEROUS lsass open, add that pid to a 120 s "watch" set. The Kernel-File consumer then passes *all* Create/Write/Close events for that pid (bypassing the sensitive-path source filter). On close of a file >20 MB (or any `.dmp/.mdmp/.dump`), a worker reads the first 4 bytes (`MDMP`) with `FILE_SHARE_*` read-only, no reparse following. Generalise the static FA filter to also include `*\lsass*.dmp`, `%LOCALAPPDATA%\CrashDumps\*`, `%TEMP%\*.dmp`, `\Windows\System32\config\(SAM|SECURITY|SYSTEM)`, `\Windows\NTDS\ntds.dit`, `HarddiskVolumeShadowCopy*` config paths, `…\Microsoft\Protect\*`, `…\Microsoft\Credentials\*`, `…\Microsoft\Vault\*`, `%SystemRoot%\System32\mimilsa.log|kiwissp.log`.
4. **Registry sensor path set (Kernel-Registry SetValueKey)**: add `…\SilentProcessExit\*`, `…\Image File Execution Options\lsass.exe\*`, `…\Control\Lsa\*` (Security/Authentication/Notification Packages, RunAsPPL, LsaCfgFlags, DisableRestrictedAdmin), `…\Control\Lsa\OSConfig\*`, `…\SecurityProviders\WDigest\*`, `…\Control\DeviceGuard\*`, `…\Services\KslD\*`, and new `…\Services\*\ImagePath` with `Type=1` (driver install). Also capture **DeleteValueKey** (RunAsPPL deletion = disable) if not already.
5. **Image load**: ensure lsass is not filtered out as a loader (CD-09) and that dbghelp/dbgcore loads by any process are emitted (CD-05). Signer info is already present.
6. **Optional stack traces (phase 2)**: enable `EVENT_ENABLE_PROPERTY_STACK_TRACE` for the Kernel-Audit-API-Calls provider only; resolve return addresses against the per-process module map from image_load; emit `call_trace_modules: Vec<String>` and `unbacked_frames: bool`. Benchmark CPU in the VM before enabling by default.
7. **Sigma interop**: map our process_access to Sigma `process_access` with `GrantedAccess := format!("0x{:x}", desired_access)` and `CallTrace` when available. Mark matches from this mapping as `approximate_fields=true` so analysts know.
8. **Not planned**: Security 4656/4663 SACL auditing on lsass (redundant with event 5, costly), DC-side DCSync (needs DC log ingestion), kernel ObRegisterCallbacks (needs a driver, v2).
