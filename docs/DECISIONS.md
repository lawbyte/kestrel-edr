### Real-Windows sensor findings (host, read-only `sensors-test --detect` + raw `logman`/`tracerpt` captures, build 26200)

* **Registry (known risk 2) — confirmed broken.** Microsoft-Windows-Kernel-Registry `SetValueKey` (event 5) arrives with `KeyName` **empty**; only `KeyObject` (a kernel pointer) identifies the key. `OpenKey`/`CreateKey` (2/1) carry `BaseObject` + `RelativeName`, but run at ~14 000 events/s on a busy workstation — too costly to decode just to build a name cache. **Decision:** keep event 5 for attribution (pid, value name, KeyObject; ~13/s) and add a user-mode watcher (`RegNotifyChangeKeyValue`) on the curated key set (HKLM + every loaded `HKU\<SID>` and `HKU\<SID>_Classes`) that diffs values and emits the full key/value/data; join the two on value name within a short window, then remember KeyObject→key for later writes. Unattributed changes are still emitted (pid 0 = unknown writer). *Alt:* OpenKey cache (CPU), NT Kernel Logger KCB rundown (all registry ops, far higher volume).
* **DPAPI 16385 (known risk 4) — flows without the Debug channel.** Field names match the decoder. The DPAPI hardening control stays (harmless) but is no longer required for ST-03.
* **Network byte order (known risk 3) — correct.** `Test-NetConnection example.com:443` produced a `net_connect` to the resolved IP and port 443; no swapped ports.
* **Short-lived command lines (known risk 6) — OK.** `cmd /c echo …` start carried its full command line.
* **DNS:** queries that end NXDOMAIN / no-records (`QueryStatus` 9003 / 9501) were dropped by the decoder. They are useful (DGA, dead resolvers), so they are now emitted with empty answers.
* **Audit-API OpenProcess volume (known risk 1) — ~500 events/s**, 98 % with desired access `0x1200` (query-limited + set-quota) from one service. Filtered at the source to masks that can read/write/inject/duplicate/terminate.

### Phase 3-4 design decisions

* **Rule families behind one seam.** RW/CD/PS rules live in `kestrel-detect/src/families/*` behind a `Family` trait (events, ticks, alerts in; `FamilyHit`s out) and go through the engine's single emission path (mode, exclusions, de-dup, protected-process filters). *Why:* three parallel implementers without touching the 3.4k-line `engine.rs`, and no second action path that could bypass safety filters. `FamilyHit.audit_only` marks variants that must never act even when their rule is in Protect.
* **SigmaHQ pack is Audit-only and seeded server-side** as ordinary Sigma rules with author, upstream URL (pinned commit) and `DRL-1.1`, so attribution shows wherever a Sigma alert shows and admins keep control of each rule.
* **M6 (enrollment token on the command line):** fixed with an MSI→registry hand-off (protected DACL via `MsiLockPermissionsEx` SDDL; the agent verifies the DACL, takes and deletes the value). *Alt:* a C++ custom-action DLL reading `CustomActionData` and piping the token on stdin — more code to sign and maintain. *Residual:* the **uninstall** token still reaches `kestrel-agent uninstall --token` through `WixQuietExec`; it is single-use for a device that is being removed and is admin-only; documented in HANDOFF.
* **Policy version after a DB restore:** the server catches up (re-versions past what the agent reports, bounded to +1,000,000 per report) rather than adding an epoch to the agent protocol. *Why:* server-only change, works with every agent already deployed. *Alt:* `(epoch, version)` tuples — needs agent + server changes and still breaks when the restored DB carries the old epoch.
* **YARA-X moved into `kestrel-scan.exe`.** The agent no longer links YARA-X/wasmtime; `Scan` runs the scanner next to the agent with a target list in the SYSTEM-only state directory and a 15-minute timeout. *Why:* the agent binary is always resident; scanning is rare.
* **Elevation on the host is interactive.** After the owner declined a UAC prompt, no further elevated runs on the host; all elevated validation happens in the QEMU VM over SSH as `labadmin`.
* **Sigma: an unknown field never matches.** rsigma treats a missing field as `null`, so upstream filters such as `filter_main_null: ParentImage: null` would silently *suppress* detections whenever Kestrel lacked the parent (process started before the agent). Kestrel now presents uncollected fields as "present but unknown", matching no value. Missing data can neither satisfy a selection nor suppress an alert; the cost is an occasional extra Audit alert.
* **Sigma `process_access` only receives successful opens** (Kestrel's new failed-open telemetry for lsass would otherwise satisfy rules written for granted handles); `GrantedAccess` is the *requested* mask, noted on those rules.
* **Sigma pack contents:** the 70 "ready now" SigmaHQ rules (pinned commit `e3f4662`), all Audit; Tier-B/C rules deferred. Upstream rule `a7ee1722` has a typo (`-DisableRuntimeMonitoring`) and does not catch `-DisableRealtimeMonitoring`; two other pack rules do.
* **Known risk 5 (`HistoricalContext` = LoggerId) — holds on build 26200.** The provider-disabled watchdog runs at start and every 30 s; during the 45 s host probe it ran at least twice against Kestrel-Core/IO and emitted no `EtwProviderDisabled` tamper event and restarted no session. A wrong logger id would have flagged every watched kernel provider. (TP-01 itself is exercised in the VM.)

### 2026-10-21 — security review v1.1 fixes: WFP identity, frozen isolation inputs, remote paths

* **V-H10: agent-scoped WFP permits match the process identity, not only its path.** Every permit with an `FWPM_CONDITION_ALE_APP_ID` (isolation server + DNS permits, always-on server hard permits) also carries `FWPM_CONDITION_ALE_USER_ID` with a security descriptor granting `FWP_ACTRL_MATCH_FILTER` (0x1, SDDL `CC`) to one SID only: the service SID `NT SERVICE\KestrelAgent` when the agent's token holds it (the service has been installed with `SERVICE_SID_TYPE_UNRESTRICTED`; checked at run time with `CheckTokenMembership`), else the token's user SID (LocalSystem for an install whose service has no SID type; the interactive user for a console run). *Why the service SID:* a user-started copy of `kestrel-agent.exe` has neither, and even a process an admin starts as SYSTEM lacks the service SID. **Fail closed:** without an identity no agent permit is planned; `IsolateHost` is refused with an explicit error (isolating anyway would cut the agent off until the auto-release deadline), and the always-on hard permits are removed rather than left app-only. The Windows glue also refuses to add any app-scoped permit without the user-id condition (invariant `app_permits_have_user_sd`). Hard permits whose stored plan differs (e.g. installed by an older version without the condition) are replaced.
* **V-M7: isolation inputs are frozen at isolation time.** The resolver set is recorded when isolation starts (`WfpState.isolation_dns`; for older state files, the resolvers the existing plan already permits) and re-plans never permit a resolver that appeared later. Server IPs are **never re-resolved while isolated** (the 60 s re-plan and the hard-permit refresh both use the frozen isolation server set). *Alt considered:* add a re-resolved IP only after a successful mTLS handshake to it — rejected for now: it needs a probe connection outside the transport and a WFP permit before the probe can run. *Trade-off:* if the server's address changes while a host is isolated, the agent loses contact until the isolation auto-release deadline or the local break-glass (`kestrel-agent release-isolation`).
* **V-M1: network paths are never opened as SYSTEM.** `kestrel_scan::is_remote_path` (UNC, `\\host@port\` / `\\host@SSL\` WebDAV, `\\?\UNC\`, `\\.\UNC\`, `\??\UNC\`, `\Device\Mup\`, redirector devices, any non-drive `\\?\` / `\\.\` path) plus `GetDriveTypeW == DRIVE_REMOTE` for drive letters. Applied to "scan running processes" target selection, explicit scan paths, the kestrel-scan target list (defence in depth), and enrichment (metadata, SHA-256, Authenticode/catalog, Zone.Identifier): facts for such images stay *unknown*. Directory expansion for scans no longer follows junctions/symlinks.
* **V-L10 / V-L11:** YARA `include` is disabled and compile errors are reported as file name + the diagnostic's first line only (the rest quotes rule source). Each scan writes its target list to a fresh `create_new` file with a random name in the state directory and deletes it afterwards.

### 2026-10-21 — security review v1.1 fixes: agent updates and the MSI (V-H3, V-L9, V-M3, V-M2)

* **V-H3: one update at a time, verified from disk, pinned until msiexec exits.** The update slot is a process-wide atomic claimed in the transport *before* the task is spawned; a delivery while one runs is dropped with a log line. The download goes to `<state>\updates\dl-<random>.part` (`create_new`, share mode 0), is renamed to `pkg-<random>.msi`, re-opened read-only with `FILE_SHARE_READ` only and hashed through that handle; the handle is held until msiexec exits (the hash from the network stream must agree too). *Why hold until exit:* the install runs while we wait; when the upgrade stops the service, the process dies and the handle closes with it, which is fine because msiexec has long opened (and cached) the package by then.
* **Authenticode on update MSIs is optional and off by default.** Build-time `KESTREL_UPDATE_REQUIRE_SIGNED=<signer subject substring>` makes the agent require a valid Authenticode signature from that signer; the owner has no code-signing certificate yet, so the Ed25519 manifest signature + SHA-256 remain the trust anchor. Until `kestrel-win` exports an Authenticode helper to the agent, a build with the variable set **fails closed** (no update installs). Recommended once a certificate exists.
* **V-L9:** download deadline 30 min overall, 60 s per read (and for the response headers / TLS handshake 20 s), and at least 64 KiB per 60 s window after the first byte.
* **V-M3: updates must be able to succeed and their outcome is reported.** msiexec `/i <pkg> /qn /norestart /l*v <pkg>.log` is waited for (max 60 min). Exit 0 / 3010 / 1641 = success (3010/1641 reported with a reboot note), anything else = failure with the code. `KV_LAST_UPDATE` is written only on success. The version is recorded as *pending* before msiexec starts: the MSI upgrade stops the service, so the **new** agent reports `UpdateResult ok=true` at start-up when the pending version is the one running, and a failure ("installer did not complete") when it is not. A failed version is retried at most every 6 h (`update_attempt` = `version|ms`).
* **MSI upgrade design:** `<MajorUpgrade Schedule="afterInstallExecute">` (install the new version over the old one, remove the old product last, so the enrolled identity, service registration and state survive), launch condition accepts `WIX_UPGRADE_DETECTED`, `CA_Install` (enrolment) runs only when `NOT Installed AND NOT WIX_UPGRADE_DETECTED`, and a `ServiceControl` (stop + start on install) in a component conditioned on `WIX_UPGRADE_DETECTED` restarts the agent around the file replacement (never on fresh install or uninstall, so an uninstall cannot stop the agent before the token check). `kestrel-agent install` also keeps an existing identity for the same server + CA instead of enrolling again. The Rust binaries have no version resource, so `DefaultVersion` makes the packaged copy replace the on-disk file (WIX1103 warnings are expected). The first upgrade from an already deployed 0.1.0 package uses the old package's uninstall condition (`NOT UPGRADINGPRODUCTCODE`), which still works.
* **V-M2: the uninstall token can no longer be skipped with `UPGRADINGPRODUCTCODE`.** `CA_Uninstall` runs on every `REMOVE="ALL"`; the custom action receives `UPGRADINGPRODUCTCODE`, the UpgradeCode, version and ProductCode and waives the token only when the claimed product is registered under Kestrel's UpgradeCode (`MsiEnumRelatedProducts`), installed (`MsiQueryProductState` = default), not this product, and newer. This relies on the new product being registered when the old one is removed (afterInstallExecute) — to be confirmed in the lab VM. Partial removal (`REMOVE=<features>`) is refused by an error custom action and the feature is `AllowAbsent="no"`. *Not done:* a TP alert for `msiexec /x` of the product code (engine side).
* **V-H1 (CLI):** `update-keygen` runs icacls from `GetSystemWindowsDirectoryW` (via `platform_win::windows_dir`), msiexec likewise; no executable path in the agent is derived from `%SystemRoot%` any more.
### 2026-10-21 — fix round 2, release candidate

* **Registry writer attribution: a sole candidate is Exact.** After round 1, every first write was Heuristic, so the PS rules could no longer act on malware's own first write (re-review NEW-1). Now one distinct writer pid in the join window is Exact. Two or more candidates are Heuristic, which still defeats framing a legitimate process, because the attacker's own write is always a candidate. Every change waits for its full join window, so a late rival write is still counted.
* **Re-planted autoruns are removed again.** `RemoveAutorun` bypasses the 10-minute de-duplication, gated to once per 30 s per object; a re-plant inside the gate is held, not dropped. The re-alert is limited to once per 10 minutes.
* **The agent's identity is image path + its own pid** (`HostContext.agent_pid`). A user who starts the real `kestrel-agent.exe` gets an ordinary process.
* **Engine-proposed quarantine never touches a validly signed file.** In shared folders (`ProgramData`, `Users\Public`, other profiles) it quarantines only files that are known unsigned or invalid; `Unknown` is refused there.
* **Canary reader exemptions require SYSTEM.** User-context backup tools (FileHistory, sdclt, an admin's scanstate) now trip ST-16. This is accepted: a stealer runs as the user.
* **Dead letters store metadata only** (length + SHA-256, redacted DB error), with 30-day retention and the newest 1,000 rows per device.
* **Version 1.1.0, tag `v1.1.0-rc1`.** An RC rather than final because the binaries are unsigned (Defender flags them) and the update signing key is not provisioned. Both are owner tasks.
* **Network blocks need an analyst "lift" action.** The lab showed that ST-02/ST-07/ST-16 image blocks are permanent (`ttl_secs: None`), and nothing in the console could lift them; a false positive on a business app would need a reinstall. Added `UnblockNetwork` (by image, block id, or all non-isolation blocks); restoring a quarantined file also lifts that image's blocks. Automatic blocks stay permanent by default, because a confirmed stealer should stay cut off until an analyst decides.
* **Lab VM hostname is `W-`.** The unattend `ComputerName` was not applied; the agent reports Windows' real name correctly. Cosmetic, lab only.

### 2026-10-21 — remote desktop and remote file manager (owner request)

* **The owner asked for VNC-style remote control and a full remote file manager in the admin console.** This reverses the "no screenshot/keystroke capture" privacy rule for **interactive, admin-initiated sessions only**; CLAUDE.md is updated accordingly.
* **Owner's choices:**
  * Screen sessions start **without employee consent**; the employee always sees a notification and an on-screen banner for the whole session.
  * The file manager has **full SYSTEM access** (browse, download, upload, rename, delete, mkdir) with no extra confirmation step.
  * Both are on by default in policy, and each has a policy switch.
* **Kept regardless:**
  * only the admin role can use them;
  * every session and file operation is in the hash-chained audit log;
  * frames and file contents never enter telemetry or ClickHouse;
  * the agent refuses when the policy switch is off.
* **Risk accepted by the owner:** a compromised admin account or server can now view and control every enrolled PC and read or modify any file on it. Recommend MFA for all admins and a restricted network path to the console.

* **Remote access is chosen per installer and locked on the device (owner request, refined).**
  * The admin web generates an installer per remote-access profile:
    * **None**;
    * **Unrestricted** (remote control + full file manager);
    * **Guarded** (remote control + file manager, with customisable guardrails: consent, reason, MFA re-auth, upload/delete, session and idle limits, allowed hours, blocked paths).
  * The profile is bound to the enrollment token and pinned on the agent at enrollment as a **ceiling** that later server messages cannot raise. The effective setting is the intersection of that ceiling and the policy, and the agent enforces it.
  * So "no remote access" devices stay closed even if the server or an admin account is compromised. Changing a device's profile requires reinstalling with the uninstall token.
  * Existing policies and previously enrolled agents default to **None**.
  * The banner and notification on the employee's screen are mandatory in every profile, including Unrestricted: covert screen viewing creates legal exposure under PDPA and UU PDP.
  * Building one MSI per profile is impractical, because WiX doesn't run on the Linux server. The server instead generates a setup script that embeds the server address, the agent CA, the MSI hash and the profile-bound token.

Base64 + zstd is acceptable for 5â€“10 fps JPEG.
* **Compatibility by capability, not by version.** `Hello.capabilities` (`live.files`, `live.desktop`) tells the server what the agent supports; the server returns 409 "agent too old" otherwise. The live message enums carry `#[serde(other)] Unknown` so either side can add message kinds later. An old agent that somehow receives a `Live` payload logs it as undecodable (not acked); an old server drops an agent `Live` as malformed (seq 0, not acked).
* **Interactive console session required, API tokens refused.** `remote.desktop` / `remote.files` are only reachable through the admin role's `*`, and additionally require a cookie session (CSRF-protected). *Why:* a leaked automation token must not be able to read or change files on every PC. The WebSocket cannot carry a custom header, so it takes the CSRF token as a query parameter and checks `Origin` against `Host`.
* **Server-side policy check as well as the agent's.** The server refuses with 403 `disabled_by_policy` before contacting the agent (clear UI message, no round trip); the agent still enforces its own copy of the policy (an agent with a newer/older policy is authoritative for itself).
* **Network paths refused.** The file manager accepts only `X:\â€¦` paths and refuses network drives, consistent with V-M1 (the agent never opens network paths as SYSTEM).
* **Protected folders:** the agent install folder and `%ProgramData%\Kestrel` are refused for every operation, and their ancestors for rename / delete / overwrite, after canonicalisation (8.3 names, junctions, symlinks). Uploads never open an existing file for writing (temp file + rename), so a hard link cannot be used to overwrite a protected file. *Residual:* reading a file through a hard link that an admin created by other means into a protected folder is not detected.

### 2026-10-21 - ST-16 false positive in the lab (Edge import) and a response safety net

**Finding.** Windows 11 lab VM, ST-16 in Protect. The employee opened Microsoft Edge (`C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe`, validly signed "Microsoft Corporation", parent explorer.exe). Edge's built-in "import from Chrome" scanned other browsers' profiles at start-up and opened `...\Google\Chrome\User Data\Profile 68\Google Profile Picture.png` inside the decoy Chrome profile Kestrel had planted (Chrome was not installed; the decoy made it look installed). ST-16 fired three times, killed the whole Edge tree and blocked Edge's network for 24 h. The alert text ("no legitimate program reads it") was wrong: browsers, password managers, backup/sync/AV and indexers legitimately enumerate or read other browsers' profiles.

**Decisions.**
* **ST-16 fires on secret material only** (`kestrel_detect::is_decoy_secret`): `Local State` (encryption key), `Login Data`, any *file* inside the decoy wallet-extension folder, `.aws\credentials` (and `Cookies` / `Web Data` should they ever be planted). Directory opens/listings, the extension folder itself and incidental profile files (pictures, `Preferences`, `Secure Preferences`, icons, `First Run`) never fire. *Why:* a stealer must read the secret files to steal anything; an import/backup scan usually touches the incidental ones first. Write/delete of a secret decoy still fires as before.
* **Decoys moved to defunct Chromium forks** stealers enumerate but mainstream import wizards do not offer: `%LOCALAPPDATA%\Kometa\User Data` (Kometa is in Lumma's built-in browser list - Cyble, SOCRadar) and `%LOCALAPPDATA%\7Star\7Star\User Data` (Vidar - Trend Micro). Each gets `Local State` (fake DPAPI-shaped `os_crypt.encrypted_key`), a `Default` profile (stealers always try `Default`) with `Login Data` and the fake MetaMask LevelDB folder. Nothing is planted under Chrome/Edge/Brave/Firefox/Opera/Vivaldi any more. If a fork's folder exists and is not Kestrel's (the user really has it), nothing is planted below it. *Alt considered:* keep the Chrome location only when Chrome is installed - rejected: Edge's importer enumerates Chrome's `User Data` whenever it exists, so the collision remains. *Residual:* stealers that only target mainstream browsers no longer trip ST-16; ST-01/02/03/04 cover reads of the real stores.
* **Migration.** On every plant the Windows agent removes decoys recorded in `canaries.json` that are not in the current spec set (files only while they still hold exactly our content, folders only when empty, deepest first, handle-based, never through a link), then removes the empty `Google\Chrome\User Data`, `Google\Chrome`, `Google` folders the legacy layout created implicitly. A changed file or a non-empty folder is left alone and forgotten. The engine no longer arms the legacy path.
* **Importers are Audit only.** A browser or password manager from the known-app table (valid signature by the expected signer + image name + genuine install location; not remote-controlled) reading decoy secrets raises a Medium **Audit** ST-16 alert with no actions, worded as a possible import. A renamed copy, an unsigned/invalid binary, a binary signed by someone else, a copy in a non-standard or user-writable folder, or a headless/remote-debugging instance still gets the full ST-16 response. Another browser-named "owner" (a fork not in the table) is only treated as an owner outside user-writable folders.
* **Global response safety net (all rules).** New `kestrel_detect::legit_apps` table (one place): Edge, Chrome, Firefox, Brave, Opera, Vivaldi, Bitwarden, 1Password, KeePass, KeePassXC, Office (WINWORD, EXCEL, POWERPNT, OUTLOOK, ONENOTE, MSACCESS), Teams (new MSIX + classic), Zoom, Slack, Adobe Acrobat/Reader, VS Code, Notepad++, OneDrive, Dropbox, Google Drive. The engine drops automatic `KillProcess` (incl. tree), `SuspendProcess`, `QuarantineFile` of the image and `BlockImageNetwork` against such a process, never opens a suspend window for it (an open one is resumed instead of escalated), appends "Kestrel did not stop <app> because it is a validly signed <vendor> application; review the alert" and reports the alert as Audit when nothing destructive is left. The Windows tree kill (engine-origin only) skips such an app when it is a *descendant* - plus its same-image helper processes - and names it in the outcome; an analyst's kill from the console is unchanged. Signer subjects verified on real binaries on 2026-10-21 (`Get-AuthenticodeSignature`): Microsoft Corporation (Edge, Office, Teams MSIX, OneDrive, VS Code), Google LLC (Chrome), Mozilla Corporation, "Brave Software, Inc.", "Zoom Communications, Inc." (Zoom's current name; the older "Zoom Video Communications, Inc." is kept). Opera Norway AS, Vivaldi Technologies AS, Bitwarden Inc. / 8bit Solutions LLC, AgileBits Inc., Dominik Reichl, DroidMonkey Apps, LLC, Slack Technologies, Adobe Inc., Notepad++, Dropbox, Inc and Google Drive paths are marked `signer_verified: false` in the table - verify on a lab image before relying on them. *Left out on purpose:* 7-Zip (binaries are not Authenticode-signed, so it can never qualify), Webex (install layout varies by deployment), Dashlane (Windows desktop app discontinued), NordPass and LastPass (signer/location not verified) - admins can exclude them per rule.
* **Never exempt:** LOLBins, script hosts and system tools (`legit_apps::NEVER_EXEMPT` plus the engine's LOLBin list: powershell, pwsh, cmd, wscript, cscript, mshta, rundll32, regsvr32, reg, sc, vssadmin, wmic, bcdedit, wevtutil, certutil, msiexec, installutil, msbuild, ...), even if placed in a known app's folder. A known app whose command line puts it under remote control (`--remote-debugging-port/pipe`, `--headless`, `--marionette`) is the attacker's instrument (ST-05/ST-06) and is not exempt. ST-07 still kills the process that injects into / opens the browser, never the browser. The protected/critical OS process list is unchanged; the safety net is an additional layer.
* **Residual risk:** per-user installs (`%LOCALAPPDATA%\Programs\...`, `%APPDATA%\Zoom\bin`, classic Teams, Chrome per-user) are user-writable: malware can copy a genuine signed binary there and side-load a DLL into it; that process is then alerted on but not killed automatically. ST-15 covers the known side-loading DLL names; a hostile-review follow-up should consider requiring the app's DLL directory to contain only validly signed modules before sparing it. Behaviour change worth knowing: RW-06 mass-rename by genuine VS Code (or Word, OneDrive...) is now alert-only.
**Addendum (same day) - global safety net withdrawn after hostile review** (`review-fp-safety-net.md`, findings F1-F9).
* **Withdrawn:** the every-rule "known app" sparing in the engine (no kill / suspend / quarantine / image block against listed apps, Audit downgrade) and the descendant sparing in the Windows tree kill. *Why:* a signature + path key is not an identity. Electron hosts (VS Code, Slack, Teams, Bitwarden, 1Password) run arbitrary JS (`ELECTRON_RUN_AS_NODE`, writable `resources\app` in per-user installs) - F1; tree kills spared the browser a stealer had launched and injected, neutering ST-07 - F2; per-user install folders are user-writable and the signature is checked on the file, not the mapped image (sideload / file swap) - F3; Office macro stealers would only be audited - F4; `--load-extension` and `-`/`/` switch prefixes bypassed the remote-control check - F5/F6. **1. Ransomware decoys visible on the Desktop (RW-07 when an employee tidies up).**
* *Root cause:*
  * `kestrel-win/src/rcanary.rs` planted the decoys **without** any attribute. The code justified this with "most ransomware skips hidden/system files", a claim with no source.
  * Two of the decoys were on the Desktop, the folder employees look at all day.
* *Second, independent cause of a Critical RW-07 when a person moves a decoy:*
  * The 2 s decoy poller (`win/rcanary.rs`) treated a decoy that **disappeared** (moved, deleted, recycled) as an *in-place rewrite*.
  * It blamed the last process that had opened the file (the V-H9 heuristic), or reported a "remote SMB writer" when the System process had opened it.
  * Kernel-File had already reported the rename/delete with the real actor: Explorer, which RW-07 already treats as alert-only.
* *Research* (`docs/research/notes/ransomware-decoy-attributes.md`, sources cited there):
  * No family we found skips hidden *files* by default.
  * Conti and Babuk source have no attribute check; Babuk resets attributes to NORMAL. Most families filter by name, extension or folder.
  * LockBit 3.0 has an optional `skip_hidden_folders`. It applies to folders, and our decoys sit in normal folders.
  * LockBit 2.0 applies its name/extension checks only to files *without* SYSTEM. So SYSTEM adds risk and no detection benefit.
* **Decision: FILE_ATTRIBUTE_HIDDEN only, on every decoy.**
  * The research suggested keeping one visible decoy per folder. Not done: visible decoys are exactly the reported problem.
  * Residual risk: a LockBit 3.0 build that also skips hidden files. This is unverified; testing it needs a real encryptor, which this project never runs.
* *Locations:*
  * Desktop decoys dropped:
    * it is the folder users browse most;
    * users with "show hidden files" on would still see them;
    * its traversal advantage is small (a depth-first walk reaches it just before Documents, and modern encryptors spread files over many threads).
  * Kept: 3 decoys in the Documents root and 2 in the Pictures root. These user-data roots come early in a profile walk and are browsed far less than the Desktop.
  * The profile root itself was considered: earliest in traversal and rarely browsed. Rejected because it is outside the file aggregator's scope and full of profile noise (`ntuser.dat`).
* *Upgrade:*
  * The planter re-applies HIDDEN to a decoy that still holds exactly Kestrel's content (`DecoyFs::ensure_attributes`).
  * The hash check and `SetFileInformationByHandle` use the same verified handle, opened with read-only sharing. The decoy is never recreated and its mtime is unchanged.
  * A decoy the user changed is never touched.
  * The 1.1.2 Desktop decoys (`RETIRED_DECOYS`) are removed when still exactly ours. A user-changed one is forgotten and left in place.
  * Credential canaries (ST-16) were already hidden; they now also get the attribute re-applied (same code path).
* *Poller:*
  * A disappearance is no longer an "in-place" hit.
  * It waits up to `GONE_GRACE_MS` (4 s) for the Kernel-File rename/delete of that decoy (`FileAgg::kernel_hit_since`, look-back 10 s), and is dropped when the kernel reported it.
  * Only when no kernel event arrives is it reported as before, so deletes Kernel-File might miss stay covered.
  * Real in-place modifications (file still there, size or mtime changed) are reported immediately, as before.
* *Explorer:*
  * Explorer is already on the protected-process list (`kestrel_detect::protect`, `%SystemRoot%\explorer.exe`, Microsoft-signed).
  * The engine already treats it as alert-only (High, no actions) for RW-07 / RW-06, so no rule change was needed.

**2. "Degraded" right after install (`etw_events_lost: 3390`, buffers lost 0).**
* *Conclusion: (b)/(c), an internal counter artefact of a sensor restart, not kernel loss.*
* *Evidence* (from reading the code path; the agent cannot run on the dev host):
  1. On a fresh install there is no cached policy, so the agent starts its sensors with the default policy. When the server's first policy arrived, `install_policy` compared it with "no previous policy" and **always restarted the sensors**, seconds after start.
  2. `Sensors::stop` set one shared stop flag:
     * The translator, the sole receiver of the 65 536-slot raw channel, exited within 100 ms.
     * The watchdog only stops the ETW sessions and event-log subscriptions on its next 500 ms tick.
     * Every event delivered in that gap failed `try_send` with *Disconnected* and was counted in `raw_dropped`. `SensorStats.events_lost` adds that to the kernel `EventsLost`.
     * Kernel-File (opens system-wide) plus Audit-API easily produce thousands of events in half a second during post-install activity.
  3. Buffers lost 0 fits: nothing was lost in the kernel.
  4. The server raises `TP-SRV-EVENTS-LOST` on a rise of 500 or more between two heartbeats, and marks the device degraded for 1 h on any rise. The first heartbeat (t = 0, before the restart) carried 0; the next one carried 3390.
* *Also found:* a sensor restart reset the kernel `EventsLost` part of the counter to 0, so losses of the old sessions vanished.
* *Fix (root cause, no grace period):*
  * (a) `Sensors::stop` stops the producers first (joins the watchdog, pollers and watchers). Then it tells the translator to **drain** its queue and exit (`kestrel-win/src/pump.rs::pump`).
  * (b) A failed hand-off is classified (`pump::classify_send_failure`):
    * a full queue is always a loss;
    * *Disconnected* is a loss unless this sensor instance's orderly stop has begun. In that case it is counted separately (`raw_discarded_shutdown`), logged in "sensors stopped" and kept out of `events_lost`.
  * (c) The kernel loss of stopped sessions is carried over (`etw_events_lost_carry`), so the reported counter stays monotonic for the agent's lifetime.
  * (d) The agent restarts sensors only when what they collect changes (`sensors_need_restart`). It compares DNS, script content, Sysmon and sensor groups with the config the sensors run with. This also fixes the old check missing a DNS change caused by `exfil_domains`.
  * No server change and no startup grace period. Any real drop at any time (queue full, kernel `EventsLost`) is still reported, and the server's derivation is unchanged.
* *Lab check for the owner:*
  * After a fresh install: no `TP-SRV-EVENTS-LOST`, and the device shows "online".
  * The agent log shows "sensors stopped ... discarded_at_stop=N" only if a restart happened.
  * `logman query Kestrel-Core -ets` / `Kestrel-IO` / `Kestrel-File` show Events Lost 0 after start.
  * If kernel Events Lost is non-zero there, that is a genuine burst and needs buffer sizing. That sizing was not done blind.

### 2026-10-21 - local "turn protection off" switch in the tray (owner request)

* The owner asked for an on/off switch in the employee tray app, unlocked with the device's uninstall token. A policy in Audit already gives detection-only for a whole group from the console; the local switch is for a person at one PC without the console, such as an on-site technician or a PC that cannot reach the server.
* **Turning off needs the uninstall token; turning back on never does.** Wrong tokens are rate-limited (5 failures, then an increasing lockout).
* **What "off" means is set by policy** (`local_pause`): `detection_only` (default; the agent keeps sensing and reporting, takes no automatic response and stops enforcing hardening) and optionally `full` (sensors stopped, only heartbeats). `full` is off by default because a stolen token would otherwise make the PC invisible.
* **Duration is set by policy:** timed (15 min, 1 h, 4 h, 8 h, capped by `max_minutes`) with automatic turn-on; "until turned back on" only when the policy allows it.
* IT sees the state on the device (status, who, mode, until), can turn protection back on remotely, and every off and on is an alert (`TP-06`) and an audit entry. The state persists across reboots and agent restarts.

**Addendum (same day) - local turn-off switch as built.**

* Contract in `kestrel_common::pause` (`PauseMode`, `PauseState`, `LocalPause`, `PauseOffer`, `PauseResult`, `PauseReport`, `TokenInput` with a redacted `Debug`). All additive with `serde(default)`; documented in `docs/contracts.md` "Local turn-off (tray switch)".
* **`ProtectionState` was not given a `paused` variant.** An older tray would fail to parse an unknown state. The tray derives "Protection is off" from the new `TrayStatus.pause` field instead, and `TrayStatus.local_pause = null` (older agent) hides the switch.
* **Device status `paused`** ranks below `isolated` and `offline` and above `degraded`, because a full turn-off stops the sensors on purpose and would otherwise show as degraded. A pause whose `until_ms` has passed is not shown as paused (SQL `device_status`, migration 0008).
* **Two gates for detection only:** `Engine::set_paused` forces Audit, marks `Alert::protection_off` and lets only `ResumeProcess` out (open suspend windows are resumed at once). The agent also refuses every `ActionOrigin::Engine` action except `ResumeProcess`. PS-15 (persistence rollback) does not fire while paused, because it only follows a Protect kill.
* **Order of checks** for a turn-off request: identity, already off, lockout, policy, token. A request refused by policy never counts as a wrong token. The policy is public in the tray status anyway.
* **Wrong tokens are reported to the server** (`AgentPayload::Pause{denied}` plus a TP-06 alert) at most once a minute, plus always when a lockout starts. This keeps a local process that spams wrong tokens from flooding the server.
* **The 24 h reset:** after 24 h without a wrong token, the lockout escalation starts over.
* **`ResumeProtection` privilege:** `response.collect`, the lowest response privilege. Turning protection back on only restores the safe state.
* **TP-06 alerts are built by the agent** (`kestrel_detect::catalog::protection_alert`), not by an event. This keeps them working in full mode with the sensors stopped, and the policy and exclusions cannot silence them. The subject is the agent process, with the tray user as `user`. The usernames in summaries and reports are pseudonymised with the policy's username hashing.
* **`max_minutes` above 480** only raises the cap the agent accepts. The tray offers 15 min, 1 h, 4 h and 8 h (plus `max_minutes` itself when it is below 8 h). The server accepts values from 1 to 10080.
* **Hardening after turn-on** is re-applied in the background (housekeeping), so the tray's request does not wait for AppLocker or PowerShell.

### 2026-10-22 - ST-04 killed Docker Desktop on the owner's PC (kubeconfig read, then the backend contacted Docker)

**Evidence (real install, default policy, ST-04 Protect).**
* ST-01 (Audit): `C:\Program Files\Docker\Docker\resources\com.docker.build.exe --log-no-timestamp` (valid signature, signer "Docker Inc", path class program_files, parent `com.docker.backend.exe` <- `com.docker.backend.exe` <- `Docker Desktop.exe`) opened `C:\Users\azka\.kube\config`.
* ST-04 (Protect, Critical), 5.6 s later: the reader's **parent** `com.docker.backend.exe` (pid 57284, Docker-signed, Program Files) connected to `desktop.docker.com` (3.165.102.21:443, about 1 MB sent). ST-04 killed `com.docker.build.exe`, killed the parent with its whole tree (wslhost.exe, wsl.exe, several Docker Desktop.exe) and blocked 3.165.102.21 (CloudFront) host-wide for 24 h. Docker Desktop could not restart until `wsl --shutdown` (its WSL data disk stayed attached).

**Root cause.**
1. Store ownership is keyed on the reader's file name (`paths::O_KUBE`). `com.docker.build.exe` is in the Docker list but not the kubeconfig list, so its read was a normal ST-01 and recorded as a credential read with no benign class. ST-04's Audit downgrade only knew WAM-cache reads and the Electron safeStorage key.
2. ST-04's "relatives" logic treats the connecting process's child as the reader and then kills **both** trees: the reader and the sender, whoever the sender is. A vendor's own signed backend doing its normal update / telemetry call was treated like a stealer's loader.
3. The destination block was host-wide (`image: None`) for any sender, so a shared CDN address was cut for every program on the host.

**Decisions (narrow, per rule; the withdrawn global safety net stays withdrawn).**
* **Developer-tool credential stores** (`legit_apps::DEV_TOOL_STORES`: store labels AWS (credentials, SSO / CLI cache), Azure CLI token cache, Google Cloud SDK credentials, Kubernetes kubeconfig, Docker `config.json`). The catalog has no `.aws\config` store (only `credentials` and the SSO / CLI cache), so nothing was added for it. Not included: the WAM cache (own rule), MSAL `.IdentityService`, Git / GitHub CLI / ngrok / Terraform tokens, and every browser, wallet, messenger, password-manager or Windows credential store. A read of one of these by `legit_apps::dev_tool_reader` (valid signature with a named signer; image under Program Files / Program Files (x86) / WindowsApps on the system volume; not an interpreter, script host, .NET / script REPL or LOLBin (`legit_apps::is_interpreter`: the engine's LOLBin list, python* incl. versioned names, pythonw, py, node, deno, bun, java, javaw, ruby, perl, php, pwsh, powershell, cmd, wscript, cscript, mshta, rundll32, regsvr32, dotnet, csi, fsi and others); no script / eval / inspector / remote-control argument; Electron hosts (now also Docker Desktop, Lens, Rancher Desktop, Cursor, Windsurf, Postman, GitHub Desktop) only for a plain launch without a positional argument; not in the engine's `tampered` set) is a **Low Audit ST-01, recorded** (`ProcState.dev_tool_cred`). ST-04 after only such reads (plus WAM / own-safeStorage reads) is **Audit**: no kill, no block. Any other credential read or DPAPI unprotect by the same process makes ST-04 a full Protect response again (tested).
* **`tampered` now covers every Program Files image** (`Engine::on_target`), not only browsers and the importer table, so an injected developer tool or vendor backend never gets either exemption.
* **ST-04 "parent sent" scope** (`legit_apps::vendor_backend`). When the connection came from the reader's parent and that parent meets the same constraints as a developer-tool reader (valid signature, Program Files on the system volume, not an interpreter / LOLBin, no script / eval / inspector / remote-control argument, not tampered) **and** its signer is exactly the reader's valid signer, the parent and its tree are not killed or quarantined, and the destination is not blocked. The reader is still killed if its own reads were not exempt. An unsigned, user-writable, script-host or differently signed parent is still killed with its tree, as before.
* **Destination block scope.** ST-04's `BlockDestination` (and the port-specific block added when ST-04 escalates a suspend window) is now scoped to the sender's image when the sender is validly signed and installed under Program Files on the system volume; it stays host-wide for unsigned or user-writable senders and System32 LOLBins. *Why:* the sender is killed anyway; a host-wide 24 h block of a CloudFront / Akamai address cuts unrelated software and vendor update endpoints after a single correlated hit. A destination contacted only by an exempt sender is never blocked: Audit hits carry no actions, and the vendor-backend case drops the block. *Trade-off:* a second, different binary of the same stealer reaching that address is not stopped by the per-image filter; it is caught by ST-04 / ST-14 on its own reads and sends.
* **Interpreters are no longer owners of the cloud CLI stores by file name.** `paths::O_AWS` dropped python, pythonw, node, java, javaw; `O_AZURE` dropped python, pythonw; `O_GCLOUD` dropped python, pythonw, java, node. *Why:* the owner list is matched on the file name only, so a stealer script under any validly signed `python.exe` read these stores silently and was never correlated by ST-04. The first version of this fix left boto3 / CDK scripts killed by ST-04 in Protect on every developer machine; the coordinator rejected that trade-off (same day), hence the next two items.
* **Official CLI layouts stay owners** (`legit_apps::bundled_cli_python`): the Azure CLI's bundled interpreter `<Program Files[ (x86)]>\Microsoft SDKs\Azure\CLI2\python.exe` started as `az.cmd` does (`-IBm azure.cli`, or any flag group of b/e/i/s/u/o/q/d ending in `m`, then exactly `azure.cli`) for the Azure CLI store, and the Google Cloud CLI's `<Program Files[ (x86)]>\Google\Cloud SDK\google-cloud-sdk\platform\bundledpython\python.exe` whose first non-flag argument is that SDK's `lib\gcloud.py` on the system drive, for the gcloud store. Valid signature, system volume, not tampered. `-c`, another module or script, another store, a per-user copy (`%LOCALAPPDATA%\Google\Cloud SDK` is user-writable) are not owners. The command lines follow the launchers' published scripts and were **not** checked on a live install (no Azure CLI / gcloud on this host); a mismatch falls back to the destination-aware ST-04 below (High Audit towards the provider), never to a kill of a genuine `az` / `gcloud` call to its own endpoints. Lab check for the owner: run `az account show` and `gcloud auth list` with an agent in Audit and confirm no ST-01.
* **ST-04 is destination-aware for one provider's own stores** (`legit_apps::cloud_provider`, `PROVIDER_ENDPOINTS`, `provider_endpoint`, `provider_allowance_ok`; `Engine::provider_destination`). The engine records per process the one provider whose developer-tool stores were read (`ProcState.cloud_provider`; AWS, Azure CLI -> Azure, Google Cloud SDK -> Google Cloud, Docker) and whether anything else was read (`non_provider_cred`: any other store, a second provider, kubeconfig, WAM, any DPAPI unprotect). When only one provider's stores were read and the connection's correlated DNS name (`dst_host`, or the name the engine saw resolve to that IP for the connecting process; never an IP alone) is a label-boundary, case-insensitive suffix match of that provider's endpoints, and reader and sender are both validly signed, outside Temp / Downloads / external media and not tampered, ST-04 is **High, Audit, no actions** with the summary "... read AWS credentials, then connected to AWS (s3.ap-southeast-1.amazonaws.com) 5.6 s later; this is normal for SDK / CLI use but would also fit an attacker using the credentials; review". It uses its own dedup key (`ST-04#provider`) so a later send of the same process elsewhere raises the full ST-04 alert (tested). Endpoints: AWS `amazonaws.com`, `aws.amazon.com`, `amazonaws.com.cn`; Azure `azure.com`, `azure.net`, `core.windows.net`, `login.windows.net`, `login.microsoftonline.com`, `graph.microsoft.com`, `azurecr.io` (not `windows.net` or `microsoft.com` as a whole); Google `googleapis.com`, `accounts.google.com`, `gcr.io`, `pkg.dev` (not `google.com` as a whole); Docker `docker.io`, `docker.com`. Kubeconfig has no provider (its API server is whatever the file names); a kubeconfig read keeps the generic behaviour unless the reader is a `dev_tool_reader`. *Residual risk, accepted:* an attacker exfiltrating to their own bucket at the same provider (an S3 bucket, an Azure blob account) or using the stolen keys against the provider's API from the victim's host with a signed interpreter gets a High Audit alert, not a kill. Unsigned readers (a PyInstaller stealer, a dropped portable python without a valid signature) never get the allowance.
* **Not changed:** `code.exe` (VS Code, an Electron host) remains a name-based owner of most cloud stores, as before; the browser owner rules, the WAM rule and the Electron safeStorage rule are unchanged.
* **Tests:** `crates/kestrel-detect/tests/fp_devtools.rs` with the lab event verbatim as fixture `tests/fixtures/lab_docker_desktop_kubeconfig.jsonl` (Audit and Protect: ST-01 Low Audit, ST-04 Audit, no actions, no standalone actions), other signed Program Files dev tools (Low / Audit), and positives: unsigned `C:\Users\x\AppData\Local\Temp\k.exe` reading `.kube\config` then connecting (kill + host-wide block), signed `python.exe` / `pythonw.exe` / `python3.13.exe` in Program Files reading `.aws\credentials` then posting to an address with no resolved name (full response, per-image block), per-user install / interpreters / LOLBin / Electron with a script or positional argument / inspector / eval / invalid or missing signature / other drive / browser store (full ST-04), an injected dev tool (full), a dev tool that also reads a browser store (full), same-vendor backend parent (reader killed only, no block), and an unsigned / user-writable / script-host / differently signed / invalidly signed parent (parent killed with its tree). Destination-aware ST-04: boto3-style python to S3 / STS / SSO / `aws.amazon.com` / `.amazonaws.com.cn` (also via a DNS answer, any case, trailing dot) is High Audit with no kill or block, and a later send to Telegram is the full ST-04; python to Telegram, Discord, pastebin, a raw IP with or without a name, `amazonaws.com.evil.net`, `evilamazonaws.com` or another provider is the full response; unsigned / Temp / Downloads / invalid-signature readers to `s3.amazonaws.com` are killed; AWS + browser store, AWS + Azure and kubeconfig keep the full response, two AWS stores do not; python on Azure CLI / gcloud / Docker stores to the provider is High Audit, to Telegram full; the Azure CLI (both Program Files folders) and gcloud bundled python layouts are silent owners, while `evil.py`, `-c`, `-cm`, `-m azure.cli.evil`, another store, unsigned, a per-user copy, a foreign `gcloud.py` and another drive are not. Unit tests in `legit_apps.rs`.


## 2026-10-22 GUI uninstaller (`kestrel-uninstall.exe`)

* **Removal through `MsiConfigureProductExW`, not `msiexec.exe /x ... UNINSTALL_TOKEN=`.** The task asked for `CreateProcessW` of msiexec; the tool instead asks Windows Installer for the removal in-process (`MsiSetInternalUI(INSTALLUILEVEL_NONE)`, `MsiEnableLogW` verbose log in `%TEMP%\kestrel-uninstall-<yyyyMMdd-HHmmss>\kestrel-uninstall-<yyyyMMdd-HHmmss>.log`, property string `UNINSTALL_TOKEN="..." REBOOT=ReallySuppress`). *Why:* same engine, same return codes (0 / 3010 / 1603), same UILevel 2, but the token is never on a process command line, so process-creation telemetry (Sysmon 1, Security 4688, any EDR) never writes it to a log (M6). The property string and token buffers are wiped after use (best effort).
* **Running image moved aside.** The tool runs from `C:\Program Files\Kestrel`; a running exe cannot be deleted, so Windows Installer would leave it for a restart and every GUI removal would report 3010. The tool renames itself into its private work folder (allowed for a running image on the same volume) just before the removal, deletes that copy at the next restart on success, and moves it back on any failure (also from `Drop`, so a worker panic cannot lose it). If the move fails, Windows Installer's own in-use handling applies (3010, "restart to finish").
* **Preview mode and elevation.** The manifest is `requireAdministrator`, which Windows applies before the program runs, so `--preview` cannot skip the prompt by itself. Screenshots run it with `__COMPAT_LAYER=RunAsInvoker` (documented in `/?`). Preview walks through the screens with a simulated success and changes nothing; it exits 0.
* **Settings > Apps.** ARP / Settings remove an MSI product with UILevel 3 (basic UI, execute sequence only); a typed `msiexec /x` uses 5. The new launch condition blocks `REMOVE="ALL" AND UILevel > 2 AND NOT UNINSTALL_TOKEN AND NOT UPGRADINGPRODUCTCODE` with a pointer to the Start menu tool. UX only: `KestrelUninstall` still verifies the token and the upgrade claim (V-M2). Residual: an interactive removal of a broken install (agent already gone) without a token is now refused; `msiexec /x {PC} /qn` still works for that case.
* **Resources without a build dependency.** `build.rs` writes a `.res` (manifest, version resource, the tray icon) and passes it to the MSVC linker for bin targets only (test executables must not require elevation); no `rc.exe`, no `embed-resource`.
* **Security review of the tool (same day, fresh reviewer, hostile).** Fixed:
  * **H1 (pre-existing, `kestrel-msica`): `|` in `UNINSTALL_TOKEN` bypassed V-M2.** `parse_uninstall` split the custom-action data from the left, so `UNINSTALL_TOKEN="x|{PC}|{UC}|0|{B}"` shifted attacker text into the upgrade fields and another product's UpgradeCode "verified" an upgrade, skipping the token check (also via plain `msiexec /x`). Now the four installer-supplied trailing fields are split off from the right (the token is everything in between), `upgrade_verified` requires Kestrel's own UpgradeCode (`KESTREL_UPGRADE_CODE`) and the CA queries related products under that constant, not the data field. The GUI also rejects `|` and `"` in tokens. Regression tests in `kestrel-msica`.
  * **M1 / M3: user-writable `%TEMP%`.** With UAC elevation the elevated tool shares the user's `%TEMP%`; a predictable log name allowed link planting against an elevated writer, and the executable moved there could be swapped and then "restored" into Program Files. Both now live in a fresh work folder created atomically by one `NtCreateFile` (`FILE_CREATE`, owner Administrators, protected DACL SYSTEM + Administrators) whose handle is held without `FILE_SHARE_DELETE` until the tool exits, so it cannot be renamed or replaced.
  * **M2: elevated Notepad.** "Open log" started Notepad elevated; with over-the-shoulder elevation its File > Open dialog is an elevated shell for the standard user at the keyboard. The log is now shown read-only inside the tool (**Show log**); the tool starts no interactive child process.
  * **Low:** the product must also be registered under Kestrel's UpgradeCode (`MsiEnumRelatedProductsW`), not only carry the display name; a worker panic is caught and reported as a failure; the result travels over a channel (the window message carries no pointer); the property string is built as UTF-16 in one allocation; the token field is cleared on every final screen.
  * **Not changed:** the token can stay on the clipboard (the tool does not touch the clipboard); clearing read-only on a hard-linked file in the purge fallback changes the shared attributes (only in the admin-only state folder, only when POSIX delete is unavailable). Still to verify in the lab VM: grep a real removal log for the token (the property is hidden; the `MsiConfigureProductEx` path was not run on this host).
