### Real-Windows sensor findings (host, read-only `sensors-test --detect` + raw `logman`/`tracerpt` captures, build 26200)

* **Registry (known risk 2) — confirmed broken.** Microsoft-Windows-Kernel-Registry `SetValueKey` (event 5) arrives with `KeyName` **empty**; only `KeyObject` (a kernel pointer) identifies the key. `OpenKey`/`CreateKey` (2/1) carry `BaseObject` + `RelativeName`, but run at ~14 000 events/s on a busy workstation — too costly to decode just to build a name cache. **Decision:** keep event 5 for attribution (pid, value name, KeyObject; ~13/s) and add a user-mode watcher (`RegNotifyChangeKeyValue`) on the curated key set (HKLM + every loaded `HKU\<SID>` and `HKU\<SID>_Classes`) that diffs values and emits the full key/value/data; join the two on value name within a short window, then remember KeyObject→key for later writes. Unattributed changes are still emitted (pid 0 = unknown writer). *Alt:* OpenKey cache (CPU), NT Kernel Logger KCB rundown (all registry ops, far higher volume).
* **DPAPI 16385 (known risk 4) — flows without the Debug channel.** Field names match the decoder. The DPAPI hardening control stays (harmless) but is no longer required for ST-03.
* **Network byte order (known risk 3) — correct.** `Test-NetConnection example.com:443` produced a `net_connect` to the resolved IP and port 443; no swapped ports.
* **Short-lived command lines (known risk 6) — OK.** `cmd /c echo …` start carried its full command line.
* **DNS:** queries that end NXDOMAIN / no-records (`QueryStatus` 9003 / 9501) were dropped by the decoder. They are useful (DGA, dead resolvers), so they are now emitted with empty answers.
* **Audit-API OpenProcess volume (known risk 1) — ~500 events/s**, 98 % with desired access `0x1200` (query-limited + set-quota) from one service. Filtered at the source to masks that can read/write/inject/duplicate/terminate.

### Phase 3-4 design decisions

* **Rule families behind one seam.** RW/CD/PS rules live in `kestrel-detect/src/families/*` behind a `Family` trait (events, ticks, alerts in; `FamilyHit`s out) and go through the engine's single emission path (mode, exclusions, de-dup, protected-process filters). *Why:* three parallel implementers without touching the 3.4k-line `engine.rs`, and no second action path that could bypass safety filters. `FamilyHit.audit_only` marks variants that must never act even when their rule is in Protect.
* **SigmaHQ pack is Audit-only and seeded server-side** as ordinary Sigma rules with author, upstream URL (pinned commit) and `DRL-1.1`, so attribution shows wherever a Sigma alert shows and admins keep control of each rule.
* **M6 (enrollment token on the command line):** fixed with an MSI→registry hand-off (protected DACL via `MsiLockPermissionsEx` SDDL; the agent verifies the DACL, takes and deletes the value). *Alt:* a C++ custom-action DLL reading `CustomActionData` and piping the token on stdin — more code to sign and maintain. *Residual:* the **uninstall** token still reaches `kestrel-agent uninstall --token` through `WixQuietExec`; it is single-use for a device that is being removed and is admin-only; documented in HANDOFF.
* **Policy version after a DB restore:** the server catches up (re-versions past what the agent reports, bounded to +1,000,000 per report) rather than adding an epoch to the agent protocol. *Why:* server-only change, works with every agent already deployed. *Alt:* `(epoch, version)` tuples — needs agent + server changes and still breaks when the restored DB carries the old epoch.
* **YARA-X moved into `kestrel-scan.exe`.** The agent no longer links YARA-X/wasmtime; `Scan` runs the scanner next to the agent with a target list in the SYSTEM-only state directory and a 15-minute timeout. *Why:* the agent binary is always resident; scanning is rare.
* **Elevation on the host is interactive.** After the owner declined a UAC prompt, no further elevated runs on the host; all elevated validation happens in the QEMU VM over SSH as `labadmin`.
* **Sigma: an unknown field never matches.** rsigma treats a missing field as `null`, so upstream filters such as `filter_main_null: ParentImage: null` would silently *suppress* detections whenever Kestrel lacked the parent (process started before the agent). Kestrel now presents uncollected fields as "present but unknown", matching no value. Missing data can neither satisfy a selection nor suppress an alert; the cost is an occasional extra Audit alert.
* **Sigma `process_access` only receives successful opens** (Kestrel's new failed-open telemetry for lsass would otherwise satisfy rules written for granted handles); `GrantedAccess` is the *requested* mask, noted on those rules.
* **Sigma pack contents:** the 70 "ready now" SigmaHQ rules (pinned commit `e3f4662`), all Audit; Tier-B/C rules deferred. Upstream rule `a7ee1722` has a typo (`-DisableRuntimeMonitoring`) and does not catch `-DisableRealtimeMonitoring`; two other pack rules do.
* **Known risk 5 (`HistoricalContext` = LoggerId) — holds on build 26200.** The provider-disabled watchdog runs at start and every 30 s; during the 45 s host probe it ran at least twice against Kestrel-Core/IO and emitted no `EtwProviderDisabled` tamper event and restarted no session. A wrong logger id would have flagged every watched kernel provider. (TP-01 itself is exercised in the VM.)

### 2026-10-21 — security review v1.1 fixes: WFP identity, frozen isolation inputs, remote paths

* **V-H10: agent-scoped WFP permits match the process identity, not only its path.** Every permit with an `FWPM_CONDITION_ALE_APP_ID` (isolation server + DNS permits, always-on server hard permits) also carries `FWPM_CONDITION_ALE_USER_ID` with a security descriptor granting `FWP_ACTRL_MATCH_FILTER` (0x1, SDDL `CC`) to one SID only: the service SID `NT SERVICE\KestrelAgent` when the agent's token holds it (the service has been installed with `SERVICE_SID_TYPE_UNRESTRICTED`; checked at run time with `CheckTokenMembership`), else the token's user SID (LocalSystem for an install whose service has no SID type; the interactive user for a console run). *Why the service SID:* a user-started copy of `kestrel-agent.exe` has neither, and even a process an admin starts as SYSTEM lacks the service SID. **Fail closed:** without an identity no agent permit is planned; `IsolateHost` is refused with an explicit error (isolating anyway would cut the agent off until the auto-release deadline), and the always-on hard permits are removed rather than left app-only. The Windows glue also refuses to add any app-scoped permit without the user-id condition (invariant `app_permits_have_user_sd`). Hard permits whose stored plan differs (e.g. installed by an older version without the condition) are replaced.
* **V-M7: isolation inputs are frozen at isolation time.** The resolver set is recorded when isolation starts (`WfpState.isolation_dns`; for older state files, the resolvers the existing plan already permits) and re-plans never permit a resolver that appeared later. Server IPs are **never re-resolved while isolated** (the 60 s re-plan and the hard-permit refresh both use the frozen isolation server set). *Alt considered:* add a re-resolved IP only after a successful mTLS handshake to it — rejected for now: it needs a probe connection outside the transport and a WFP permit before the probe can run. *Trade-off:* if the server's address changes while a host is isolated, the agent loses contact until the isolation auto-release deadline or the local break-glass (`kestrel-agent release-isolation`).
* **V-M1: network paths are never opened as SYSTEM.** `kestrel_scan::is_remote_path` (UNC, `\\host@port\` / `\\host@SSL\` WebDAV, `\\?\UNC\`, `\\.\UNC\`, `\??\UNC\`, `\Device\Mup\`, redirector devices, any non-drive `\\?\` / `\\.\` path) plus `GetDriveTypeW == DRIVE_REMOTE` for drive letters. Applied to "scan running processes" target selection, explicit scan paths, the kestrel-scan target list (defence in depth), and enrichment (metadata, SHA-256, Authenticode/catalog, Zone.Identifier): facts for such images stay *unknown*. Directory expansion for scans no longer follows junctions/symlinks.
* **V-L10 / V-L11:** YARA `include` is disabled and compile errors are reported as file name + the diagnostic's first line only (the rest quotes rule source). Each scan writes its target list to a fresh `create_new` file with a random name in the state directory and deletes it afterwards.

### 2026-10-21 — security review v1.1 fixes: agent updates and the MSI (V-H3, V-L9, V-M3, V-M2)

* **V-H3: one update at a time, verified from disk, pinned until msiexec exits.** The update slot is a process-wide atomic claimed in the transport *before* the task is spawned; a delivery while one runs is dropped with a log line. The download goes to `<state>\updates\dl-<random>.part` (`create_new`, share mode 0), is renamed to `pkg-<random>.msi`, re-opened read-only with `FILE_SHARE_READ` only and hashed through that handle; the handle is held until msiexec exits (the hash from the network stream must agree too). *Why hold until exit:* the install runs while we wait; when the upgrade stops the service, the process dies and the handle closes with it, which is fine because msiexec has long opened (and cached) the package by then.
* **Authenticode on update MSIs is optional and off by default.** Build-time `KESTREL_UPDATE_REQUIRE_SIGNED=<signer subject substring>` makes the agent require a valid Authenticode signature from that signer; the owner has no code-signing certificate yet, so the Ed25519 manifest signature + SHA-256 remain the trust anchor. Until `kestrel-win` exports an Authenticode helper to the agent, a build with the variable set **fails closed** (no update installs). Recommended once a certificate exists.
* **V-L9:** download deadline 30 min overall, 60 s per read (and for the response headers / TLS handshake 20 s), and at least 64 KiB per 60 s window after the first byte.
* **V-M3: updates must be able to succeed and their outcome is reported.** msiexec `/i <pkg> /qn /norestart /l*v <pkg>.log` is waited for (max 60 min). Exit 0 / 3010 / 1641 = success (3010/1641 reported with a reboot note), anything else = failure with the code. `KV_LAST_UPDATE` is written only on success. The version is recorded as *pending* before msiexec starts: the MSI upgrade stops the service, so the **new** agent reports `UpdateResult ok=true` at start-up when the pending version is the one running, and a failure ("installer did not complete") when it is not. A failed version is retried at most every 6 h (`update_attempt` = `version|ms`).
* **MSI upgrade design:** `<MajorUpgrade Schedule="afterInstallExecute">` (install the new version over the old one, remove the old product last, so the enrolled identity, service registration and state survive), launch condition accepts `WIX_UPGRADE_DETECTED`, `CA_Install` (enrolment) runs only when `NOT Installed AND NOT WIX_UPGRADE_DETECTED`, and a `ServiceControl` (stop + start on install) in a component conditioned on `WIX_UPGRADE_DETECTED` restarts the agent around the file replacement (never on fresh install or uninstall, so an uninstall cannot stop the agent before the token check). `kestrel-agent install` also keeps an existing identity for the same server + CA instead of enrolling again. The Rust binaries have no version resource, so `DefaultVersion` makes the packaged copy replace the on-disk file (WIX1103 warnings are expected). The first upgrade from an already deployed 0.1.0 package uses the old package's uninstall condition (`NOT UPGRADINGPRODUCTCODE`), which still works.
* **V-M2: the uninstall token can no longer be skipped with `UPGRADINGPRODUCTCODE`.** `CA_Uninstall` runs on every `REMOVE="ALL"`; the custom action receives `UPGRADINGPRODUCTCODE`, the UpgradeCode, version and ProductCode and waives the token only when the claimed product is registered under Kestrel's UpgradeCode (`MsiEnumRelatedProducts`), installed (`MsiQueryProductState` = default), not this product, and newer. This relies on the new product being registered when the old one is removed (afterInstallExecute) — to be confirmed in the lab VM. Partial removal (`REMOVE=<features>`) is refused by an error custom action and the feature is `AllowAbsent="no"`. *Not done:* a TP alert for `msiexec /x` of the product code (engine side).
* **V-H1 (CLI):** `update-keygen` runs icacls from `GetSystemWindowsDirectoryW` (via `platform_win::windows_dir`), msiexec likewise; no executable path in the agent is derived from `%SystemRoot%` any more.
### 2026-10-21 — fix round 2, release candidate

* **Registry writer attribution: a sole candidate is Exact.** After round 1, every first write was Heuristic, so the PS rules could no longer act on malware's own first write (re-review NEW-1). Now one distinct writer pid in the join window is Exact. Two or more candidates are Heuristic, which still defeats framing a legitimate process, because the attacker's own write is always a candidate. Every change waits for its full join window, so a late rival write is still counted.
* **Re-planted autoruns are removed again.** `RemoveAutorun` bypasses the 10-minute de-duplication, gated to once per 30 s per object; a re-plant inside the gate is held, not dropped. The re-alert is limited to once per 10 minutes.
* **The agent's identity is image path + its own pid** (`HostContext.agent_pid`). A user who starts the real `kestrel-agent.exe` gets an ordinary process.
* **Engine-proposed quarantine never touches a validly signed file.** In shared folders (`ProgramData`, `Users\Public`, other profiles) it quarantines only files that are known unsigned or invalid; `Unknown` is refused there.
* **Canary reader exemptions require SYSTEM.** User-context backup tools (FileHistory, sdclt, an admin's scanstate) now trip ST-16. This is accepted: a stealer runs as the user.
* **Dead letters store metadata only** (length + SHA-256, redacted DB error), with 30-day retention and the newest 1,000 rows per device.
* **Version 1.1.0, tag `v1.1.0-rc1`.** An RC rather than final because the binaries are unsigned (Defender flags them) and the update signing key is not provisioned. Both are owner tasks.
* **Network blocks need an analyst "lift" action.** The lab showed that ST-02/ST-07/ST-16 image blocks are permanent (`ttl_secs: None`), and nothing in the console could lift them; a false positive on a business app would need a reinstall. Added `UnblockNetwork` (by image, block id, or all non-isolation blocks); restoring a quarantined file also lifts that image's blocks. Automatic blocks stay permanent by default, because a confirmed stealer should stay cut off until an analyst decides.
* **Lab VM hostname is `W-`.** The unattend `ComputerName` was not applied; the agent reports Windows' real name correctly. Cosmetic, lab only.

### 2026-10-21 — remote desktop and remote file manager (owner request)

* **The owner asked for VNC-style remote control and a full remote file manager in the admin console.** This reverses the "no screenshot/keystroke capture" privacy rule for **interactive, admin-initiated sessions only**; CLAUDE.md is updated accordingly.
* **Owner's choices:**
  * Screen sessions start **without employee consent**; the employee always sees a notification and an on-screen banner for the whole session.
  * The file manager has **full SYSTEM access** (browse, download, upload, rename, delete, mkdir) with no extra confirmation step.
  * Both are on by default in policy, and each has a policy switch.
* **Kept regardless:**
  * only the admin role can use them;
  * every session and file operation is in the hash-chained audit log;
  * frames and file contents never enter telemetry or ClickHouse;
  * the agent refuses when the policy switch is off.
* **Risk accepted by the owner:** a compromised admin account or server can now view and control every enrolled PC and read or modify any file on it. Recommend MFA for all admins and a restricted network path to the console.

* **Remote access is chosen per installer and locked on the device (owner request, refined).**
  * The admin web generates an installer per remote-access profile:
    * **None**;
    * **Unrestricted** (remote control + full file manager);
    * **Guarded** (remote control + file manager, with customisable guardrails: consent, reason, MFA re-auth, upload/delete, session and idle limits, allowed hours, blocked paths).
  * The profile is bound to the enrollment token and pinned on the agent at enrollment as a **ceiling** that later server messages cannot raise. The effective setting is the intersection of that ceiling and the policy, and the agent enforces it.
  * So "no remote access" devices stay closed even if the server or an admin account is compromised. Changing a device's profile requires reinstalling with the uninstall token.
  * Existing policies and previously enrolled agents default to **None**.
  * The banner and notification on the employee's screen are mandatory in every profile, including Unrestricted: covert screen viewing creates legal exposure under PDPA and UU PDP.
  * Building one MSI per profile is impractical, because WiX doesn't run on the Linux server. The server instead generates a setup script that embeds the server address, the agent CA, the MSI hash and the profile-bound token.

Base64 + zstd is acceptable for 5â€“10 fps JPEG.
* **Compatibility by capability, not by version.** `Hello.capabilities` (`live.files`, `live.desktop`) tells the server what the agent supports; the server returns 409 "agent too old" otherwise. The live message enums carry `#[serde(other)] Unknown` so either side can add message kinds later. An old agent that somehow receives a `Live` payload logs it as undecodable (not acked); an old server drops an agent `Live` as malformed (seq 0, not acked).
* **Interactive console session required, API tokens refused.** `remote.desktop` / `remote.files` are only reachable through the admin role's `*`, and additionally require a cookie session (CSRF-protected). *Why:* a leaked automation token must not be able to read or change files on every PC. The WebSocket cannot carry a custom header, so it takes the CSRF token as a query parameter and checks `Origin` against `Host`.
* **Server-side policy check as well as the agent's.** The server refuses with 403 `disabled_by_policy` before contacting the agent (clear UI message, no round trip); the agent still enforces its own copy of the policy (an agent with a newer/older policy is authoritative for itself).
* **Network paths refused.** The file manager accepts only `X:\â€¦` paths and refuses network drives, consistent with V-M1 (the agent never opens network paths as SYSTEM).
* **Protected folders:** the agent install folder and `%ProgramData%\Kestrel` are refused for every operation, and their ancestors for rename / delete / overwrite, after canonicalisation (8.3 names, junctions, symlinks). Uploads never open an existing file for writing (temp file + rename), so a hard link cannot be used to overwrite a protected file. *Residual:* reading a file through a hard link that an admin created by other means into a protected folder is not detected.

### 2026-10-21 - ST-16 false positive in the lab (Edge import) and a response safety net

**Finding.** Windows 11 lab VM, ST-16 in Protect. The employee opened Microsoft Edge (`C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe`, validly signed "Microsoft Corporation", parent explorer.exe). Edge's built-in "import from Chrome" scanned other browsers' profiles at start-up and opened `...\Google\Chrome\User Data\Profile 68\Google Profile Picture.png` inside the decoy Chrome profile Kestrel had planted (Chrome was not installed; the decoy made it look installed). ST-16 fired three times, killed the whole Edge tree and blocked Edge's network for 24 h. The alert text ("no legitimate program reads it") was wrong: browsers, password managers, backup/sync/AV and indexers legitimately enumerate or read other browsers' profiles.

**Decisions.**
* **ST-16 fires on secret material only** (`kestrel_detect::is_decoy_secret`): `Local State` (encryption key), `Login Data`, any *file* inside the decoy wallet-extension folder, `.aws\credentials` (and `Cookies` / `Web Data` should they ever be planted). Directory opens/listings, the extension folder itself and incidental profile files (pictures, `Preferences`, `Secure Preferences`, icons, `First Run`) never fire. *Why:* a stealer must read the secret files to steal anything; an import/backup scan usually touches the incidental ones first. Write/delete of a secret decoy still fires as before.
* **Decoys moved to defunct Chromium forks** stealers enumerate but mainstream import wizards do not offer: `%LOCALAPPDATA%\Kometa\User Data` (Kometa is in Lumma's built-in browser list - Cyble, SOCRadar) and `%LOCALAPPDATA%\7Star\7Star\User Data` (Vidar - Trend Micro). Each gets `Local State` (fake DPAPI-shaped `os_crypt.encrypted_key`), a `Default` profile (stealers always try `Default`) with `Login Data` and the fake MetaMask LevelDB folder. Nothing is planted under Chrome/Edge/Brave/Firefox/Opera/Vivaldi any more. If a fork's folder exists and is not Kestrel's (the user really has it), nothing is planted below it. *Alt considered:* keep the Chrome location only when Chrome is installed - rejected: Edge's importer enumerates Chrome's `User Data` whenever it exists, so the collision remains. *Residual:* stealers that only target mainstream browsers no longer trip ST-16; ST-01/02/03/04 cover reads of the real stores.
* **Migration.** On every plant the Windows agent removes decoys recorded in `canaries.json` that are not in the current spec set (files only while they still hold exactly our content, folders only when empty, deepest first, handle-based, never through a link), then removes the empty `Google\Chrome\User Data`, `Google\Chrome`, `Google` folders the legacy layout created implicitly. A changed file or a non-empty folder is left alone and forgotten. The engine no longer arms the legacy path.
* **Importers are Audit only.** A browser or password manager from the known-app table (valid signature by the expected signer + image name + genuine install location; not remote-controlled) reading decoy secrets raises a Medium **Audit** ST-16 alert with no actions, worded as a possible import. A renamed copy, an unsigned/invalid binary, a binary signed by someone else, a copy in a non-standard or user-writable folder, or a headless/remote-debugging instance still gets the full ST-16 response. Another browser-named "owner" (a fork not in the table) is only treated as an owner outside user-writable folders.
* **Global response safety net (all rules).** New `kestrel_detect::legit_apps` table (one place): Edge, Chrome, Firefox, Brave, Opera, Vivaldi, Bitwarden, 1Password, KeePass, KeePassXC, Office (WINWORD, EXCEL, POWERPNT, OUTLOOK, ONENOTE, MSACCESS), Teams (new MSIX + classic), Zoom, Slack, Adobe Acrobat/Reader, VS Code, Notepad++, OneDrive, Dropbox, Google Drive. The engine drops automatic `KillProcess` (incl. tree), `SuspendProcess`, `QuarantineFile` of the image and `BlockImageNetwork` against such a process, never opens a suspend window for it (an open one is resumed instead of escalated), appends "Kestrel did not stop <app> because it is a validly signed <vendor> application; review the alert" and reports the alert as Audit when nothing destructive is left. The Windows tree kill (engine-origin only) skips such an app when it is a *descendant* - plus its same-image helper processes - and names it in the outcome; an analyst's kill from the console is unchanged. Signer subjects verified on real binaries on 2026-10-21 (`Get-AuthenticodeSignature`): Microsoft Corporation (Edge, Office, Teams MSIX, OneDrive, VS Code), Google LLC (Chrome), Mozilla Corporation, "Brave Software, Inc.", "Zoom Communications, Inc." (Zoom's current name; the older "Zoom Video Communications, Inc." is kept). Opera Norway AS, Vivaldi Technologies AS, Bitwarden Inc. / 8bit Solutions LLC, AgileBits Inc., Dominik Reichl, DroidMonkey Apps, LLC, Slack Technologies, Adobe Inc., Notepad++, Dropbox, Inc and Google Drive paths are marked `signer_verified: false` in the table - verify on a lab image before relying on them. *Left out on purpose:* 7-Zip (binaries are not Authenticode-signed, so it can never qualify), Webex (install layout varies by deployment), Dashlane (Windows desktop app discontinued), NordPass and LastPass (signer/location not verified) - admins can exclude them per rule.
* **Never exempt:** LOLBins, script hosts and system tools (`legit_apps::NEVER_EXEMPT` plus the engine's LOLBin list: powershell, pwsh, cmd, wscript, cscript, mshta, rundll32, regsvr32, reg, sc, vssadmin, wmic, bcdedit, wevtutil, certutil, msiexec, installutil, msbuild, ...), even if placed in a known app's folder. A known app whose command line puts it under remote control (`--remote-debugging-port/pipe`, `--headless`, `--marionette`) is the attacker's instrument (ST-05/ST-06) and is not exempt. ST-07 still kills the process that injects into / opens the browser, never the browser. The protected/critical OS process list is unchanged; the safety net is an additional layer.
* **Residual risk:** per-user installs (`%LOCALAPPDATA%\Programs\...`, `%APPDATA%\Zoom\bin`, classic Teams, Chrome per-user) are user-writable: malware can copy a genuine signed binary there and side-load a DLL into it; that process is then alerted on but not killed automatically. ST-15 covers the known side-loading DLL names; a hostile-review follow-up should consider requiring the app's DLL directory to contain only validly signed modules before sparing it. Behaviour change worth knowing: RW-06 mass-rename by genuine VS Code (or Word, OneDrive...) is now alert-only.
**Addendum (same day) - global safety net withdrawn after hostile review** (`review-fp-safety-net.md`, findings F1-F9).
* **Withdrawn:** the every-rule "known app" sparing in the engine (no kill / suspend / quarantine / image block against listed apps, Audit downgrade) and the descendant sparing in the Windows tree kill. *Why:* a signature + path key is not an identity. Electron hosts (VS Code, Slack, Teams, Bitwarden, 1Password) run arbitrary JS (`ELECTRON_RUN_AS_NODE`, writable `resources\app` in per-user installs) - F1; tree kills spared the browser a stealer had launched and injected, neutering ST-07 - F2; per-user install folders are user-writable and the signature is checked on the file, not the mapped image (sideload / file swap) - F3; Office macro stealers would only be audited - F4; `--load-extension` and `-`/`/` switch prefixes bypassed the remote-control check - F5/F6. **1. Ransomware decoys visible on the Desktop (RW-07 when an employee tidies up).**
* *Root cause:*
  * `kestrel-win/src/rcanary.rs` planted the decoys **without** any attribute. The code justified this with "most ransomware skips hidden/system files", a claim with no source.
  * Two of the decoys were on the Desktop, the folder employees look at all day.
* *Second, independent cause of a Critical RW-07 when a person moves a decoy:*
  * The 2 s decoy poller (`win/rcanary.rs`) treated a decoy that **disappeared** (moved, deleted, recycled) as an *in-place rewrite*.
  * It blamed the last process that had opened the file (the V-H9 heuristic), or reported a "remote SMB writer" when the System process had opened it.
  * Kernel-File had already reported the rename/delete with the real actor: Explorer, which RW-07 already treats as alert-only.
* *Research* (`docs/research/notes/ransomware-decoy-attributes.md`, sources cited there):
  * No family we found skips hidden *files* by default.
  * Conti and Babuk source have no attribute check; Babuk resets attributes to NORMAL. Most families filter by name, extension or folder.
  * LockBit 3.0 has an optional `skip_hidden_folders`. It applies to folders, and our decoys sit in normal folders.
  * LockBit 2.0 applies its name/extension checks only to files *without* SYSTEM. So SYSTEM adds risk and no detection benefit.
* **Decision: FILE_ATTRIBUTE_HIDDEN only, on every decoy.**
  * The research suggested keeping one visible decoy per folder. Not done: visible decoys are exactly the reported problem.
  * Residual risk: a LockBit 3.0 build that also skips hidden files. This is unverified; testing it needs a real encryptor, which this project never runs.
* *Locations:*
  * Desktop decoys dropped:
    * it is the folder users browse most;
    * users with "show hidden files" on would still see them;
    * its traversal advantage is small (a depth-first walk reaches it just before Documents, and modern encryptors spread files over many threads).
  * Kept: 3 decoys in the Documents root and 2 in the Pictures root. These user-data roots come early in a profile walk and are browsed far less than the Desktop.
  * The profile root itself was considered: earliest in traversal and rarely browsed. Rejected because it is outside the file aggregator's scope and full of profile noise (`ntuser.dat`).
* *Upgrade:*
  * The planter re-applies HIDDEN to a decoy that still holds exactly Kestrel's content (`DecoyFs::ensure_attributes`).
  * The hash check and `SetFileInformationByHandle` use the same verified handle, opened with read-only sharing. The decoy is never recreated and its mtime is unchanged.
  * A decoy the user changed is never touched.
  * The 1.1.2 Desktop decoys (`RETIRED_DECOYS`) are removed when still exactly ours. A user-changed one is forgotten and left in place.
  * Credential canaries (ST-16) were already hidden; they now also get the attribute re-applied (same code path).
* *Poller:*
  * A disappearance is no longer an "in-place" hit.
  * It waits up to `GONE_GRACE_MS` (4 s) for the Kernel-File rename/delete of that decoy (`FileAgg::kernel_hit_since`, look-back 10 s), and is dropped when the kernel reported it.
  * Only when no kernel event arrives is it reported as before, so deletes Kernel-File might miss stay covered.
  * Real in-place modifications (file still there, size or mtime changed) are reported immediately, as before.
* *Explorer:*
  * Explorer is already on the protected-process list (`kestrel_detect::protect`, `%SystemRoot%\explorer.exe`, Microsoft-signed).
  * The engine already treats it as alert-only (High, no actions) for RW-07 / RW-06, so no rule change was needed.

**2. "Degraded" right after install (`etw_events_lost: 3390`, buffers lost 0).**
* *Conclusion: (b)/(c), an internal counter artefact of a sensor restart, not kernel loss.*
* *Evidence* (from reading the code path; the agent cannot run on the dev host):
  1. On a fresh install there is no cached policy, so the agent starts its sensors with the default policy. When the server's first policy arrived, `install_policy` compared it with "no previous policy" and **always restarted the sensors**, seconds after start.
  2. `Sensors::stop` set one shared stop flag:
     * The translator, the sole receiver of the 65 536-slot raw channel, exited within 100 ms.
     * The watchdog only stops the ETW sessions and event-log subscriptions on its next 500 ms tick.
     * Every event delivered in that gap failed `try_send` with *Disconnected* and was counted in `raw_dropped`. `SensorStats.events_lost` adds that to the kernel `EventsLost`.
     * Kernel-File (opens system-wide) plus Audit-API easily produce thousands of events in half a second during post-install activity.
  3. Buffers lost 0 fits: nothing was lost in the kernel.
  4. The server raises `TP-SRV-EVENTS-LOST` on a rise of 500 or more between two heartbeats, and marks the device degraded for 1 h on any rise. The first heartbeat (t = 0, before the restart) carried 0; the next one carried 3390.
* *Also found:* a sensor restart reset the kernel `EventsLost` part of the counter to 0, so losses of the old sessions vanished.
* *Fix (root cause, no grace period):*
  * (a) `Sensors::stop` stops the producers first (joins the watchdog, pollers and watchers). Then it tells the translator to **drain** its queue and exit (`kestrel-win/src/pump.rs::pump`).
  * (b) A failed hand-off is classified (`pump::classify_send_failure`):
    * a full queue is always a loss;
    * *Disconnected* is a loss unless this sensor instance's orderly stop has begun. In that case it is counted separately (`raw_discarded_shutdown`), logged in "sensors stopped" and kept out of `events_lost`.
  * (c) The kernel loss of stopped sessions is carried over (`etw_events_lost_carry`), so the reported counter stays monotonic for the agent's lifetime.
  * (d) The agent restarts sensors only when what they collect changes (`sensors_need_restart`). It compares DNS, script content, Sysmon and sensor groups with the config the sensors run with. This also fixes the old check missing a DNS change caused by `exfil_domains`.
  * No server change and no startup grace period. Any real drop at any time (queue full, kernel `EventsLost`) is still reported, and the server's derivation is unchanged.
* *Lab check for the owner:*
  * After a fresh install: no `TP-SRV-EVENTS-LOST`, and the device shows "online".
  * The agent log shows "sensors stopped ... discarded_at_stop=N" only if a restart happened.
  * `logman query Kestrel-Core -ets` / `Kestrel-IO` / `Kestrel-File` show Events Lost 0 after start.
  * If kernel Events Lost is non-zero there, that is a genuine burst and needs buffer sizing. That sizing was not done blind.

### 2026-10-21 - local "turn protection off" switch in the tray (owner request)

* The owner asked for an on/off switch in the employee tray app, unlocked with the device's uninstall token. A policy in Audit already gives detection-only for a whole group from the console; the local switch is for a person at one PC without the console, such as an on-site technician or a PC that cannot reach the server.
* **Turning off needs the uninstall token; turning back on never does.** Wrong tokens are rate-limited (5 failures, then an increasing lockout).
* **What "off" means is set by policy** (`local_pause`): `detection_only` (default; the agent keeps sensing and reporting, takes no automatic response and stops enforcing hardening) and optionally `full` (sensors stopped, only heartbeats). `full` is off by default because a stolen token would otherwise make the PC invisible.
* **Duration is set by policy:** timed (15 min, 1 h, 4 h, 8 h, capped by `max_minutes`) with automatic turn-on; "until turned back on" only when the policy allows it.
* IT sees the state on the device (status, who, mode, until), can turn protection back on remotely, and every off and on is an alert (`TP-06`) and an audit entry. The state persists across reboots and agent restarts.

**Addendum (same day) - local turn-off switch as built.**

* Contract in `kestrel_common::pause` (`PauseMode`, `PauseState`, `LocalPause`, `PauseOffer`, `PauseResult`, `PauseReport`, `TokenInput` with a redacted `Debug`). All additive with `serde(default)`; documented in `docs/contracts.md` "Local turn-off (tray switch)".
* **`ProtectionState` was not given a `paused` variant.** An older tray would fail to parse an unknown state. The tray derives "Protection is off" from the new `TrayStatus.pause` field instead, and `TrayStatus.local_pause = null` (older agent) hides the switch.
* **Device status `paused`** ranks below `isolated` and `offline` and above `degraded`, because a full turn-off stops the sensors on purpose and would otherwise show as degraded. A pause whose `until_ms` has passed is not shown as paused (SQL `device_status`, migration 0008).
* **Two gates for detection only:** `Engine::set_paused` forces Audit, marks `Alert::protection_off` and lets only `ResumeProcess` out (open suspend windows are resumed at once). The agent also refuses every `ActionOrigin::Engine` action except `ResumeProcess`. PS-15 (persistence rollback) does not fire while paused, because it only follows a Protect kill.
* **Order of checks** for a turn-off request: identity, already off, lockout, policy, token. A request refused by policy never counts as a wrong token. The policy is public in the tray status anyway.
* **Wrong tokens are reported to the server** (`AgentPayload::Pause{denied}` plus a TP-06 alert) at most once a minute, plus always when a lockout starts. This keeps a local process that spams wrong tokens from flooding the server.
* **The 24 h reset:** after 24 h without a wrong token, the lockout escalation starts over.
* **`ResumeProtection` privilege:** `response.collect`, the lowest response privilege. Turning protection back on only restores the safe state.
* **TP-06 alerts are built by the agent** (`kestrel_detect::catalog::protection_alert`), not by an event. This keeps them working in full mode with the sensors stopped, and the policy and exclusions cannot silence them. The subject is the agent process, with the tray user as `user`. The usernames in summaries and reports are pseudonymised with the policy's username hashing.
* **`max_minutes` above 480** only raises the cap the agent accepts. The tray offers 15 min, 1 h, 4 h and 8 h (plus `max_minutes` itself when it is below 8 h). The server accepts values from 1 to 10080.
* **Hardening after turn-on** is re-applied in the background (housekeeping), so the tray's request does not wait for AppLocker or PowerShell.

## 2026-10-22 Sensor fixes from the owner-PC triage (pid reuse, event loss, MSIX signatures)

Evidence: `D:\kestrel-build2\owner-pc-alert-triage.json` (Windows 11 developer workstation, Docker Desktop + parallel Rust builds).

**1. Process attribution after PID reuse (correctness bug).**
* *Root cause.* `ProcTracker::at` returned the current owner of a pid for any event stamped up to **1 s** before that owner's start, and fell back to the current owner when no earlier instance matched. In addition, a pid whose last known owner had exited still counted as "known", so an event that arrived before the core session had delivered its owner's start was given to whatever entry the pid had last. Docker Desktop runs short-lived `docker-*.exe` CLI plugins that read `.docker\config.json`; during a build their pids are reused within milliseconds by rustc / link.exe / conhost, and the Kernel-File session is delivered independently of Kernel-Process (Kestrel-Core). Result: ST-01 alerts blaming rustc, cl, link, lib, cargo, clippy-driver, build-script-build, conhost and wsl.
* *Decision.* Events are attributed to the instance that owned the pid **at the event's ETW timestamp** (`kestrel_win::proctrack`): each instance has an `order_ts` in the ETW clock (the Kernel-Process start event's timestamp; snapshot / live-query sightings use the wall-clock create time shifted by the measured ETW−wall offset, because ferrisetw sessions use QPC timestamps (`ClientContext = 1`), which do not follow system-clock adjustments — Microsoft Learn, WNODE_HEADER). The owner is the latest instance with `order_ts <= ts` that had not exited before `ts`. **No tolerance** on either boundary: at millisecond resolution any slack re-opens the window (the old 1 s slack was the bug); a sensitive open in a process's first or last milliseconds is implausible, a misattribution is not acceptable.
* An event older than a known, ordered start whose own instance is unknown is **dropped and counted** (`pid_reuse_dropped`, logged in "sensor health"), never given to the new owner. An event whose owner may simply not be delivered yet (previous owner exited, or only an unordered sighting started after it) is **held** up to 2.5 s (`PendingAttr`, per-pid index, bound 8 192) and decided when that pid's start / stop arrives or at the deadline (then dropped and counted; a pid never seen at all keeps the legacy unlinkable GUID, as before). The existing early-pid hold (events before their own ProcessStart) is unchanged.
* Applies to the sessions delivered independently of Kestrel-Core: Kernel-File (file access, file activity), Kestrel-IO (network, DNS, PowerShell script blocks). Core-session events (image load, Audit-API, registry) are ordered with process start/stop and use the same fixed lookup. File-open de-duplication is now per process instance (GUID), not per pid.
* A late start of an older instance never displaces the current owner; a displaced instance gets an implied exit at its successor's start.
* *Residual.* The ransomware aggregator (`fileagg`) still groups operations per pid inside its window; a summary spanning a reuse is attributed by its timestamp. Lab check in `TESTING-ON-WINDOWS.md` §4.

**2. Event loss under build load.**
* *Root cause (most likely; the device only reported the total).* Every session ran with Minimum = Maximum buffers (Core 32, File 128, IO 128 × 64 KB = 19 MB fixed), so a burst had no headroom and ETW discarded events. `etw_events_lost` also summed kernel loss with Kestrel's own queue drops, so the console could not say which. Every Kernel-File open in the system (thousands per second during a build) was also queued to the translator, which drops all but credential stores / decoys / persistence paths.
* *Decisions.* (a) `consts::buffers`: Core 32→256, File 64→512, IO 128→256 (IO keeps its preallocated minimum: Kernel-Network can log at DISPATCH_LEVEL where ETW cannot allocate on demand), Persist / ProcCmd 8. Idle reservation 15 MB (less than before), worst case 65 MB (**+46 MB**, ≤ 64 MB budget, unit-tested). ETW grows the pool only "if the buffers are filled more quickly than they can be processed" (EVENT_TRACE_PROPERTIES, Microsoft Learn); real-time buffers of kernel providers are non-paged. (b) Kernel-File opens / creates are filtered **in the ETW callback** (`filters::kernel_file_candidate`): detection prefilter (drive-independent substrings), `is_extra_sensitive` (persistence drops, dumps, hives, DPAPI / Vault stores) and credential canaries compared volume-relative — a superset of the translator's check, so nothing the translator used is lost (tested on NT paths). The ransomware aggregation still sees every event (it runs before the filter). With `FILE_READ_EVENTS` on, the filter is disabled (the translator needs every file object). Agent / System (pid 4) opens are not queued (the translator ignored them). (c) Health reports the split additively: `AgentHealth.etw_kernel_events_lost` and `sensor_internal_dropped` (`Option<u64>`, `#[serde(default)]`; older agents send neither), `SensorStats.kernel_events_lost` / `internal_dropped`; `etw_events_lost` stays the total. Callers updated: agent heartbeat, sim, console types, `docs/contracts.md`. **Not done (other owners):** the console device page still shows only the total; the server's `TP-SRV-EVENTS-LOST` summary could name the side.

**3. MSIX / Store apps reported unsigned.**
* *Root cause.* Packaged executables usually carry no embedded Authenticode signature and are not in the system catalog database; the existing catalog fallback (`CryptCATAdminEnumCatalogFromHash`) therefore found nothing and `WhatsApp.Root.exe` was `Unsigned`. The package's PE files are covered by `<package>\AppxMetadata\CodeIntegrity.cat`, signed with the package certificate (Red Canary, "Installer packages"; checked on the owner PC: `Get-AuthenticodeSignature` on that catalog is Valid, the exe itself NotSigned).
* *Decision.* After embedded and system-catalog checks, a file under `…\WindowsApps\<package>\` or `…\SystemApps\<package>\` (any volume, no `..`, never network paths) is verified against that package catalog: Authenticode hash via `CryptCATAdminCalcHashFromFileHandle2` (SHA256, then SHA1), member found by tag or by comparing member digests (`CryptCATOpen` / `CryptCATGetMemberInfo` / `CryptCATEnumerateMember`), then `WinVerifyTrust` with `WTD_CHOICE_CATALOG` on that catalog. `Valid` only when WinVerifyTrust returns 0; bad digest / revoked → `Invalid`; chain or policy failures (e.g. a sideloaded package signed with a certificate trusted only in TrustedPeople) → no verdict, stays `Unsigned` — never `Valid` for something WinVerifyTrust rejected. `microsoft_root` is always false for package-catalog verdicts (Store publisher certificates chain to the Microsoft Marketplace CA under a Microsoft root without the file being Microsoft's; response safety relies on that flag). Verified on the owner PC (read-only): WhatsApp.Root.exe → Valid, source PackageCatalog.
* *Signer.* The certificate's simple display name: for Store-signed third-party packages that is the Store publisher id (`24803D75-212C-471A-BC57-9EF86AB91435` for WhatsApp), not "WhatsApp LLC"; Microsoft's packages show "Microsoft Corporation". Not decorated with the manifest's `PublisherDisplayName`, because rules compare signers by equality / substring and a display name is publisher-chosen.
* *Indication of catalog signing.* `FileFacts.sig_source` / `SigVerdict.source` (`Embedded`, `SystemCatalog`, `PackageCatalog`) inside `kestrel-win`. Not yet on the wire: surfacing it needs an additive field on `ProcessStart` / `ProcessInfo`, which touches `kestrel-detect` (being edited concurrently); left as a follow-up.

## 2026-10-22 Remove device (remote uninstall + removal from the device list)

Owner-agreed design; contract in `docs/contracts.md` "Remove device (remote uninstall)". Decisions taken while building it:

* **Token only at delivery, two candidates.** `ResponseAction::UninstallAgent{purge_data}` never carries the token. The server attaches `ServerPayload::Command.secret = {uninstall_tokens}` when it writes the command to the agent's stream, opened from the sealed columns at that moment. It sends the current **and** the pending (rotated, unconfirmed) token: on connect the pending `SetUninstallToken` is queued after pending commands, so the agent may still hold the old hash; it uses whichever matches. `CommandSecret`'s `Debug` is redacted.
* **Capability, not "unsupported" answers.** Older agents fail to parse an unknown `ResponseAction` variant and drop the whole message unacked (they never answer). So the server stores `Hello.capabilities` per device (`devices.capabilities`), the console disables the button without `agent.uninstall`, and a queued removal is failed as "unsupported" when the connecting agent lacks the capability instead of being sent.
* **Lifetime 90 days** for a queued removal (other commands keep 7): a laptop in a drawer still removes itself when it comes back.
* **Removed only after a confirmed start, certificates revoked a week later** (independent review F1). The agent starts the helper only after the server acked its `uninstall_started` outcome (up to 5 minutes; otherwise it reports failure and does not start). The server marks a device removed after 10 minutes of silence following that outcome, but keeps its certificates valid for 7 days. A removed PC that connects within that week (shut down mid-uninstall, installer rollback) is put back with the removal failed, instead of leaving a running agent locked out with a console that says "uninstalled". This deviates from the design's "revoke at removal"; the owner can shorten `REVOKE_AFTER_REMOVED_MS`.
* **Cancel only before anything was sent** (review F2): `pending` with `sent_at IS NULL`, one atomic UPDATE. After a send attempt the agent may already hold the token.
* **Automatic token rotation after a failed removal** (review F3): the token travelled to the PC (a local admin could read it from the helper's stdin), so an agent-reported failure or a reappearing PC rotates the uninstall token (pending + `SetUninstallToken`, audited).
* **Unreadable sealed token never breaks the session** (review F4): the removal fails instead of the Hello.
* **MFA step-up only when the admin has MFA** (review F5, accepted): as agreed in the design and like enrollment tokens with remote access. Remote access itself requires MFA; making removal require it would block admins without MFA entirely. Mitigations: admin only, interactive session, typed hostname, 20/hour per admin, audit. Revisit if the owner wants `require_mfa` for this.
* **Helper = `kestrel-uninstall.exe --quiet --token-stdin [--purge]`**, reusing the dialog's worker (`MsiConfigureProductExW`, link-safe purge) rather than a second implementation. The agent copies it into `%SystemRoot%\SystemTemp\kestrel-remote-uninstall-<uuid>` (atomic `CreateDirectoryW` with a protected SYSTEM/Administrators DACL) because Windows Installer deletes the install folder. Started with `DETACHED_PROCESS | CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP | CREATE_BREAKAWAY_FROM_JOB` (retry without breakaway). Failure result in `%ProgramData%\Kestrel\remote-uninstall-result.json`, reported by the still-running agent or by the agent the installer rollback restarted (store marker).
* **Two pre-existing clippy lints** in `kestrel-detect` (`paths.rs` `contains`, `engine.rs` `sort_by_key`) were fixed so `clippy -D warnings` passes with the current toolchain; behaviour unchanged.

## 2026-10-22 Kestrel 1.1.6 integration (ST-12 persistence, file-activity semantics, events-lost split)

Follow-ups left open by the three entries above, done by one engineer owning all paths.

**1. ST-12 first-seen memory persists across agent restarts** (`kestrel-agent/src/detection.rs` `load_st12` / `save_st12`, kv key `st12_seen`).
* Only sha256 identities are persisted (see review #7 below). Loaded in the detection thread right after the engine is built (before the agent reports the engine ready, so before any event); saved every 5 minutes from the engine tick and once after the detection loop ends (the agent joins that thread at shutdown). A crash loses at most 5 minutes of first-seen entries: those binaries alert once more.
* Missing, unreadable, malformed or oversized (> 4 MB; 8,192 rows are about 1 MB) values start empty and are overwritten by the next save; import and export run under `catch_unwind`. Never a panic, never a refusal to start.
* `Engine::st12_seen_import(json, now)` gained `now` (API change inside the workspace; the only callers are the agent and the kestrel-detect test): rows already expired, or stamped more than a day after `now`, are dropped. A clock set back, or a damaged value with a far-future timestamp, must not silence ST-12 for good; the cost is one more alert per binary. The store is SYSTEM-only, so this is robustness, not a security boundary.
* Tests: store round trip (no second alert after a "restart"), every damaged variant (missing, `{not json`, wrong row shape, `null`, empty, 4 MB + 1, future-dated) alerts once and is replaced by a valid save, and a SimPlatform agent restores the memory at start and writes it back at stop.

**2. File-activity semantics for RW-06 / RW-08** (`kestrel-win/src/fileagg.rs`, `win/etw.rs`, `kestrel-common` `FileActivity`, `kestrel-detect` `families/rw.rs`).
* *`self_created` (new, additive, `#[serde(default)]`).* The aggregator keeps, per process, how it first met each file (`origins`: created by itself or not, plus the FileObject), beyond the 10 s window, bounded at 2,048 self-created and 4,096 pre-existing files per process (separate FIFOs; about 250 KB for a busy process, about 60 MB worst case across the 256 tracked processes). A rename target is an alias of its source (bounded 2,048), so later operations on the new name belong to the same file and keep its mark. `self_created` = distinct touched files in the window whose first known operation was a create by this process. The state lives as long as the per-process aggregation state (dropped after 30 s idle with an empty window), which is "the aggregation's knowledge" in the brief.
* *Create (12) then CreateNewFile (30) of the same open.* `CreateFile(CREATE_ALWAYS)` of a file that did not exist produces Create with disposition overwrite-if and then CreateNewFile with the same FileObject (delivery order not documented). When CreateNewFile follows, the earlier Overwrite op of that FileObject becomes a create and the origin flips to "created", so a compiler writing new outputs is never "overwriting" anything. A summary emitted between those two events sees one transient overwrite (accepted; tested).
* *`new_files` = first operation in the window is a create of a file the process did not already know.* Delete-then-recreate of `report.docx` is no longer new: its first op is the delete, its origin is "not created", and the recreate counts in `overwrites` (the content was replaced). Fixes review M4 of the detection-quality entry. An origin evicted from the bounded memory counts as unknown (new), i.e. a process that touched more than 2,048 other files since its delete of a document can again hide that one file; noted as residual.
* *Directories are never files or notes.* (a) A Create (12) with FILE_DIRECTORY_FILE now records its FileObject (in scope only, bounded 16,384, cleared on overflow, removed when the FileObject is reused by a non-directory open); CreateNewFile / RenamePath / DeletePath on such an object are ignored. (b) CreateNewFile reads its own CreateOptions (the event uses the Create template: research notes, Kernel-File manifest dump) and ignores FILE_DIRECTORY_FILE. (c) Fallback in `summarise`: a "file" that is the parent folder of another operation in the window is a directory and is skipped (CreateNewFile delivered before the Create that carried the directory flag, and no CreateOptions). Cargo's `out` folders and folders named `README` no longer reach `note_name`.
* *Engine.* `preexisting_files = files_touched - max(new_files, self_created)`; older agents send `self_created = 0` and their `new_files` (every CreateNewFile) keeps the previous bound. RW-08 keeps its note rules (extensionless names never count, build artefacts never count) as defence in depth for older agents.
* *Callers.* Server storyline and console event text add "(N created by the process itself, M existing files)" when `self_created > 0`; console type `FileActivity.self_created?`; `docs/contracts.md`. The agent sim and privacy filter need no change (no field-by-field construction; paths only).
* *Tests* (`fileagg.rs`, feeding the summaries into the real engine): a compiler sequence (60 `out` folders in all three delivery orders, generated files inside them, `.tmp` outputs written with CREATE_ALWAYS and renamed to `.rlib` / `.rmeta` 15 s later) gives no RW-06 / RW-08 in default and Protect policy; deleting and re-creating 150 existing `.docx` / `.xlsx` in 6 folders (both 12/30 orders) fires RW-06 with `new_files = 0`, `self_created = 0`; 200 junk files do not hide 100 renamed documents; folders named `readme`, `readme.txt`, `how_to_decrypt.txt` in 30 folders are never a note while files of those names are; origins stay bounded. Engine tests in `fp_workstation.rs` (`rw06_uses_self_created_and_rewrites`).
* *Hostile review (fresh read-only reviewer, same day) and the changes it caused.* Shared assumption: Create (12) is logged when the open is dispatched, so a **failed** open still produces it; only CreateNewFile (30) proves a create. Where these bullets differ from the description above, the bullets are the shipped behaviour.
  * **#1 High (new), fixed:** the parent-folder fallback let one failed open of `doc.docx\x` per document hide that document and ransom notes. A "file" is now a folder only when every operation on it in the window is a confirmed create (event 30) and the child is a confirmed create too.
  * **#2 High (older, now easier), fixed:** a failed `CREATE_NEW` on an existing document (Create 12, disposition FILE_CREATE) made it look created. Disposition-2 creates are now unconfirmed: no self-created credit, not counted as files or notes, confirmed only by the CreateNewFile of the same open.
  * **#3 Medium, fixed in part:** junk creates could evict the knowledge that documents existed. ## 2026-10-25 Evidence capture for suspected data theft (owner decision)

**Owner decision (2026-10-25), recorded verbatim in substance.** When Kestrel suspects data theft, admins may collect and download evidence that can contain the employee's real secrets. Same guardrails as the remote file manager:
* admin role only: new privilege `evidence.download`, held only by the built-in `admin` role (through `*`); API tokens are refused even with `*` (interactive console session only);
* every download is audited;
* stored encrypted at rest on the server;
* deleted automatically after a retention period (default 14 days, configurable in Settings);
* never put into telemetry, ClickHouse or hunt;
* the employee is told in the tray: "IT collected evidence from this PC for a security investigation".

**Privacy exception wording (extends the CLAUDE.md privacy exception of 2026-10-21; CLAUDE.md itself is not edited):** besides the admin-initiated remote desktop and remote file manager, *evidence capture for suspected data theft* is an exception to "never upload content": after an ST-02 / ST-04 alert the agent keeps, encrypted on the PC, copies of files the suspicious process tree staged, copies of the credential stores it read and a 60-second packet capture of its connections. Only metadata (the privacy-filtered manifest) reaches the server automatically; the content is uploaded only when an administrator clicks Collect evidence, is stored encrypted, is downloadable only by administrators as a password-protected archive, every collection / download / deletion is audited, it is deleted automatically after the retention period, it never enters telemetry, ClickHouse or hunt, and the employee is notified in the tray when it is collected. No background capture of keystrokes, screenshots or browsing is added: everything is tied to one alert and one process tree.

The owner chose all four parts and asked for all of them on by default in the Default policy.

**Design decisions taken autonomously (reasons):**
1. **Triggers**: ST-02 and ST-04 alerts in any mode (Audit included) and also while protection is turned off in *detection only* mode: capture is collection, not containment, and nothing on the PC changes. A second trigger for the same tree within 10 min joins the running capture (`alert_ids`), so ST-02 + ST-04 on one stealer make one bundle.
2. **Process tree** = the alerting process, its descendants, and its ancestors up to (not including) the first one in Windows / System32 / Program Files (the loader that started a stealer from `%TEMP%` is part of the theft; `explorer.exe` is not). At most 64 processes. Descendants started during the 60 s follow-up are included.
3. **Where "files the process wrote" come from.** Existing telemetry is not enough: `file_access` covers only credential-store / persistence paths and `file_activity` only user-data folders with 10+ files and 5 sample paths. A new sensor side channel `SensorConfig.write_tx` reports Kernel-File creates with write dispositions (create / supersede / overwrite / overwrite-if; open-if only for new files via CreateNewFile) and new files (CreateNewFile) under user-writable locations (`\Users\…`, `\ProgramData\…`, `\Windows\Temp\…`, `\Temp\…`) as `WriteHint`s. They never become `Event`s (so they can never reach telemetry, ClickHouse or hunt by construction), feed a bounded per-process journal in `kestrel-detect` (pure, Linux-tested), and are only sent while staged-file capture is on. `file_access` writes and `file_activity` sample paths are fed to the same journal too. Limitation: an append to an existing file opened with FILE_OPEN is not seen (Kernel-File Create carries no desired access); staging archives and dumps are new files, which are seen.
4. **Copies are taken at the end of the follow-up window (alert + 60 s)**, i.e. as the files are then; files deleted in between are listed as `missing`. Originals are opened read-only, sharing read / write / delete (never blocking the owner), never followed through junctions / symbolic links / mount points, hard-linked files and alternate data streams are refused, and Kestrel's own folders are skipped. Limits: 50 MB per file, 200 MB and 500 files of staged files, 50 MB per credential store and 100 MB in total, 50 MB pcap.
5. **Locked SQLite files.** Kestrel had no Volume Shadow Copy-free raw-read approach for scanning to reuse (checked: scan and quarantine use normal handle-based reads), and a VSS snapshot or raw NTFS read would be new attack surface and heavy. A credential store opened by its browser without read sharing is recorded as `locked` ("locked, not copied"). Chrome / Edge lock `Cookies` while running; `Login Data` and `Web Data` are usually readable.
6. **Bundle format.** One file per bundle on the PC, `KEB1` container (entries + `manifest.json` last; names restricted to `staged/NNNN-<safe name>`, `secrets/NNNN-<safe name>`, `capture.pcapng`, `manifest.json`), sealed with streaming AES-256-GCM (`KSE1`, `kestrel_common::seal`, the quarantine vault construction plus the bundle id bound into every chunk) under a per-PC key stored DPAPI-protected (machine scope) in the SYSTEM-only state folder. Pure, shared by agent and server, Linux-tested.
7. **Upload is pulled by the server over the existing live channel**, the same chunked, sequential, SHA-256-verified scheme as remote file manager downloads (512 KiB chunks): `ResponseAction::CollectEvidence` (durable command, delivered when the PC is online; the agent checks the bundle, notifies the tray and answers ok) → server sends `LiveServerMsg::EvidenceRead` → agent answers `LiveAgentMsg::EvidenceData`. Reason: the outbox (SQLite, capped) is wrong for hundreds of MB, and the live channel already has flow control and integrity checks. Evidence reads are not part of the remote-access profile: a device enrolled with no remote access can still give evidence. After the server stored and verified the bundle it queues `ResponseAction::DeleteEvidence`, and the PC deletes its copy.
8. **Server storage**: `KESTREL_EVIDENCE_DIR` (docker volume), one sealed file per bundle under a server key derived from `KESTREL_MASTER_KEY` (`subkey("evidence-at-rest-v1")`), context = bundle id. Total storage capped (`KESTREL_EVIDENCE_MAX_GB`, default 20). The container is re-validated (names, sizes, manifest last) when it is stored.
9. **Download format: AES-256 encrypted ZIP (WinZip AE-2)** built with the `zip` crate (MIT, `aes-crypto` feature only), stored entries, a random 24-character password generated per download, shown once in the console and never stored or logged. The archive is built into a temporary file whose entries are already encrypted (plaintext never touches the server disk) and is streamed once to the same admin session within 10 minutes. Opens in 7-Zip, WinRAR, WinZip, Keka and `7z x`; Windows Explorer's built-in zip support cannot open AES-encrypted archives (ZipCrypto, which it can open, is broken and was rejected). Documented in the console and docs.
10. **Packet capture: `PktMon.exe`** (research `docs/research/notes/evidence-pcap.md`), Windows 10 2004 (build 19041) and later only. One `filter add` per remote IP / port / protocol tuple of the tree (at most 16), `start --capture --comp nics --pkt-size 0 --file-size 50 --log-mode circular`, `stop`, `filter remove`, `etl2pcap`. Arguments are built only from parsed `IpAddr`, `u16` and the protocol enum; no shell; absolute path under `%SystemRoot%\System32`. Kestrel never takes over a running pktmon session (`busy`) and never runs `pktmon unload`. A marker file lets the next agent start stop a capture a crashed agent left behind, only when its log file is in Kestrel's folder. Limitations shown in the UI and recorded in the manifest (`filters`): other programs' traffic to the same IP:port (shared CDN addresses) is included; TLS / VPN traffic stays encrypted; loopback is not captured; connections the tree opens after the capture started are missed unless pktmon accepts filters during a capture (lab check); past 50 MB the oldest packets are overwritten (circular log). The Microsoft-Windows-NDIS-PacketCapture ETW provider was rejected (no port filter, needs `netsh trace` and an extra converter).
11. **Retention**: on the PC, `Policy.evidence.local_retention_days` (default 14) for bundles nobody collected; on the server, `Settings.retention_days.evidence` (default 14) from the time it was stored. Both delete the data and keep the metadata row (status `expired`) with the audit trail.
12. **Settings / policy toggles**: `Policy.evidence = {staged_files, secrets_list, secrets_copy, pcap, local_retention_days}`, all on by default (also for policies saved before the field). Turning every part off disables capture entirely; `secrets_copy` needs `secrets_list`.
13. **Audit**: `evidence.collect_requested`, `evidence.collected` (stored on the server), `evidence.collect_failed`, `evidence.downloaded`, `evidence.deleted`, `evidence.expired` (actor system). The manifest (metadata, privacy-filtered by the device policy and scrubbed again by the server) is visible to every role with `read`; only collecting, downloading and deleting need `evidence.download`.

## 2026-10-25 Endpoint footprint (CPU, memory, disk, network)

Owner request: make the agent and tray as light as possible without losing detection. Details and numbers: `docs/PERFORMANCE.md`.

1. **Drops: shed by value, coalesce exact duplicates at the source.** The owner's own telemetry showed OneDrive opening `explorer.exe` with `PROCESS_DUP_HANDLE` about 25,000 times per second for four minutes; 7,403 records were dropped somewhere in that storm (the split by queue was not logged). Instead of only enlarging queues: identical `OpenProcess` records (actor, target, access, status) within 2 s are coalesced in the ETW callback (a start / stop of either pid ends the window; `TerminateProcess`, `OpenThread`, DPAPI are never coalesced because rules count or time them); image loads the translator would discard are filtered in the callback; the raw queue sheds low-value records at half full and medium ones at 7/8, never high-value ones before it is full. Reason: detection decides on the first of identical records; a queue full of noise must not cost a process start.
2. **Aggregator window trims are not losses.** A process with more than 2,048 file operations in 10 s keeps being summarised from its latest 2,048 (far above every RW threshold); those trims were reported as dropped events and are now a diagnostics counter.
3. **Degraded needs significant loss.** Any high-value loss, or more than 1 % of the interval's events. Older agents keep "any increase". Reason: a handful of shed image loads during a build is not "detections may be blind".
4. **Upload de-duplication with a count, 5-minute window.** Detection always sees every event; only the hunting copy is merged. 1 minute removed 13 % of idle rows, 5 minutes 41 %, 10 minutes 51 %; 5 minutes keeps a summary within 5 minutes and bounds memory (8,192 open windows). First occurrence is uploaded at once.
5. **No double compression; no compressed requests.** Payloads have been zstd-compressed in the envelope since 1.0 (bounded inflation). The server sends zstd responses to agents that advertise it, but refuses compressed requests: tonic 0.12 inflates them unbounded before any handler, and `Enroll` is unauthenticated (independent review H1). The owner asked for "accept compressed and uncompressed"; uncompressed (all agents) is what matters for compatibility, and request compression would add nothing on top of the envelope's zstd. Revisit when tonic bounds decompressed size.
8. **Review follow-ups.** Kernel ETW loss always counts for Degraded; image loads that pass the source filter and DNS answers are high value; the agent channel does not shed early; coalescer invalidation is O(1) (pid generations); de-dup key includes host name, DNS answers and signature.
6. **Priorities.** `kestrel-scan` runs in process background mode + EcoQoS; enrichment workers below normal + EcoQoS; revocation checks background mode; the outbox writer below normal + EcoQoS (not background mode: it holds the store lock that alerts use). Detection, response, the first-run enrichment worker and the ETW consumers keep normal priority. Scans are not skipped on battery saver: they are analyst-requested.
7. **Tray: no WebView while closed.** The window is created on demand and destroyed when closed; GPU off for the WebView. The always-on remote-session banner is drawn by the agent's desktop helper, not the tray, so it is unaffected.

**Addendum (same day): independent hostile review and what changed.** A fresh read-only reviewer attacked the feature (compromised admin, stealer on the endpoint, malicious agent, pktmon injection, tampering, retention, leakage). No Critical. Confirmed and fixed:
* **H1 (High)** Kernel-File Create (12) is logged for failed opens, so a stealer could "write" or "read" another user's files and machine secrets and make the SYSTEM agent copy them. Write hints now come only from CreateNewFile (30) (decision 3 above is narrowed: overwrites / appends in place are not seen), and the builder copies only from the tree user's own profile (plus `Public`; nothing under `\Users\` when the user is unknown) and never from machine-secret folders (`ProgramData\Microsoft\{Crypto, Vault, Wlansvc, Windows\WER, Group Policy}`, `ProgramData\ssh`, `System32\config`, `System32\Microsoft\Protect`, `Windows\NTDS`, `Windows\repair`); refused files stay listed as metadata. WER and Group Policy were added on judgement (crash dumps hold other processes' memory; cached GPP passwords).
* **H2 (High)** an oplock that is never acknowledged, or a user-registered cloud provider, could block the single bundle builder forever. Opens use `FILE_COMPLETE_IF_OPLOCKED` (a break in progress = `locked`), cloud placeholders are refused (never hydrated as SYSTEM; OneDrive "always keep" files are lost coverage), reads are cancelled after 30 s (`CancelSynchronousIo` watchdog), files after 2 min (`truncated`), builds after 10 min (`failed`, slot released, abandoned thread cleans up).
* **M1** junk files evicting the archive from the journal: high-value extensions are kept preferentially, evictions counted in the manifest. **M2** 16 junk alerts blocking captures: 2 uncollected bundles per program (image hash), 32 / 2 GB total, 2 GB free-space floor (residual: 16+ distinct binaries can still fill the slots). **M3** a huge manifest failing the bundle: strings clipped to 1024 bytes, lists trimmed with a note. **M4** long paths growing SYSTEM memory: paths > 1024 UTF-16 units dropped in the ETW callback, dedup bounded by bytes. **M5** signed per-user apps (Telegram, Discord) pulled in as ancestors: ancestors need a user-writable folder and no valid signature. **M6** a malicious agent holding the pull slots: fixed per-chunk deadline, overall deadline, one pull per device. **M7** no step-up: collect and download need MFA re-auth within 10 min when the admin has MFA (admins without MFA allowed, same as Remove device F5), optional audited reason.
* **Low**: tickets of a bundle deleted during the archive build (re-check + revoke), retention following the current setting, per-bundle server keys wrapped by the master key and erased on delete / expiry (crypto-shredding; the PC side still relies on file deletion under one DPAPI key — accepted, the bundle is deleted within the retention), `evidence.download_started` audit before the first byte and `collect_failed` as a system action with the agent's text labelled, stricter entry names (`NNNN-` prefix, no trailing dot, case-insensitive duplicates), pktmon never stops a session when `status` fails, pcap size slack, infrastructure ports (53, 88, 135, 139, 389, 445, 464, 636, 3268, 3269) never used as capture filters, profile folder names pseudonymised in uploaded manifests under `hash_usernames`.
* Accepted as designed: the manifest (metadata, file names) is visible to every role with `read`; the AES zip's central directory shows entry names in plaintext (standard for WinZip AES); the PC key is machine-scope DPAPI protected by the SYSTEM-only folder ACL; pktmon cannot filter per process (documented in UI and manifest).

## 2026-10-25 Sensor: file-open attribution (FP-01) and `Local State` opens (FP-04)

**1. FP-01 root cause: pid reuse in the agent builds that recorded the export, already fixed by the 2026-10-22 tracker. The pattern is not a header-pid or FileObject-cache defect.** Evidence from `D:\kestrel-build2\corpus\owner-pc-2026-10.jsonl.zst` (read-only; analysis scripts kept outside the repo):
* 310 opens of `C:\Users\<user>\.docker\…` are attributed to unrelated processes: rustc 143, link 24, build-script-build 24, powershell 22, conhost 19, cl 14, bash 12, wsl 10, grep 8, sed 6 and others. They are always the Docker CLI's open sequence (`config.json` 108, `contexts\meta\<hash>\meta.json` 107, `contexts\tls\<hash>` 76, `cli-plugins`), never a single file.
* 294 of the 310 are stamped **after the attributed process had exited**: 0.1 to 28 s after its ProcessStop. The "9 to 67 s into the process's life" is the gap from the start of a process that was already gone. Example: `wsl.exe` ran 165 ms, and 13.6 s after its stop "it" opened `config.json`, `meta.json` and `cli-plugins`.
* For all 310, the pid was **later** held by a `docker*.exe` process. That instance had started 10 to 100 ms before the open (271 of the 310 were within 0 to 50 ms), which matches docker.exe's normal pattern of opening `config.json` 10 to 50 ms after it starts. In 226 cases that docker instance has **no** `.docker` open of its own in the export. In the whole corpus only 133 of 57,887 short docker.exe instances have none. The opens were therefore docker's own, given to the pid's **previous** owner. The harness check ("the previous holders were not Docker") looked in the wrong direction. The new holder is the Docker one.
* By time: the 294 occur from 10-21 23:00 to 10-22 18:41 SGT. Those are the agent instances (agent pids 12104, 32888, 62676) started at or before 10-22 01:22, before the pid-reuse fix (commit 30a0699, 10-22 02:49). The next agent instance (started 10-23 21:20) ran with the same Docker Desktop polling and about 103,000 process starts on 10-24/25, and produced **zero** such opens. The remaining 16 are a genuine directory walk by a live `powershell.exe` (`.docker\`, `buildx\…`, `contexts\…`), not misattribution.
* Mechanism (old code): Kernel-File and Kestrel-Core are separate real-time sessions with independent flushes, so docker's open was delivered before docker's ProcessStart. The old `ProcTracker::at` still counted the exited previous owner as "known" and gave it the open. The 2026-10-22 tracker (attribute at the event's ETW time, hold up to 2.5 s while the owner is pending, drop rather than guess) covers exactly this. A regression test now replays the measured interleaving (`proctrack::opens_of_successor_delivered_before_its_start_are_not_given_to_exited_owner`, `successor_never_seen_is_not_given_to_exited_owner`).
* FileObject name cache: it is keyed by (pid, FileObject) and only used for first-read events (`FILE_READ_EVENTS`, off). It played no part in FP-01: no Read events were enabled, and every `file_access` open comes from the Create's own `FileName`.

**2. Hardening done anyway (cheap, closes the remaining theoretical paths):**
* *Issuing thread.* Kernel-File Create (12) and CreateNewFile (30) carry the issuing thread: `IssuingThreadId` (UInt32) in template v1, `ThreadId` (Pointer) in v0. This was checked on build 26200 with `(Get-WinEvent -ListProvider Microsoft-Windows-Kernel-File).Events`. For opens that pass the source filter, the callback compares it with the event header's ThreadId. When they are equal (the normal synchronous case) the header pid is used and no syscall is made. When they differ, the issuing thread's process is used (`OpenThread(THREAD_QUERY_LIMITED_INFORMATION)` + `GetProcessIdOfThread`), but only if that thread was created no later than the event plus 2 s (`GetThreadTimes`), so that a reused thread id is not trusted. If the thread cannot be resolved, the open is dropped and counted, never blamed on the logging context. New counters `file_issuer_other` and `file_issuer_unresolved` are in the 5-minute "sensor health" log line. The ransomware aggregator and evidence write hints keep the header pid (resolving every create would be a syscall per mismatched event on the hot path). This is residual and should be revisited if the lab shows `file_issuer_other` > 0.
* *FileObject names.* Entries are recorded only when Read events are on. A first read is named after its Create only if the pid tracker shows the same process instance at both timestamps, and a read stamped before the create is never named. A stale entry is removed (`fileattr::FileObjects`).

**3. FP-04: `Local State` opens outside the known stores are forwarded.**
* The Kernel-File callback forwards any open whose last path component is `Local State` (`filters::kernel_file_candidate`). The callback cannot know the opener's `--user-data-dir`, so it does not filter by location. The translator keeps such an open when it is not already a sensitive path (sensitive paths take the existing path) and when it is either under a user profile (`<vol>:\Users\<name>\…`, no UNC, no `..`) or under the opener's **last** `--user-data-dir` from its final command line (Chromium honours the last one; `=`, quoted and space-separated forms are accepted). Each (process instance, path) is forwarded once, with at most 16 paths per instance and 4,096 instances remembered (clearing beyond that costs at worst one repeat). It is emitted as a normal `file_access` open; no contract change.
* Reason: an Electron / Chromium app reads its own `Local State` immediately before its DPAPI "Chromium" decrypt. With this open visible, the engine can tie the decrypt to the app's own profile instead of guessing. Recognising "own profile" is the detection engineer's job in `kestrel-detect`. The sensor only makes the read visible.
* Volume: the export shows Brave re-opening its own `Local State` about 86 times an hour (8,148 opens over 76 h, after the 10 s de-dup). That is the upper bound per running Chromium-family app reaching the **raw queue** (a few hundred records an hour on a typical desktop, negligible next to `file_prefiltered`). Emitted events are once per (process instance, path): typically one per app start for Discord, VS Code, Slack and similar apps.
* Drop policy: `Raw::FileCreate` is `Value::High`, so it is never shed early, and `Local State` opens share it with credential-store opens. Evidence write hints (`Raw::WriteHint`, low value) are a separate record sent in addition. Shedding a hint never affects the open.

Input: `docs/DETECTION-QUALITY.md` (FP-01..FP-18, owner-PC export of 5.0 M events), `docs/research/malware-corpus-report.md` (117 malicious scenarios, 28 misses), the ratchet `harness-known-failures.json` (29 entries). Details per decision:

1. **Identity, not name** (`identity.rs`, new). A process is the application it claims only with a valid signature by the publisher's *exact* signer subject (list per publisher, case-insensitive, no substring), at the publisher's install location, and never tampered with. Listed: Chrome / Edge / WebView2 / Brave / Firefox / Thunderbird / Opera / Vivaldi / Yandex / Arc, the Windows hosts that own Windows stores (System32 + Microsoft signer only: svchost, lsass, dllhost, explorer, backgroundTaskHost, RuntimeBroker, taskhostw), VS Code, OneDrive, Teams, Discord and Exodus (incl. their Squirrel `Update.exe`), Telegram, Steam, KeePass, KeePassXC, Bitwarden, 1Password, Docker. Used by `is_trusted_owner`, the browser shortcuts of ST-03 / ST-04 / ST-14 / ST-07, `domain_owner_ok` and the tree boundary. `BENIGN_READERS` now carries exact signer lists (the old substring match let "Reset Data Systems Ltd" pass as ESET) and needs the same identity (or the Defender platform folder); KeePass, KeePassXC, BleachBit and PrivaZer no longer pass without a signer. *Deviation:* the brief asked for the location to be part of every identity; for portable apps (Telegram, Steam, KeePass, KeePassXC) the exact signer is the identity and any non-Temp / non-Downloads folder is accepted, because these are routinely installed on other drives.
2. **Taint** (`engine.rs` `on_target`, `on_image_load`, `taint`). A process that receives a remote thread, a thread-context change or a debugger from a non-protected, non-AV process, or a successful handle with VM_WRITE / CREATE_THREAD (0x20 / 0x2; plus VM_OPERATION for browsers and installed apps as before) from an untrusted or itself tainted actor, or that (validly signed) loads an unsigned / invalid DLL from a folder that is not System / Windows / Program Files, is tainted for its lifetime: no owner status, no benign-reader entry, no Windows-binary exemption, no WAM / dev-tool / vendor / own-key allowance, never a genuine browser, and an untrusted actor for ST-07. Not from an actor without an image (processes predating the agent that it could not open), not refused opens (return code ≠ 0: Roblox's anti-cheat probing LSASS), not the WebView2 hosting case. Bounded at 8,192 (dead processes dropped first).
3. **Windows binaries** (`system_reader_ok`). Trusted, untainted Windows binaries are only exempt for the Windows Credential Manager, DPAPI master keys, the WAM token cache and MSAL. Any other store read by a Windows binary is judged like any other reader.
4. **Process trees** (`TreeCred`, `tree_keys`, `tree_boundary`, `check_tree_st02`, `st04`). Every non-benign credential read (and DPAPI unprotect) is recorded for the reader and its untrusted ancestors up to the first boundary (trusted Windows binary, protected process, or a genuine installed non-interpreter application). ST-02 also fires for a tree root when ≥ 2 processes of the tree collected ≥ 3 categories in 60 s. ST-04's reader search: the sender, its parent, its direct children (any read), deeper descendants (non-benign reads only), the sender's tree (a reader with a high-value store or two different stores; survives the reader's exit, GUID-keyed), and for the BITS service host the trees that created a BITS upload job (`bitsadmin /upload`, `Start-BitsTransfer ... Upload`). Non-benign readers win over benign ones (a signed Electron app's own key no longer shadows its child that copied the real stores). Window 5 min, or 30 min once the flow reported ≥ 64 KB sent. *Trade-off:* a single developer-tool store (FP-01's `.docker\config.json`) never links beyond direct relatives, so a build tree's later `git push` is not "steal-then-send".
5. **Sends that are not sends**: a single UDP/443 datagram of ≤ 1,500 bytes (QUIC Initial; Xeno's 1,250 B) is ignored by ST-04; the flow's 64 KB report still counts.
6. **Destination classes for benign reads** (`st04`). A dead-drop / exfiltration-service host always gets the full response. Program Files WAM clients: Microsoft first-party domains (`MICROSOFT_FIRST_PARTY`, incl. SharePoint / Outlook / Xbox Live) Low, other names and raw IPs High Audit. Developer-tool stores: only the store's tool publisher (`DEV_TOOL_PUBLISHERS`: Docker Inc → Docker + kube, Microsoft → Azure CLI + kube + Docker, Amazon → AWS, Google → gcloud + kube, HashiCorp / JetBrains → all five, SUSE (Rancher, unverified subject) → kube + Docker) counts as a developer tool; its own or the provider's endpoints Low, other names and raw IPs High Audit. Per-user VS Code (FP-03): `github.com` Low, `api.github.com` High Audit (decision: the GitHub sign-in calls it, but it can also create gists), `gist.github.com` / `uploads.github.com` / `*.githubusercontent.com` / anything else the full response. FP-02: native CLI plugins are not judged by runtime eval switches (`docker-buildx bake --file -` reads stdin); `-e` / `-p` / `--eval` / `--require` / `--inspect` still disqualify.
7. **Provider allowance** (Shai-Hulud): never under a package-manager install (npm / pnpm / yarn / bun / pip / poetry, up to 5 ancestors), and not after three distinct service hosts of the provider (region / service sweep).
8. **Own profile key** (FP-04, Xeno; sensor change of the same day). Any `...\Local State` open is evaluated first: the process's own profile (last `--user-data-dir` of itself or a same-image parent / child, or `%APPDATA%` / `%LOCALAPPDATA%\<name>\Local State` with `<name>` matching its image or install folder; never a named browser's profile or Discord's key unless it is their owner) or foreign. On its own such an open raises nothing. A "Chromium" DPAPI decrypt after an own-profile read and nothing foreign by the process or its tree (10 min) is ST-03 Info, Audit, not a credential signal. Without that evidence: the own-key Low allowance now needs identity (genuine Program Files install or a listed per-user publisher such as Discord / VS Code) instead of "under Program Files"; otherwise ST-03 stays High (current behaviour), and a ST-04 whose only secret is a "Chromium" key with no store opened by the reader or its tree is High Audit without containment (own dedup key, so a later store read + send is the full response). *Reasoning:* a stealer must read the store whose key it decrypts; that read is what gets contained.
9. **Paths.** 8.3 short components are expanded against a vocabulary of store path components and the wallet / password-manager extension ids (`match_short_names`, bounded to 256 combinations; `may_be_sensitive_short` keeps ordinary `PROGRA~1` paths out). `\\?\GLOBALROOT\Device\...`, `\\.\GLOBALROOT\...` and `\??\GLOBALROOT\...` normalise like `\Device\...` (shadow copies). FP-13: an `open` of a store *folder* (wallet-extension folder, Vault / Credentials / Protect folders, `.aws\cli\cache`, a Telegram account folder, any path ending in `\`) is not a read. FP-01: a read stamped more than 5 s after the process exited is dropped (PID reuse in pre-1.1.6 agents; the sensor engineer confirmed the cause). The sensor's own prefilter (`kestrel-win` `filters::may_be_sensitive`) now also forwards paths that pass `may_be_sensitive_short` (integration, 2026-10-25).
10. **ST-07** also for a tainted actor (DeerStealer's side-loaded Q-Dir host). **FP-05**: an MSIX app in its WindowsApps folder (not invalidly signed) opening a WebView2 launched by another process of its own package, or a WebView2 from the Edge WebView tree whose launcher is not in the table.

A new build is judged again.

## 2026-10-25 Detection-quality harness (corpus, ratchet, owner replay)

* **What it is.** `kestrel-detect` gets a replay harness (`src/eval.rs`, `examples/eval.rs`) and a corpus gate (`tests/corpus_eval.rs`): every scenario under `tests/corpus/{malicious,benign,benign-lookalike}` is replayed with all rules in Audit and again in Protect, and checked against its `.expect.json` (`must_alert` any-of groups, `min_severity`, `must_act`, `allow`). It runs in the normal `cargo test` and in CI. Details: `docs/DETECTION-QUALITY.md`.
* **Malicious scenarios are synthetic.** We never run real malware (CLAUDE.md). The 117 original scenarios are written from public behaviour reports (`docs/research/malware-corpus-report.md`, cited per scenario) as event sequences in the agent's own event format, not captured from samples. They test the rule logic, not the sensor. The sensor side remains covered only by the benign emulations in the lab VM.
* **Benign data is real but anonymised.** 47 slices are cut from the owner's PC export (5.0 M events, 2026-10) with the user name and host name replaced (`j.doe`, `WS-01`). The raw export stays outside the repo (`D:\kestrel-build2\corpus`), because it is personal data.
* **Ratchet instead of a red build.** Known gaps go in `tests/corpus/harness-known-failures.json` with a reason. The gate fails on a new failure, and also on a listed scenario that now passes, so the list can only shrink. It held 29 entries at the start and is empty after the fix round.
* **Signatures the export lacks.** Processes started before the agent have no signer in the export. `--signatures <file>` fills them from a separate file, applied also to process starts with an unknown signature, as the live agent does when a signature check finishes late. The owner-replay numbers are given both without it and with it. The "with" run assumes that Discord 1.0.9262 is signed like the other two Discord builds in the export, and uses the NordVPN signer seen on this PC. ## 2026-10-25 Review of the 1.1.7 integration

A fresh read-only hostile review of the uncommitted 1.1.7 work (evidence capture, footprint, `FileSessionEnd`, trust rewrite) found 4 Medium, 3 Low and 2 Info items. Each was checked against the code and all were confirmed. What was done:

* **M1, 8.3 short names bypass the evidence scope checks (confirmed).** `collect_refusal` and the own-folder check ran on the journal's raw path while the Windows open expanded short names (`C:\PROGRA~3\Microsoft\Vault\...` was copied as SYSTEM). Fix: new `EvidenceHost::resolve_path` (Windows: the existing link-safe attributes-only open, which returns the long path that equals `GetFinalPathNameByHandleW`). The agent decides on the resolved path, refuses a path that still has an 8.3 component (`has_short_component`, pure and Linux-tested), also refuses a protected raw spelling, and `copy_file` checks the opened handle's verified path again before reading anything. The free-space estimate uses the same decision.
* **M2, failed opens outside `\Users\` copied as SYSTEM (confirmed).** The sensor cannot tell a successful open from a failed one: Kernel-File Read events (the proof of success) are off by default (`FILE_READ_EVENTS = false`) and Create (12) has no status. Decision: restrict instead of impersonating. Credential stores are copied only from the tree user's own profile and only listed elsewhere. Staged files outside the own profile (`Public`, `ProgramData`, `\Windows\Temp`, other folders) are copied only when the sensor confirmed that a tree member created them (`StagedCandidate.confirmed`, set by the CreateNewFile write hints, `EvidenceJournal::observe_sensor_write`). `FileAccess` creates and writes and file-activity samples are open attempts and stay unconfirmed. The deny-list gained `\Windows\ServiceProfiles`, `Panther`, `System32\Sysprep` (unattend files), `Windows\Security`, `Windows\CCM`, `Minidump`, `LiveKernelReports`, `MEMORY.DMP`, `System Volume Information`, `pagefile.sys`, `hiberfil.sys` and `swapfile.sys`. Impersonating the alerting process's token was rejected for now. It needs the token duplicated at trigger time, but the process may be gone 60 s later, and the token of a killed or suspended stealer would have to be kept. Recorded as a possible later improvement. The simulator now sends a write hint for replayed `file_access` creates and writes, as the real sensor does for new files.
* **M3, a genuine Electron owner running attacker JavaScript is silent (confirmed).** A process start carries image, command line, user, integrity, session, signature and parent, but no environment, so `ELECTRON_RUN_AS_NODE` is invisible. Fix (`legit_apps::electron_runs_foreign_code`, `EngineState::electron_hijack_suspected`): an Electron image (`ELECTRON_OWNERS`: Discord, Exodus, Slack, Ledger, Bitwarden, 1Password, Signal, Element, Atomic, Guarda, Trezor Suite, KeeWeb, Teams classic, Skype, WhatsApp, Mailspring, Jaxx, Binance, plus the developer `ELECTRON_HOSTS`) with a script, eval / require or inspector / remote-control switch is never an owner. A store-owning one is also refused on any positional argument except a protocol activation, a Squirrel launcher value (`--processStart Discord.exe`) or the relauncher's own target (`--type=relauncher --- "...\Discord.exe"`, found in the owner replay). It is refused as well when its launcher is untrusted (walking up through plain instances of the same genuine app, so the Squirrel stub, Chromium children and the update relaunch keep ownership). Developer hosts (VS Code etc.) are not held to the positional / launcher rule because their own extension hosts run as Node with positional arguments. The guard applies to `is_trusted_owner`, `own_embedded_profile`, the own-`Local State` decision and the ST-01 browser-name owner downgrade. Corpus: `malicious/evasion_electron_run_as_node_discord_script`, `malicious/evasion_electron_run_as_node_stdin_untrusted_parent` (both fail without the fix: only ST-12 fired) and `benign-lookalike/benign_discord_squirrel_stub_children`. Gate: malicious 127/127, benign 47/47, benign-lookalike 16/16. Owner replay (`--signatures owner-signatures.jsonl`): Default policy 463 alerts and 13 containment actions, the same as before. With the assumed signatures: 347 alerts and 0 containment actions. The first run without the relauncher exception gave 34. That is how the relauncher case was found.
* **M4, unbounded evidence rows from a compromised agent (confirmed).** Fix in `evidence::report`. The alert must be this device's ST-02 / ST-04 alert. Because the agent queues its `capturing` (and an immediate `failed`) report before the alert, an alert the server does not have yet is accepted for those states. `ready`, the only state that stores a manifest, needs the alert. New rows are capped at 32 per device that are open or name an unknown alert (so terminal reports for unknown alerts do not free the cap), and at 4 per alert, under a device-row lock. The stored manifest cap is lowered from 4 MB to 1 MiB, and the staged, secrets and process lists are halved in turn with a note. SSE events are sent only on a real change. A per-device token bucket was not added: the caps bound storage, and unchanged reports no longer publish.
* **L1, the taint set was cleared when full (confirmed).** Now only entries of exited processes, or processes no longer in the table, are pruned. Live tainted processes always stay (bounded by the process table's own cap). The prune mark doubles to what is left, so a flood costs amortised O(1). Unit test `taint_overflow_never_untaints_live_processes_l1`.
* **L2, `name.<suffix>` profile matching crossed users (confirmed).** New `EvidenceHost::profile_dir`. On Windows it is `LookupAccountNameW`, then `ProfileList\<SID>\ProfileImagePath`. When it resolves, only that exact folder is the user's. Otherwise only the exact folder name counts, never a prefix.
* **L3, delete without MFA step-up (confirmed).** `DELETE /evidence/:id` calls `require_step_up`. The console's delete dialog goes through `withReauth` like collect and download. The mock and the docs say so.
* **I1, unencrypted zip names and dangerous staged files (confirmed).** The download archive names credential-store copies `secrets/NNNN.bin` (the encrypted `manifest.json` maps the number) and staged files `staged/NNNN-<name>.bin`. README.txt and `website/console/evidence.md` say that entry names are not encrypted and that staged files come from the suspicious program and must only be opened in an isolated machine. Bundle entry names on the PC and in the manifest are unchanged (contract compatibility).
* **I2, a download kept streaming after delete (confirmed).** The fix was cheap: the streaming task checks the bundle's status about once a second and ends the stream with an error when it is `deleted` or `expired`. The audit row records `cancelled_by_delete`.


## 2026-10-25 The agent starts the tray after an install or upgrade

Owner report: after upgrading to 1.1.7 the tray icon was missing. The MSI's restart manager closes the running tray during an upgrade, and the HKLM Run key only starts it again at the next logon. A fresh install has the same gap.

* **Where:** in the agent, not the MSI. When the service starts (which the MSI does at the end of every install and upgrade), the Windows platform waits for the tray pipe, then starts `kestrel-tray.exe --background` from the agent's own install folder in every active user session (console and RDP) that does not run it yet (`kestrel-win` `win/tray_launch.rs`, pure part `tray::sessions_needing_tray`).
* **Why not an MSI custom action:** an immediate custom action runs with the installer's token, so an install from an elevated prompt would start the tray elevated, and a fleet install by Intune / SCCM / GPO runs as SYSTEM in session 0 and starts nothing. Starting it from the service works for both.
* **Never elevated:** the token comes from `WTSQueryUserToken`, which returns the user's filtered (non-elevated) token. The tray has the user's own environment and desktop, and no job object, so it survives agent restarts.
* **Only at service start.** A user who quits the tray is not overridden while the agent runs. The tray's single-instance guard covers the race with the Run key at logon. The tray is **not** recorded as the agent's own child (`spawnreg`): agent children are exempt from detection for their lifetime, and the tray runs under the user's token, so any program of that user could inject into it (review finding, High). A second `--background` start no longer opens the tray window. The environment is always the user's (no launch without one), an existing tray only counts when its full image path is the installed one, and disconnected sessions (fast user switching, dropped RDP) are included. *Open:* a session the user first signs in to after the service start still relies on the Run key, and a disconnected session that reconnects later is not handled by a session-change notification.
* **Not lab-validated yet:** check in the VM that after an upgrade the tray appears without signing out, runs at medium integrity under the user, and that a second start (Run key at logon) does not create a second icon.
