## 2026-10-21 — Windows phase (v1.1 run)

* **Git identity and line endings.** Repo initialised locally with a baseline commit; author email `islahelanggi10@gmail.com` (owner's instruction). `core.autocrlf=false` and a `.gitattributes` forcing LF (CRLF only for `.ps1`/`.wxs`), because the owner's global `autocrlf=true` would turn `scripts/e2e.sh` into CRLF and break it in WSL. *Alt:* rely on global config — rejected.
* **WiX v6 pinned (6.0.2).** `dotnet tool install wix` now installs WiX 7, which adds an OSMF EULA acceptance gate. The installer is authored for v6 and CLAUDE.md names v6. *Alt:* migrate to v7 — deferred; licence terms are the same maintenance-fee model (see research report).
* **Defender exclusion for build output only.** Defender quarantined the `kestrel-detect` test binary as `Trojan:Win32/Cryware.B` (heuristic on the wallet/credential path tables the engine embeds). Per CLAUDE.md rule 4 we added exclusions only for `D:\project\kestrel\target`, `D:\project\kestrel\tray\src-tauri\target` and the scratch build root `D:\kestrel-build` (parallel `CARGO_TARGET_DIR`s, VM work files). Nothing else. **The shipped agent will hit the same heuristic on customer machines** — code signing + submitting the release binaries to Microsoft (WDSI false-positive submission) is an owner task; see HANDOFF.
* **Disposable VM = QEMU/KVM inside WSL2.** The host is Windows 11 *Home*: no Hyper-V Manager, no Windows Sandbox. WSL2 exposes `/dev/kvm` (nested virtualisation), so a Windows 11 Enterprise **Evaluation** VM (90-day, free from the Microsoft Evaluation Center) runs under QEMU in the Kali distro with a qcow2 overlay that is thrown away after each run. This satisfies CLAUDE.md's "disposable VM" requirement without enabling features or rebooting the host. Enterprise also lets us validate AppLocker enforcement (known risk 8). *Alt:* VirtualBox on the host (installs kernel drivers on the owner's PC) — rejected; skip Phase 2 — rejected since a safe option exists.

### Real-Windows sensor findings (host, read-only `sensors-test --detect` + raw `logman`/`tracerpt` captures, build 26200)

* **Registry (known risk 2) — confirmed broken.** Microsoft-Windows-Kernel-Registry `SetValueKey` (event 5) arrives with `KeyName` **empty**; only `KeyObject` (a kernel pointer) identifies the key. `OpenKey`/`CreateKey` (2/1) carry `BaseObject` + `RelativeName`, but run at ~14 000 events/s on a busy workstation — too costly to decode just to build a name cache. **Decision:** keep event 5 for attribution (pid, value name, KeyObject; ~13/s) and add a user-mode watcher (`RegNotifyChangeKeyValue`) on the curated key set (HKLM + every loaded `HKU\<SID>` and `HKU\<SID>_Classes`) that diffs values and emits the full key/value/data; join the two on value name within a short window, then remember KeyObject→key for later writes. Unattributed changes are still emitted (pid 0 = unknown writer). *Alt:* OpenKey cache (CPU), NT Kernel Logger KCB rundown (all registry ops, far higher volume).
* **DPAPI 16385 (known risk 4) — flows without the Debug channel.** Field names match the decoder. The DPAPI hardening control stays (harmless) but is no longer required for ST-03.
* **Network byte order (known risk 3) — correct.** `Test-NetConnection example.com:443` produced a `net_connect` to the resolved IP and port 443; no swapped ports.
* **Short-lived command lines (known risk 6) — OK.** `cmd /c echo …` start carried its full command line.
* **DNS:** queries that end NXDOMAIN / no-records (`QueryStatus` 9003 / 9501) were dropped by the decoder. They are useful (DGA, dead resolvers), so they are now emitted with empty answers.
* **Audit-API OpenProcess volume (known risk 1) — ~500 events/s**, 98 % with desired access `0x1200` (query-limited + set-quota) from one service. Filtered at the source to masks that can read/write/inject/duplicate/terminate.

### Phase 3-4 design decisions

* **Rule families behind one seam.** RW/CD/PS rules live in `kestrel-detect/src/families/*` behind a `Family` trait (events, ticks, alerts in; `FamilyHit`s out) and go through the engine's single emission path (mode, exclusions, de-dup, protected-process filters). *Why:* three parallel implementers without touching the 3.4k-line `engine.rs`, and no second action path that could bypass safety filters. `FamilyHit.audit_only` marks variants that must never act even when their rule is in Protect.
* **SigmaHQ pack is Audit-only and seeded server-side** as ordinary Sigma rules with author, upstream URL (pinned commit) and `DRL-1.1`, so attribution shows wherever a Sigma alert shows and admins keep control of each rule.
* **M6 (enrollment token on the command line):** fixed with an MSI→registry hand-off (protected DACL via `MsiLockPermissionsEx` SDDL; the agent verifies the DACL, takes and deletes the value). *Alt:* a C++ custom-action DLL reading `CustomActionData` and piping the token on stdin — more code to sign and maintain. *Residual:* the **uninstall** token still reaches `kestrel-agent uninstall --token` through `WixQuietExec`; it is single-use for a device that is being removed and is admin-only; documented in HANDOFF.
* **Policy version after a DB restore:** the server catches up (re-versions past what the agent reports, bounded to +1,000,000 per report) rather than adding an epoch to the agent protocol. *Why:* server-only change, works with every agent already deployed. *Alt:* `(epoch, version)` tuples — needs agent + server changes and still breaks when the restored DB carries the old epoch.
* **YARA-X moved into `kestrel-scan.exe`.** The agent no longer links YARA-X/wasmtime; `Scan` runs the scanner next to the agent with a target list in the SYSTEM-only state directory and a 15-minute timeout. *Why:* the agent binary is always resident; scanning is rare.
* **Elevation on the host is interactive.** After the owner declined a UAC prompt, no further elevated runs on the host; all elevated validation happens in the QEMU VM over SSH as `labadmin`.
* **Sigma: an unknown field never matches.** rsigma treats a missing field as `null`, so upstream filters such as `filter_main_null: ParentImage: null` would silently *suppress* detections whenever Kestrel lacked the parent (process started before the agent). Kestrel now presents uncollected fields as "present but unknown", matching no value. Missing data can neither satisfy a selection nor suppress an alert; the cost is an occasional extra Audit alert.
* **Sigma `process_access` only receives successful opens** (Kestrel's new failed-open telemetry for lsass would otherwise satisfy rules written for granted handles); `GrantedAccess` is the *requested* mask, noted on those rules.
* **Sigma pack contents:** the 70 "ready now" SigmaHQ rules (pinned commit `e3f4662`), all Audit; Tier-B/C rules deferred. Upstream rule `a7ee1722` has a typo (`-DisableRuntimeMonitoring`) and does not catch `-DisableRealtimeMonitoring`; two other pack rules do.
* **Known risk 5 (`HistoricalContext` = LoggerId) — holds on build 26200.** The provider-disabled watchdog runs at start and every 30 s; during the 45 s host probe it ran at least twice against Kestrel-Core/IO and emitted no `EtwProviderDisabled` tamper event and restarted no session. A wrong logger id would have flagged every watched kernel provider. (TP-01 itself is exercised in the VM.)

### 2026-10-21 — security review v1.1 fixes: WFP identity, frozen isolation inputs, remote paths

* **V-H10: agent-scoped WFP permits match the process identity, not only its path.** Every permit with an `FWPM_CONDITION_ALE_APP_ID` (isolation server + DNS permits, always-on server hard permits) also carries `FWPM_CONDITION_ALE_USER_ID` with a security descriptor granting `FWP_ACTRL_MATCH_FILTER` (0x1, SDDL `CC`) to one SID only: the service SID `NT SERVICE\KestrelAgent` when the agent's token holds it (the service has been installed with `SERVICE_SID_TYPE_UNRESTRICTED`; checked at run time with `CheckTokenMembership`), else the token's user SID (LocalSystem for an install whose service has no SID type; the interactive user for a console run). *Why the service SID:* a user-started copy of `kestrel-agent.exe` has neither, and even a process an admin starts as SYSTEM lacks the service SID. **Fail closed:** without an identity no agent permit is planned; `IsolateHost` is refused with an explicit error (isolating anyway would cut the agent off until the auto-release deadline), and the always-on hard permits are removed rather than left app-only. The Windows glue also refuses to add any app-scoped permit without the user-id condition (invariant `app_permits_have_user_sd`). Hard permits whose stored plan differs (e.g. installed by an older version without the condition) are replaced.
* **V-M7: isolation inputs are frozen at isolation time.** The resolver set is recorded when isolation starts (`WfpState.isolation_dns`; for older state files, the resolvers the existing plan already permits) and re-plans never permit a resolver that appeared later. Server IPs are **never re-resolved while isolated** (the 60 s re-plan and the hard-permit refresh both use the frozen isolation server set). *Alt considered:* add a re-resolved IP only after a successful mTLS handshake to it — rejected for now: it needs a probe connection outside the transport and a WFP permit before the probe can run. *Trade-off:* if the server's address changes while a host is isolated, the agent loses contact until the isolation auto-release deadline or the local break-glass (`kestrel-agent release-isolation`).
* **V-M1: network paths are never opened as SYSTEM.** `kestrel_scan::is_remote_path` (UNC, `\\host@port\` / `\\host@SSL\` WebDAV, `\\?\UNC\`, `\\.\UNC\`, `\??\UNC\`, `\Device\Mup\`, redirector devices, any non-drive `\\?\` / `\\.\` path) plus `GetDriveTypeW == DRIVE_REMOTE` for drive letters. Applied to "scan running processes" target selection, explicit scan paths, the kestrel-scan target list (defence in depth), and enrichment (metadata, SHA-256, Authenticode/catalog, Zone.Identifier): facts for such images stay *unknown*. Directory expansion for scans no longer follows junctions/symlinks.
* **V-L10 / V-L11:** YARA `include` is disabled and compile errors are reported as file name + the diagnostic's first line only (the rest quotes rule source). Each scan writes its target list to a fresh `create_new` file with a random name in the state directory and deletes it afterwards.

### 2026-10-21 — security review v1.1 fixes: agent updates and the MSI (V-H3, V-L9, V-M3, V-M2)

* **V-H3: one update at a time, verified from disk, pinned until msiexec exits.** The update slot is a process-wide atomic claimed in the transport *before* the task is spawned; a delivery while one runs is dropped with a log line. The download goes to `<state>\updates\dl-<random>.part` (`create_new`, share mode 0), is renamed to `pkg-<random>.msi`, re-opened read-only with `FILE_SHARE_READ` only and hashed through that handle; the handle is held until msiexec exits (the hash from the network stream must agree too). *Why hold until exit:* the install runs while we wait; when the upgrade stops the service, the process dies and the handle closes with it, which is fine because msiexec has long opened (and cached) the package by then.
* **Authenticode on update MSIs is optional and off by default.** Build-time `KESTREL_UPDATE_REQUIRE_SIGNED=<signer subject substring>` makes the agent require a valid Authenticode signature from that signer; the owner has no code-signing certificate yet, so the Ed25519 manifest signature + SHA-256 remain the trust anchor. Until `kestrel-win` exports an Authenticode helper to the agent, a build with the variable set **fails closed** (no update installs). Recommended once a certificate exists.
* **V-L9:** download deadline 30 min overall, 60 s per read (and for the response headers / TLS handshake 20 s), and at least 64 KiB per 60 s window after the first byte.
* **V-M3: updates must be able to succeed and their outcome is reported.** msiexec `/i <pkg> /qn /norestart /l*v <pkg>.log` is waited for (max 60 min). Exit 0 / 3010 / 1641 = success (3010/1641 reported with a reboot note), anything else = failure with the code. `KV_LAST_UPDATE` is written only on success. The version is recorded as *pending* before msiexec starts: the MSI upgrade stops the service, so the **new** agent reports `UpdateResult ok=true` at start-up when the pending version is the one running, and a failure ("installer did not complete") when it is not. A failed version is retried at most every 6 h (`update_attempt` = `version|ms`).
* **MSI upgrade design:** `<MajorUpgrade Schedule="afterInstallExecute">` (install the new version over the old one, remove the old product last, so the enrolled identity, service registration and state survive), launch condition accepts `WIX_UPGRADE_DETECTED`, `CA_Install` (enrolment) runs only when `NOT Installed AND NOT WIX_UPGRADE_DETECTED`, and a `ServiceControl` (stop + start on install) in a component conditioned on `WIX_UPGRADE_DETECTED` restarts the agent around the file replacement (never on fresh install or uninstall, so an uninstall cannot stop the agent before the token check). `kestrel-agent install` also keeps an existing identity for the same server + CA instead of enrolling again. The Rust binaries have no version resource, so `DefaultVersion` makes the packaged copy replace the on-disk file (WIX1103 warnings are expected). The first upgrade from an already deployed 0.1.0 package uses the old package's uninstall condition (`NOT UPGRADINGPRODUCTCODE`), which still works.
* **V-M2: the uninstall token can no longer be skipped with `UPGRADINGPRODUCTCODE`.** `CA_Uninstall` runs on every `REMOVE="ALL"`; the custom action receives `UPGRADINGPRODUCTCODE`, the UpgradeCode, version and ProductCode and waives the token only when the claimed product is registered under Kestrel's UpgradeCode (`MsiEnumRelatedProducts`), installed (`MsiQueryProductState` = default), not this product, and newer. This relies on the new product being registered when the old one is removed (afterInstallExecute) — to be confirmed in the lab VM. Partial removal (`REMOVE=<features>`) is refused by an error custom action and the feature is `AllowAbsent="no"`. *Not done:* a TP alert for `msiexec /x` of the product code (engine side).
* **V-H1 (CLI):** `update-keygen` runs icacls from `GetSystemWindowsDirectoryW` (via `platform_win::windows_dir`), msiexec likewise; no executable path in the agent is derived from `%SystemRoot%` any more.
### 2026-10-21 — fix round 2, release candidate

* **Registry writer attribution: a sole candidate is Exact.** After round 1, every first write was Heuristic, so the PS rules could no longer act on malware's own first write (re-review NEW-1). Now one distinct writer pid in the join window is Exact. Two or more candidates are Heuristic, which still defeats framing a legitimate process, because the attacker's own write is always a candidate. Every change waits for its full join window, so a late rival write is still counted.
* **Re-planted autoruns are removed again.** `RemoveAutorun` bypasses the 10-minute de-duplication, gated to once per 30 s per object; a re-plant inside the gate is held, not dropped. The re-alert is limited to once per 10 minutes.
* **The agent's identity is image path + its own pid** (`HostContext.agent_pid`). A user who starts the real `kestrel-agent.exe` gets an ordinary process.
* **Engine-proposed quarantine never touches a validly signed file.** In shared folders (`ProgramData`, `Users\Public`, other profiles) it quarantines only files that are known unsigned or invalid; `Unknown` is refused there.
* **Canary reader exemptions require SYSTEM.** User-context backup tools (FileHistory, sdclt, an admin's scanstate) now trip ST-16. This is accepted: a stealer runs as the user.
* **Dead letters store metadata only** (length + SHA-256, redacted DB error), with 30-day retention and the newest 1,000 rows per device.
* **Version 1.1.0, tag `v1.1.0-rc1`.** An RC rather than final because the binaries are unsigned (Defender flags them) and the update signing key is not provisioned. Both are owner tasks.
* **Network blocks need an analyst "lift" action.** The lab showed that ST-02/ST-07/ST-16 image blocks are permanent (`ttl_secs: None`), and nothing in the console could lift them; a false positive on a business app would need a reinstall. Added `UnblockNetwork` (by image, block id, or all non-isolation blocks); restoring a quarantined file also lifts that image's blocks. Automatic blocks stay permanent by default, because a confirmed stealer should stay cut off until an analyst decides.
* **Lab VM hostname is `W-`.** The unattend `ComputerName` was not applied; the agent reports Windows' real name correctly. Cosmetic, lab only.

### 2026-10-21 — remote desktop and remote file manager (owner request)

* **The owner asked for VNC-style remote control and a full remote file manager in the admin console.** This reverses the "no screenshot/keystroke capture" privacy rule for **interactive, admin-initiated sessions only**; CLAUDE.md is updated accordingly.
* **Owner's choices:**
  * Screen sessions start **without employee consent**; the employee always sees a notification and an on-screen banner for the whole session.
  * The file manager has **full SYSTEM access** (browse, download, upload, rename, delete, mkdir) with no extra confirmation step.
  * Both are on by default in policy, and each has a policy switch.
* **Kept regardless:**
  * only the admin role can use them;
  * every session and file operation is in the hash-chained audit log;
  * frames and file contents never enter telemetry or ClickHouse;
  * the agent refuses when the policy switch is off.
* **Risk accepted by the owner:** a compromised admin account or server can now view and control every enrolled PC and read or modify any file on it. Recommend MFA for all admins and a restricted network path to the console.

* **Remote access is chosen per installer and locked on the device (owner request, refined).**
  * The admin web generates an installer per remote-access profile:
    * **None**;
    * **Unrestricted** (remote control + full file manager);
    * **Guarded** (remote control + file manager, with customisable guardrails: consent, reason, MFA re-auth, upload/delete, session and idle limits, allowed hours, blocked paths).
  * The profile is bound to the enrollment token and pinned on the agent at enrollment as a **ceiling** that later server messages cannot raise. The effective setting is the intersection of that ceiling and the policy, and the agent enforces it.
  * So "no remote access" devices stay closed even if the server or an admin account is compromised. Changing a device's profile requires reinstalling with the uninstall token.
  * Existing policies and previously enrolled agents default to **None**.
  * The banner and notification on the employee's screen are mandatory in every profile, including Unrestricted: covert screen viewing creates legal exposure under PDPA and UU PDP.
  * Building one MSI per profile is impractical, because WiX doesn't run on the Linux server. The server instead generates a setup script that embeds the server address, the agent CA, the MSI hash and the profile-bound token.

* **One generic live channel on the existing stream.** `AgentPayload::Live` / `ServerPayload::Live { session_id, msg }` carry both features (JSON over the mTLS gRPC bidi stream, binary as base64). Agent-side they use envelope seq 0, bypass the SQLite outbox and are never acked; the server never tracks them in its ack map and never stores them. *Why:* no new port, listener or certificate path; the stream is already authenticated per device. *Alt:* a second gRPC method with `bytes` fields: ~30 % less bandwidth for frames, but a proto change for every agent and server and a second stream to authenticate and tear down. Base64 + zstd is acceptable for 5â€“10 fps JPEG.
* **Compatibility by capability, not by version.** `Hello.capabilities` (`live.files`, `live.desktop`) tells the server what the agent supports; the server returns 409 "agent too old" otherwise. The live message enums carry `#[serde(other)] Unknown` so either side can add message kinds later. An old agent that somehow receives a `Live` payload logs it as undecodable (not acked); an old server drops an agent `Live` as malformed (seq 0, not acked).
* **Interactive console session required, API tokens refused.** `remote.desktop` / `remote.files` are only reachable through the admin role's `*`, and additionally require a cookie session (CSRF-protected). *Why:* a leaked automation token must not be able to read or change files on every PC. The WebSocket cannot carry a custom header, so it takes the CSRF token as a query parameter and checks `Origin` against `Host`.
* **Server-side policy check as well as the agent's.** The server refuses with 403 `disabled_by_policy` before contacting the agent (clear UI message, no round trip); the agent still enforces its own copy of the policy (an agent with a newer/older policy is authoritative for itself).
* **Network paths refused.** The file manager accepts only `X:\â€¦` paths and refuses network drives, consistent with V-M1 (the agent never opens network paths as SYSTEM).
* **Protected folders:** the agent install folder and `%ProgramData%\Kestrel` are refused for every operation, and their ancestors for rename / delete / overwrite, after canonicalisation (8.3 names, junctions, symlinks). Uploads never open an existing file for writing (temp file + rename), so a hard link cannot be used to overwrite a protected file. *Residual:* reading a file through a hard link that an admin created by other means into a protected folder is not detected.
* **Tray compatibility.** A new `TrayRequest::SubscribeWith { features }` opts a tray into `TrayResponse::RemoteSession` pushes; older trays keep using `Subscribe` and never receive the new response type (their parser would reject it). The employee notification itself is an ordinary `Notification` (severity High) that every tray version shows as a Windows toast, plus the helper's on-screen banner, which does not depend on the tray at all.
* **JPEG encoder: `jpeg-encoder` 0.7.1** (MIT OR Apache-2.0, plus the permissive Independent JPEG Group licence for the DCT code). `IJG` was added to the `deny.toml` allow list; the IJG notice is in the README's third-party notices. *Alt:* the `image` crate (larger dependency tree for one encoder).
